## 1. `yunhee sql` 기본 모드가 읽기 전용이 아니다 — 치명

**증상**
```bash
$ yunhee sql "select current_setting('transaction_read_only') ro"
| ro |  → off
$ yunhee sql "update sys01_company set sys01_note=sys01_note where sys01_company_id=-1; commit"
UPDATE 0
COMMIT ok
```
- 기본(읽기) 모드에서 UPDATE가 오류 없이 실행된다.
- 같은 스크립트에 `COMMIT`이 있으면 **실제로 저장된다**. 위 예는 0건이라 바뀐 것이 없다.
- `finally`의 `conn.rollback()` 덕분에 COMMIT이 없으면 저장은 안 된다. 하지만 "읽기 전용"이라는 안내와 동작이 다르다.
- COMMIT·DDL 가드가 `--rollback` 모드에만 있어서, 기본 모드에서는 COMMIT이 그대로 통과한다.
  - `--rollback` 모드 자체는 정상이다. 회사 초기화 SQL 15문장이 돌고, `\gset`도 되고, 남은 변경은 0건이었다.

**원인** (`tools/sql_runner.py`)
- L175 `psycopg.connect(db_url, autocommit=False)` 다음 첫 `cur.execute("SET statement_timeout …")`(L184)가 **트랜잭션을 연다**.
- 그 뒤 L187 `SET default_transaction_read_only = on`은 **다음 트랜잭션부터** 적용된다. 이미 열린 현재 트랜잭션은 읽기·쓰기 그대로다.
- L155-163 DDL_RE 가드가 `if rollback:` 안에만 있다.

**수정**
1. 첫 문장 실행 전에 읽기 전용을 건다. 다음 중 하나:
   - `conn.read_only = True` (psycopg3, connect 직후, execute 전)
   - `psycopg.connect(db_url, autocommit=False, options="-c default_transaction_read_only=on")`
   - 첫 실행을 `cur.execute("SET TRANSACTION READ ONLY")`로 한다.
2. COMMIT·END·DDL 가드를 **두 모드 모두에** 적용한다.
   - 기본 모드에서는 `ROLLBACK`, `SAVEPOINT`, `SET`(세션 변경) 외의 트랜잭션 제어문도 막는다.
3. 기본 모드에서 쓰기 문장(INSERT·UPDATE·DELETE·MERGE·CALL)이 보이면 실행 전에 "읽기 전용 모드입니다. 쓰기 시험은 --rollback" 오류를 낸다.
   - DB의 read-only 오류에만 맡기지 않는다. `CALL`은 프로시저 안에서 COMMIT할 수 있으므로 기본 모드에서는 무조건 막는다.
4. `--rollback` 모드의 `CALL` 경고: 프로시저 안의 COMMIT은 ROLLBACK으로 되돌릴 수 없다. `pg_proc.prosrc`에 `COMMIT`/`ROLLBACK`이 있으면 실행 전에 거부한다.
   - 예: `dcr01_import_from_admin`은 없음 → 통과.

**검증**
- `yunhee sql "select current_setting('transaction_read_only')"` → `on`
- `yunhee sql "update sys01_company set sys01_note=sys01_note where sys01_company_id=-1"` → 실행 전 거부(또는 `cannot execute UPDATE in a read-only transaction`)
- `yunhee sql "select 1; commit"` → 가드에 걸림
- `yunhee sql -f init.sql --rollback` → 지금처럼 정상, "남은 변경 없음"
- 테스트: 위 4개를 `tests/`에 넣는다(DB 없으면 skip).

## 2. `port-save` 결과를 그대로 쓰면 서버가 뜨지 않는다

**증상** (`yunhee port-save sys01_company --cols company_nm`)
1. **같은 id 두 번**: `<insert id="insertFormIcs30">`이 두 번 나온다. AS-IS에서 `ics30_compliance.insertFormIcs30`과 `ics33_compliance_answer.insertFormIcs30`이 이름이 같기 때문이다. 한 TOBE 매퍼 namespace에 넣으면 MyBatis가 시작 시 `Mapped Statements collection already contains value`로 실패한다.
2. **INSERT인데 `<select>` 태그**: AS-IS `ast02_detail.insertFromAst02`, `sys30_leave_year.insertFromSys30`이 `<select id=… resultMap="mapper">` 안에 INSERT를 쓴다. 그대로 옮기면 TOBE에서 resultMap이 없어 실패하거나, 매퍼 메서드가 select로 실행된다.
3. **원본 Java가 넣던 고정값이 사라짐**: ast02의 `ast02_use_yn = #{useYn}`은 UpdateDataModel이 `map.put("useYn", "true")`로 넣는다(L161). pay04의 `#{itemTypeCodeName}`은 `"PayFormulaCode"`(L172)다. 결과만 보면 호출하는 쪽이 무엇을 넣어야 하는지 모른다.

**원인** (`tools/as_is/sql_porter.py`)
- L575-584: 원본 태그를 `m_tag.group(1)` 그대로 쓰고, id도 원본 SQL id를 그대로 쓴다.
- `map.put(...)` 값은 읽지 않는다.

**수정**
1. 부수 효과 SQL의 TOBE id는 `{매퍼}`+`{원본 id}`를 camelCase로 붙여 항상 유일하게 만든다.
   - 예: `ics30ComplianceInsertFormIcs30`, `ics33ComplianceAnswerInsertFormIcs30`
   - 만든 id 목록에 중복이 있으면 숫자를 붙이고 경고한다.
2. 본문이 `INSERT`/`UPDATE`/`DELETE`/`CALL`로 시작하면 원본 태그와 관계없이 `<insert>`/`<update>`/`<delete>`/`<update>`로 바꾼다. `resultMap`·`resultType` 속성은 버린다.
3. `UpdateDataModel.java`의 그 블록에서 `map.put("키", 값)` 중 리터럴(문자열·숫자·`0l`·`null`)을 읽는다.
   - 해당 `#{키}`를 그 값으로 바꾸거나, 바꾸지 않을 거면 SQL 위에 `<!-- useYn = 'true' (UpdateDataModel L161) -->` 주석을 단다.
   - 바꾸는 쪽을 권장한다. TOBE 코드는 `companyId`만 넘기게 된다.
4. 결과 끝에 "Mapper 인터페이스 메서드 목록"을 같이 낸다(`int ics30ComplianceInsertFormIcs30(Long companyId);` …). 이름이 XML과 어긋나지 않게 하기 위해서다.

**검증**
- `yunhee port-save sys01_company --cols company_nm`
  - 결과의 `id="…"`에 중복이 0개
  - `<select`는 `selectNextId` 하나뿐
  - `#{useYn}`·`#{itemTypeCodeName}`이 없거나 주석이 붙음
- 그 결과를 임시 매퍼로 저장하고 `yunhee sql-check --tobe <폴더>` → 모두 ✅
- 비교 기준: AssetERP_1이 손으로 쓴 `backend/src/main/resources/mapper/SysCompanyMapper.xml`(같은 15개 SQL, 고정값을 SQL에 넣음)

## 3. `sql-check --tobe` DTO 필드 대조가 틀리게 경고한다 (오탐 3종)

SQL 자체의 EXPLAIN 검사는 정확하다. 일부러 넣은 오류 4건(없는 컬럼 2, 없는 프로시저, 잘못된 별칭)을 모두 줄 번호와 함께 잡았다. 틀리는 것은 record 필드와 별칭을 비교하는 경고뿐이다.

**3-A. record를 이름만으로 찾는다**
- 증상: `CompanyMapper.findByCompanyCode`의 resultType이 `kr.co.kfs.asseterp.biz.company.dto.CompanyRes`(필드 4개)인데, `biz.sys.dto.CompanyRes`(필드 32개)와 비교해 "필드 누락 30개"를 낸다.
- 원인: `sql_checker.py` L376 `r.glob(f"**/{cls_name}.java")` — 패키지를 버리고 첫 파일을 쓴다.
- 수정: resultType FQN을 경로로 바꿔(`kr/co/kfs/asseterp/biz/company/dto/CompanyRes.java`) 소스 루트(`src/main/java`) 아래에서 정확히 찾는다. 짧은 이름(typeAlias)이면 그때만 glob하고, 여러 개면 경고하고 대조를 건너뛴다.

**3-B. AS 없이 쓴 컬럼을 세지 않는다**
- 증상: `AuditLogMapper.findRecent`가 `SELECT audit_id, event_type, …`(AS 없음)인데 "필드 누락 10개 전부"를 낸다.
- 원인: `extract_select_aliases_from_sql`(L393)이 `\bAS\s+(\w+)`만 본다.
- 수정: 최상위 SELECT 목록을 콤마로 나눈다(괄호 깊이 0에서만). 항목마다 출력 이름을 정한다.
  - `… AS x`면 x
  - `t.col`·`col`처럼 맨 끝이 식별자면 그 식별자
  - 그 밖의 식이면 이름 없음 → 대조에서 뺀다

**3-C. 안쪽 SELECT(서브쿼리·CTE)의 별칭까지 센다**
- 증상:
  - `SysMenuMapper.searchTailMenusByUser` "미사용 별칭: depth, path" — `WITH RECURSIVE …(depth, path)` 안의 별칭
  - `AccountMapper.findEmployee` "미사용 별칭: ageDays, pwd" — `LEFT JOIN (SELECT … AS pwd, … AS age_days) pw` 안의 별칭. 바깥에서는 `pw.pwd AS password`로 쓴다.
- 원인: 위와 같다. SQL 전체에서 `AS`를 찾는다.
- 수정: 3-B의 "최상위 SELECT 목록"만 쓴다.
  - `WITH … AS (…)` 뒤의 마지막 본 SELECT가 대상이다.
  - `<include>`는 펼친 뒤 판단한다.

**검증**
- `yunhee sql-check --tobe AssetERP_1/backend/src/main/resources/mapper` → ⚠가 0개
  - 지금은 AuditLog 1, Company 2, SysMenu 1, Account 2
- 일부러 `AS note` → `AS notes`로 바꾼 임시 매퍼 → 지금처럼 "필드 누락: note; 미사용 별칭: notes"

## 4. `api`·`compare`: `-c`만 주면 동작이 서로 다르다

**증상**
- `.yunhee.toml`에 `tenant`가 있으면 `yunhee api … -c kfstest`가 tenant를 자동으로 붙인다(11행, 정상).
- toml이 없으면 `.env.local`에 `YUNHEE_TEST_COMPANY=admin`이 있어도:
  - `api`는 "오류: 회사 선택 로그인은 admin 테넌트에서만 됩니다: -t admin"으로 **멈춘다**.
  - `compare`는 같은 문구를 노란 경고로 찍고 **계속 진행해** 결과(`API rows=11`)를 낸다. 진짜 오류인지 알 수 없다.

**원인** (`cli.py`)
- `api`: L410-418 `target_tenant = tenant or config.API_DEFAULT_TENANT`, 없으면 Exit
- `compare`: L573-579 같은 조건인데 경고만 한다.
- `API_DEFAULT_TENANT`가 toml에서만 채워지는 것으로 보인다.

**수정**
1. 기본 테넌트를 고르는 순서를 한 함수로 만들고 api·compare가 같이 쓴다.
   - 순서: `-t` → `.yunhee.toml [api] tenant` → `.env.local YUNHEE_API_DEFAULT_TENANT`(신설) → `YUNHEE_TEST_COMPANY`
2. 그래도 없으면 둘 다 **멈춘다**(Exit 1).
3. 결과 머리 태그(`[AssetERP_1 · tenant=admin · company=kfstest]`)를 `compare`에도 찍는다.

**검증**
- toml 없는 폴더에서 `yunhee api GET /api/v1/sys/roles -c kfstest` → 11행, 태그에 `tenant=admin`
- 같은 곳에서 `yunhee compare GET /api/v1/sys/roles -c kfstest --sql sys04_role.selectByName --param roleName=%% --param companyId=28000` → 경고 없이 `API rows=11, SQL rows=11 ✅`
