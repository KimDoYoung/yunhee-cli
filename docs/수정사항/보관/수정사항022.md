# 수정사항 022 — `yunhee log` 결함과 다듬을 점 (대상 0.2.5)

- 작성: 2026-10-12, yunhee **0.2.5** 기준. 021 B(`yunhee log`)를 AssetERP_1 Tomcat 배포본(docker `t3600-tomcat`)에 실제로 돌려 본 결과다. 이 문서를 모두 반영하면 버전을 **0.2.6**으로 올린다.
- 잘 되는 것: `api … --log`(응답 + 매퍼 ID·파라미터·행 수·WARN/ERROR), `log trace`(`--sql`·`--raw`, 없는 trace면 Exit 1), `log req`(대소문자 무관, `--since`·`--since-deploy`·`--trace`), `log tail --since`·`--from/--to`(KST 입력 → UTC 비교, 021 B-3(0) 규칙 1대로), `log errors --since-deploy`, 시작 옵션 둘이면 오류, 잘못된 기간 형식 오류.
- 아래는 결함이다. 우선순위 순. 줄 번호는 `src/yunhee/tools/log_reader.py`(0.2.5).

## 1. 첫 줄이 빈 WARN/ERROR 때문에 `errors`·`tail`이 죽음 (가장 급함)

**재현**
```
yunhee log errors                 # 기본 1h
yunhee log errors --since 1h
yunhee log errors --ignore Global
yunhee log tail --since-run last
→ 오류: list index out of range
```
`--since-deploy`는 된다(아래 원인 때문에 우연히 피해 간다).

**원인**: Spring Boot가 기동할 때 쓰는 WARN의 메시지가 빈 줄이고, 본문은 다음 줄에 있다.
```
2026-10-12 00:22:18.509 [...] WARN  o.s.b.a.s.s.UserDetailsServiceAutoConfiguration - 
Using generated security password: 70ea24fd-…
```
파싱 결과 `msg=''`, `extra_lines=['', 'Using generated security password: …']`. `''.splitlines()[0]`에서 IndexError가 난다. 같은 코드가 네 곳에 있다:
- L641 (`get_trace_summary`), L876·L922 (`get_errors_summary`), L1085 (`get_tail_summary` standalone 에러)
- L952 `res_exp.strip().splitlines()[0]`(`--explain`)도 Qwen이 빈 응답을 주면 똑같이 죽는다.

`--since-deploy`는 이 줄이 배포 기준(`Started … in`) 줄보다 앞이라 범위에 들어오지 않아서 괜찮았다. `--since-run last`도 범위에 기동 시각이 들어오면 죽는다.

**수정**
1. 첫 줄을 고르는 함수를 하나 두고 네 곳 모두 그것을 쓴다: `msg`의 첫 비어 있지 않은 줄 → 없으면 `extra_lines`의 첫 비어 있지 않은 줄 → 없으면 `(빈 메시지)`.
2. `errors`를 묶는 키(L873~882 `norm_msg`)도 이 첫 줄로 만든다. 지금은 빈 문자열이라 서로 다른 빈 메시지 WARN이 한 묶음이 된다.
3. **마스킹 추가**: `Using generated security password: <UUID>`의 값을 `****`로 바꾼다(B-4 표에 추가). 지금은 `--raw`·`errors`에 그대로 나온다. 운영 비밀번호는 아니지만 "비밀번호" 줄을 그대로 보여 주지 않는 것이 맞다.

**기대 (검증 ID `022-1 빈 첫 줄`)**: 픽스처 error 로그에 위 두 줄을 넣고 `yunhee log errors --file <픽스처> --tz UTC --from "2026-10-12 09:00"` → Exit 0, 출력에 `UserDetailsServiceAutoConfiguration - Using generated security password: ****`, `!70ea24fd`.

## 2. WARN/ERROR가 두 번씩 나오고 두 번 세어짐

**재현**: `yunhee api GET /api/v1/emp/educations --log`(405가 나는 호출)
```
WARN/ERROR 2:
  03:04:20 WARN k.c.k.a.c.e.GlobalExceptionHandler - 요청 처리 실패: status=405, …
  03:04:20 WARN k.c.k.a.c.e.GlobalExceptionHandler - 요청 처리 실패: status=405, …
```
`log tail`의 요약 줄도 `WARN 2`로 센다. `log errors`는 `× 2`.

**원인**: 서버는 한 번만 쓴다. logback 설정상 WARN 이상은 `-info.log`(DEBUG 이상 전부)와 `-error.log` **둘 다**에 쓰인다(컨테이너 안에서 `grep -c '<trace>.*WARN'` → 두 파일에 각 1줄). yunhee가 두 파일을 합치면서(L163~168 trace grep, L207~218 tail 병합) 중복을 지우지 않는다.

**수정**
- 두 파일을 합친 뒤 `(ts, trace, thread, level, logger, msg)`가 같은 레코드는 하나만 남긴다(`read_logs_local`도 같은 방식으로).
- 또는 info 파일만 읽어도 WARN/ERROR가 모두 있으면 error 파일은 `errors`(error_only)에서만 쓴다. 어느 쪽이든 결과는 한 번씩이어야 한다.
- `--raw`도 같은 줄이 두 번 나온다(info 줄과 error 줄이 시각 순서도 어긋나 섞인다) — 중복을 지운 뒤 시각 순으로 정렬해 출력.

**기대 (검증 ID `022-2 중복 제거`)**: info·error 픽스처에 같은 WARN 한 줄씩 → `log trace <id>`의 `WARN/ERROR 1:`, `log errors`의 `× 1`, `log tail` 요약의 `WARN 1`.

## 3. `log tail --level`이 무시됨

**재현**: `yunhee log tail --since 30m --level WARN` → `--level` 없이 돌린 것과 같은 출력(200 요청까지 전부).

**원인**: `get_tail_summary(… level=…)`(L963~)가 인자를 받기만 하고 쓰지 않는다.

**수정**: `--level WARN`이면 WARN 이상 레코드가 하나라도 있는 trace와 standalone WARN/ERROR만 보여 준다(`ERROR`면 ERROR만). 요약 줄의 수는 걸러진 범위의 것.

**기대 (검증 ID `022-3 level`)**: 200 요청 1개 + 405(WARN) 요청 1개 픽스처 → `--level WARN`이면 405 줄만, `--level ERROR`면 `(기록 없음)`.

## 4. `log tail --grep`이 줄을 거르면서 SQL 수가 0이 됨

**재현**: `yunhee log tail --since 30m --grep careers`
```
최근 30m: 요청 1, SQL 0, WARN 0, ERROR 0
  03:04:27  GET   /api/v1/emp/persons/1/careers   200  11ms  SQL 0  trace afc00e89…
```
같은 요청이 `--grep` 없이는 `SQL 2`다.

**원인**: L1034~1035가 **레코드(줄)** 단위로 거른 뒤 trace로 묶는다. 접근 로그 줄만 남고 같은 trace의 SQL 줄은 빠진다.

**수정**: 먼저 trace로 묶고, 묶음 안의 어느 줄이라도 문자열을 포함하면 그 trace 전체를 남긴다(standalone 레코드는 줄 단위 그대로). 요약 수도 남은 trace 전체로 센다.

**기대 (검증 ID `022-4 grep`)**: `--grep careers` → `SQL 2`, 요약 `SQL 2`. `--grep emp07_career`(SQL 본문에만 있는 문자열)로도 같은 요청이 나온다.

## 5. `log tail`에서 요청 안의 WARN/ERROR가 보이지 않음

**재현**: `yunhee log tail --from 12:04 --to 12:05` → 요약은 `WARN 2`인데 목록 어디에도 WARN이 없다. 405·401 요청 줄은 상태 코드만 보인다.

**원인**: L1080~1088은 trace가 없는(standalone) WARN/ERROR만 줄로 넣는다. trace에 속한 WARN/ERROR는 수에만 들어간다. 021 B-3(4)의 예시는 `WARN 06:35:36 StompAuthChannelInterceptor - …` 줄을 보여 준다.

**수정**: 요청 줄 끝에 그 trace의 WARN/ERROR 수와 첫 메시지를 붙인다. 예:
```
  03:04:20  GET   /api/v1/emp/educations   405   6ms  SQL 1  trace b1e9fbe5…  ⚠WARN 요청 처리 실패: status=405, …
```
(60자에서 자름. ERROR가 있으면 ERROR 것을 우선.)

**기대 (검증 ID `022-5 tail 경고 표시`)**: 405 픽스처 → 요청 줄에 `⚠WARN`과 `status=405`.

## 6. `--archived`가 없는데 안내 문구에 나옴

**재현**
```
yunhee log trace deadbeef00000000
→ trace deadbeef00000000: 로그에 없음 (오늘 파일만 봄 — 지난 날은 --archived)
yunhee log trace deadbeef00000000 --archived
→ Error: No such option: --archived
```
`trace`·`req`·`errors`·`tail` 어느 것의 `--help`에도 `--archived`가 없다. 안내 문구는 L346·350·359·364·368(`--since-deploy`)과 L517(trace)에 있다.

**수정**: 021 B-2대로 `--archived`를 구현한다(`archived/yyyy-MM/AssetERP-backend-info-yyyy-MM-dd.N.log.gz`를 `docker exec … zgrep -F`/`zcat`). 이번에 구현하지 않으면 안내 문구에서 `--archived`를 빼고 `--file <gz 경로>`를 안내한다. 쓸 수 없는 옵션을 안내하면 안 된다.

**기대 (검증 ID `022-6 archived`)**: `yunhee log trace --help | grep -c archived` ≥ 1, 또는 안내 문구에 `--archived`가 없다.

## 7. 작은 것

1. **`--tz` 도움말**: 지금 `로그 시간대 (UTC 또는 KST)`라서 "출력 시간대"로 읽힌다. docker 로그에 `--tz KST`를 주면 UTC로 쓰인 로그를 KST로 읽어서 `--since 2h`도 `(기록 없음)`이 된다(재현함). 도움말을 `로그 파일에 쓰인 시각의 시간대 (docker 기본 UTC — 보통 지정하지 않음, --file과 함께 쓸 때만)`로 바꾼다.
2. **`--from`/`--to` 도움말**: 입력이 KST(호스트 시간대)라는 것을 적는다(`시작 시각, 호스트 시간대(KST) — 예: 15:10`). 출력은 UTC라 사용자가 출력에서 본 시각(UTC)을 그대로 `--from`에 넣는 실수가 쉽다. 머리 줄의 범위 표시(`범위 … UTC (12:04 ~ 12:05 KST)`)는 좋으니 그대로 둔다.
3. **trace ID 검사**: `yunhee log trace xyz`도 grep을 돈다. 16진수(8~32자)가 아니면 Exit 2 + "trace ID는 16진수".
4. **잡음 줄**: `log tail` 기본 출력에 `(비-HTTP 요청)`(스케줄러·WebSocket 메시지)과 `GET /ws 101`이 화면 확인 요청보다 많다. 기본은 숨기고 요약 줄에 `(비-HTTP 3, /ws 2 숨김 — --all)`처럼 수만 적는다. WARN/ERROR가 있는 비-HTTP trace는 숨기지 않는다.
