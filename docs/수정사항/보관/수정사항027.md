# 수정사항 027 — 그리드가 여럿인 클래스를 잘못 셈, 원본 교체 뒤 옮긴 SQL의 변경을 못 찾음 (대상 0.3.1)

- 작성: 2026-10-14, yunhee **0.3.1** 기준. 반영하면 **0.3.2**.
- AssetERP_1 A04(사용자별 권한그룹 맵핑 `Sys05_Tab_PersonRole`)에서 찾았다. 1·2·3은 결함이다(06 항목 3·10 대조를 yunhee만으로 끝낼 수 없음). 4는 빠진 기능, 5는 작은 개선이다.
- 우선순위: **1 > 4 > 2 > 3 > 5**. 1은 그리드가 둘 이상인 화면마다(A02·A04 등) 대조표를 손으로 고치게 하고, 4는 이미 끝낸 화면의 SQL이 원본과 달라져도 알 수 없게 한다.

## 1. 그리드 수를 0 또는 1로만 셈 (`analysis screen --list`, `analysis ui`)

**재현**
```
cd AssetERP_1
yunhee analysis screen Sys05_Tab_PersonRole --list
→ | Sys05_Tab_PersonRole | 65 | 2 | 5 | 0 |          (실제 그리드 2: userGrid, userRoleGrid)
yunhee analysis ui Sys05_Tab_PersonRole --tobe frontend/src/pages/sys
→ | Sys05_Tab_PersonRole | 2/2 | 5/5 | 0/1 |          (TOBE도 <SingleGrid> 2개)
bash tools/ui-count.sh docs/as-is/src/sys/screens/Sys05_Tab_PersonRole.md
→ 그리드 2
```
- 색인 화면 파일에는 두 그리드가 다 있다:
  `- 그리드 \`userGrid\` (buildUserGrid(), 체크박스):`, `- 그리드 \`userRoleGrid\` (buildRoleGrid(), 체크박스):`
  Grid Spec에도 `const buildUserGrid = () => [`, `const buildRoleGrid = () => [` 두 블록이 있다.
- A02(`Sys04_Tab_RoleAdmin`, gridCompany + gridRole)에서도 같은 일이 있었다(05 §7 0.2.7 메모). 그 뒤로 매번 `tools/ui-count.sh`로 교차 확인하고 대조표를 손으로 고친다.

**원인**
- `tools/analysis/screen.py` L65·L133, `tools/analysis/ui.py` L109·L167:
  `grid_cnt = 1 if re.search(r"const buildGrid\b|그리드[^\n]*\(buildGrid", …) else 0`
  ① `1 if … else 0`이라 **있는지만** 본다(개수가 아님). ② 메서드 이름이 정확히 `buildGrid`일 때만 맞는다 → `buildUserGrid`·`buildRoleGrid`는 0.
- `ui.py` L189·L201(TOBE): `t_grid = 1 if re.search(r"<(?:SingleGrid|MultiGrid|CellEditGrid|ModalEditGrid)\b", f_text) else 0` — 같은 문제로 2개를 1로 센다.

**수정**
1. AS-IS: 클래스 절 안의 `^- 그리드 \`` 줄 수(없으면 Grid Spec의 `const build\w*Grid\b` 블록 수)를 센다. 두 방법의 값이 다르면 큰 값을 쓰고 `⚠`를 붙인다.
2. TOBE: `<(SingleGrid|MultiGrid|CellEditGrid|ModalEditGrid)\b` **나온 횟수**를 센다(주석 안은 뺀다).
3. 트리 그리드(`getTreeGrid`)는 0.2.4 때부터 0으로 셌다(05 §7 C02 메모). 같은 기준으로 `- 트리` 또는 `getTreeGrid`도 1개로 센다.

**기대 (검증 ID `027-1`)**
```
yunhee analysis screen Sys05_Tab_PersonRole --list     → 그리드 2
yunhee analysis ui Sys05_Tab_PersonRole --tobe frontend/src/pages/sys   → 2/2
yunhee analysis ui Sys04_Tab_RoleAdmin --tobe frontend/src/pages/sys    → 그리드 2/2
yunhee analysis screen Sys05_Tab_UserRole --list        → 그리드 1 (buildGrid 하나 — 지금과 같음)
```
- pytest: 그리드 0·1·2개 클래스, `buildGrid`와 `build*Grid` 이름 섞임, TOBE 주석 안의 `<SingleGrid` 무시.

## 2. `analysis grid`가 그리드 여럿을 한 표로 합침

**재현**
```
yunhee analysis grid Sys05_Tab_PersonRole
→ 표 하나: rowNumberer, checkBoxSelection, orgKorName … emailAddress, roleName, userRoleYn, seq, note (14행)
   유형 SingleGrid / 선택 모드 SINGLE 하나만
```
- 실제는 `buildUserGrid()`(Emp00_TransInfoModel, 8컬럼)와 `buildRoleGrid()`(Sys04_RoleModel, 4컬럼, addBoolean)로 두 그리드다. 그래서 그리드별 컬럼·선택 모드·모델을 `analysis method … -o code` 두 번으로 다시 봤다.

**원인**
- `tools/analysis/grid.py` L67-93이 **클래스 파일 전체**를 그리드 하나로 본다: 첫 `GridBuilder<…Model>`만 모델로 쓰고(L67), 첫 `setChecked`만 읽고(L77), 파일 안의 모든 `builder.add*` 줄(L93~)을 한 목록에 모은다.

**수정**
1. `GridBuilder` 변수를 선언하는 **메서드 단위**로 나눈다(메서드 시작~끝 줄 범위 안의 `GridBuilder<M> v = …`, `v.setChecked`, `v.setRowNumHidden`, `v.add*`). 메서드 밖(생성자·필드 초기화)에서 만들면 지금처럼 클래스 단위.
2. 그리드가 둘 이상이면 그리드마다 `### 그리드 \`buildRoleGrid()\` (유형: SingleGrid, 모델: Sys04_RoleModel)` 제목으로 표를 나눠 낸다. 필드 이름(`userRoleGrid = buildRoleGrid()`)을 알면 제목에 같이 적는다.
3. `--method <메서드>`(예: `--method buildRoleGrid`)로 하나만 낸다. `-o json`은 그리드 목록 배열로.
4. 그리드가 하나면 출력은 지금과 같다.

**기대 (검증 ID `027-2`)**
```
yunhee analysis grid Sys05_Tab_PersonRole
→ 그리드 2개: buildUserGrid()(행번호·체크 + 8컬럼, Emp00_TransInfoModel), buildRoleGrid()(행번호·체크 + 4컬럼, userRoleYn addBoolean)
yunhee analysis grid Sys05_Tab_PersonRole --method buildRoleGrid
→ roleName, userRoleYn, seq, note
yunhee analysis grid Sys04_Tab_RoleAdmin
→ gridCompany·gridRole 두 표
```

## 3. `compare`가 다른 화면·다른 그리드의 컬럼으로 대조함 (`--grid`도 소용없음)

**재현**
```
yunhee compare GET /api/v1/sys/persons/29035/roles -c kfstest --sql sys04_role.selectByUserId \
  --param userId=29035 --param companyId=28000 --grid Sys05_Tab_PersonRole
→ API rows=11, SQL rows=11 ✅  fields ⊇ grid cols ⚠️  (missing: adminYn, authOrgId, companyId, companyNm, defaultRole, userId)
yunhee compare GET /api/v1/emp/trans-infos -p transCode=100 -p separateAddTitle=false -c kfstest \
  --sql emp00_trans_info.selectByText --param companyId=28000 --param searchText=%% --param transCode=100 \
  --param transDate=2026-10-14 --param isSeparateAddTitle=false --grid Sys05_Tab_PersonRole
→ … ⚠️  (missing: actionCell)
```
- 이 화면의 권한 그리드는 roleName·userRoleYn·seq·note뿐이고 API에 다 있다. `actionCell`은 같은 SQL을 쓰는 다른 화면(`Emp00_Tab_RoleMenu`)의 그리드 컬럼이다. A04에서 compare 10번을 모두 "경고는 무시"로 판단해야 했다(06 항목 3의 '필드 ⊇ 그리드 컬럼' 판정을 못 씀).

**원인**
- `tools/comparator.py` L188: `re.search(r'-\s+그리드[^\n]*\(buildGrid[^\n]*\):\n…')` — 1번과 같이 `buildGrid` 이름만 찾는다. L199·L201 Grid Spec도 `const buildGrid\b`만 찾는다.
- 그래서 `--grid Sys05_Tab_PersonRole`(L95-102)로 화면을 맞게 골라도 그리드를 못 찾고, 빈 목록이면 L159·L168의 대체 경로(같은 SQL을 쓰는 다른 화면, 또는 SQL 컬럼)로 넘어간다. 어느 그리드로 대조했는지 출력에 없어서 잘못 고른 것을 알기 어렵다.

**수정**
1. L188·L199·L201의 `buildGrid`를 `build\w*Grid`로 넓히고, 한 절 안의 그리드를 **모두** 모은다.
2. `--grid <클래스>[#<메서드>]` — 메서드를 주면 그 그리드만. 클래스만 주고 그리드가 여럿이면 **API 필드와 가장 많이 겹치는 그리드**를 고른다.
3. 결과 줄에 대조한 그리드를 적는다: `fields ⊇ grid cols ✅ (Sys05_Tab_PersonRole#buildRoleGrid, 4컬럼)`.
4. `--grid`로 준 클래스에서 그리드를 못 찾으면 다른 화면으로 넘어가지 말고 `⚠ 그리드 못 찾음: Sys05_Tab_PersonRole`을 내고 컬럼 대조는 건너뛴다.

**기대 (검증 ID `027-3`)**
```
yunhee compare GET /api/v1/sys/persons/29035/roles -c kfstest --sql sys04_role.selectByUserId \
  --param userId=29035 --param companyId=28000 --grid Sys05_Tab_PersonRole
→ API rows=11, SQL rows=11 ✅  fields ⊇ grid cols ✅ (Sys05_Tab_PersonRole#buildRoleGrid, 4컬럼)
yunhee compare GET /api/v1/emp/trans-infos … --grid 'Sys05_Tab_PersonRole#buildUserGrid'
→ … ✅ (Sys05_Tab_PersonRole#buildUserGrid, 8컬럼)
```
- 조회만 하는 호출이다(데이터를 바꾸지 않음).

## 4. 원본 소스를 바꾼 뒤, 이미 옮긴 TOBE SQL이 원본과 달라진 것을 찾을 수 없음 (새 기능)

**상황**
- AssetERP_1은 2026-10-13에 AS-IS 원본을 `~/oms-data/src/Asset-ERP`(옛)에서 `~/work/IDMS-IC`(새, `YUNHEE_ASIS_SRC_DIR`)로 바꿨다. 그 전에 끝낸 화면(C01·C02·A01~A03·A05~A10·A13·A14·A15 일부·B10 …)의 TOBE 매퍼는 **옛 원본 SQL**을 옮긴 것이다.
- A04에서 우연히 찾았다: `emp00_trans_info.selectByText`의 검색어가 새 원본에서 `(emp01_kor_nm||org00_kor_nm||emp01_emp_no||f_cdnm('EmpTitleCode', …))`로 바뀌었는데(옛 원본에는 직책명 없음), C01 때 옮긴 `EmpTransInfoMapper.searchTransInfos`는 옛 것이었다. `analysis sql -o sql` 출력을 TOBE 매퍼와 눈으로 맞춰 보다가 알았고, 옛·새 비교는 `grep -rn`으로 했다(훅 경고 대상).
- 규모(2026-10-14, `diff -q -w --strip-trailing-cr`로 셈): 두 원본에 다 있는 매퍼 XML **467개 중 153개가 공백 말고도 다르다**. 그중 이미 변환한 도메인: `emp00_trans_info`·`emp01_person`·`emp03_trans`·`emp06_family`·`emp07_career`·`emp08_license`·`emp11_reward`·`emp19_education`·`org00_org_info`·`org01_code`·`org02_info`·`sys01_company`·`sys06_menu`·`sys08_code_kind`·`sys10_file`·`sys11_relate_file`·`Common.xml` 등. 파일 단위 `diff -q`는 465개가 "다름"으로 나와(대부분 줄바꿈·공백) 쓸 수 없다.
- 파일이 다르다고 옮긴 statement가 다른 것은 아니다. **statement 단위**로, 공백·주석을 무시하고 봐야 한다.

**제안: `yunhee sql-drift`**
```
yunhee sql-drift --old ~/oms-data/src/Asset-ERP [--new $YUNHEE_ASIS_SRC_DIR] \
                 [--tobe backend/src/main/resources/mapper] [--only-tobe] [-o md|json]
```
1. 두 원본의 매퍼 XML을 statement(`<select|insert|update|delete|sql id=…>`) 단위로 읽어 정규화한다(주석 `<!-- -->`·`/** */`·`--` 제거, 공백 하나로, 대소문자 그대로). `<include refid>`는 `analysis sql`처럼 펼친 뒤 비교한다(포함한 `Common.xml` 조각이 바뀐 것도 잡히도록).
2. `ns.id`마다 같음 / 바뀜 / 새로 생김 / 없어짐을 낸다.
3. `--tobe`: TOBE 매퍼 XML 주석에서 원본 SQL을 찾는다. 지금 TOBE 매퍼는 두 형식을 쓴다:
   - 파일 머리: `AS-IS server/emp/mapper/emp00_trans_info.xml selectByText(L339) · selectById(L66) …` (+ `common.emp00_trans_info(Common.xml L1372)`)
   - statement 위: `<!-- AS-IS selectByText L339 (…) -->`
   바뀐 원본 statement를 쓰는 **TOBE statement 목록**을 낸다: `EmpTransInfoMapper.searchTransInfos ← emp00_trans_info.selectByText (바뀜) · common.emp00_trans_info (같음)`. `--only-tobe`는 이 목록만.
4. 바뀐 것마다 정규화한 SQL의 단어 단위 diff를 몇 줄로 보인다(예: `+ ||f_cdnm('EmpTitleCode', emp00_title_cd, emp01_company_id, emp00_trans_date)`). 원문이 필요하면 `analysis sql <ns.id> -o sql`로 본다.
5. 주석으로 원본을 못 찾은 TOBE statement는 `⚠ 출처 없음`으로 따로 모은다(05 §3 "SQL 이식" 표에 적은 SQL ID로 찾을 수 있으면 그것도).

**기대 (검증 ID `027-4`)**
```
cd AssetERP_1
yunhee sql-drift --old ~/oms-data/src/Asset-ERP --tobe backend/src/main/resources/mapper --only-tobe
→ 목록에 EmpTransInfoMapper.searchTransInfos ← emp00_trans_info.selectByText 가 없음
   (A04에서 새 원본으로 고쳤으므로. 고치기 전 커밋 c22f774의 매퍼로 돌리면 "바뀜"으로 나와야 한다)
yunhee sql-drift --old ~/oms-data/src/Asset-ERP --new ~/oms-data/src/Asset-ERP
→ 바뀜 0
```
- 원본 두 벌만 읽는다(DB·서버 안 씀). pytest: 공백·주석만 다른 statement는 같음, include 조각이 바뀌면 그것을 포함하는 statement도 바뀜, 주석 형식 두 가지 인식.

## 5. `log errors --since-deploy`가 아직 기동 전인 새 배포를 알리지 않음 (작은 개선)

**재현**
- `yunhee run "./deploy.sh"`가 끝나고 몇 초 안에 `yunhee log errors --since-deploy`를 부르면, Tomcat이 새 WAR를 아직 올리지 않아서 헤더가 그 전 배포 시각(`배포 04:47:57 UTC`)이 되고 그 뒤 2시간치 WARN이 나온다. 이때 API도 404였다(05 §7: 배포 직후 404).
- yunhee 결함은 아니다(로그에 새 `Started … in … seconds`가 아직 없음). 하지만 출력만 보면 "배포 뒤 경고"로 읽힌다.

**수정**
- `find_deploy_time_docker`(`tools/log_reader.py` L645)가 찾은 기동 시각이 마지막 `yunhee run "./deploy.sh"`(`yunhee runs`의 deploy 명령 끝 시각)보다 이르면 `⚠ 마지막 배포(HH:MM) 뒤 앱 기동 기록 없음 — 아직 올라오는 중이면 잠시 뒤 다시`를 헤더 아래에 낸다. runs 기록이 없으면 지금처럼.

## 이번에 넣지 않은 것
- `analysis tobe`의 렌더 트리 뼈대만으로는 비슷한 화면을 참고하기에 부족해, A04에서 TOBE 파일 2개(115줄·80줄)를 Read로 읽었다. 다만 `outline` + Read(offset/limit)가 맞는 방법이라 기능 요청으로 만들지 않는다. 같은 일이 또 생기면 "함수 하나 본문 보기(`analysis tobe <파일> --fn <이름>`)"로 다시 제안한다.
