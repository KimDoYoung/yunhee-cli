# 수정사항 031 — `analysis ui` 공통 부품 버튼 집계·E-id 차이 목록, 동적 SQL 이름·미정의 SQL 표시, 버튼 type 미등록 표시, overload 선택, 클래스 필드 초기값, `outline` 타입 필드 (대상 0.3.6)

- 작성: 2026-10-16, yunhee **0.3.6** 기준. 반영하면 **0.3.7**.
- AssetERP_1에서 B12-4(UX보강 일괄 적용), A30(개선사항 및 오류 통보, 8클래스), A21(로그인 Mac 주소 관리 + 연결 사원찾기)을 하면서 쓴 명령에서 찾았다. `analysis screen/grid/method/sql`, `sql-check --tobe`, `compare`, `api --log`, `sql --rollback`, `run`은 잘 동작했고 원본 Java·로그를 통째로 읽지 않고 끝낼 수 있었다. 아래는 **고쳐 주면 손으로 판단하는 일이 줄어드는 것**이다.
- 1·2·3은 분석 결과가 사실과 달라 보이거나 빠지는 것, 4~7은 정보 추가, 8은 훅 보완, 9는 확인할 것이다. 우선순위: **1 > 2 > 3 > 5 > 6 > 4 > 7 > 8 > 9**.
- 새 top-level 명령은 만들지 않는다.

## 1. `analysis ui --tobe`가 공통 부품이 그리는 조회 버튼을 세지 못함

**재현** (AssetERP_1, `SearchBar`가 조회 버튼을 그리는 화면)
```
yunhee analysis ui Sys90_Tab_AfterServiceAdmin --tobe frontend/src/pages/sys
yunhee analysis ui Sys27_Tab_LoginManage --tobe frontend/src/pages
```
- 결과: `Sys90_Tab_AfterServiceAdmin | 버튼 1/0`, `Sys27_Tab_LoginManage | 2/1`, `Emp00_Lookup_SelectSingle | 6/3`. 조회 버튼은 `<SearchBar onSearch=…>`가 그리므로 화면 코드에 `<Button type="search">`가 없다.
- 결과확인 표마다 "조회 버튼은 SearchBar가 그림(yunhee 미집계)"을 손으로 적고 있다. B12 이후 조회 영역은 거의 모두 `SearchBar`다.

**수정**
1. `--tobe` 집계에서 `<SearchBar …>`(`components/search`에서 import한 것)를 **조회 버튼 1개**로 센다. `onReset`이 있으면 초기화는 세지 않는다(06 항목 10: UX보강이 더한 버튼은 세지 않음). `extra={<Button …/>}`의 버튼은 센다.
2. 같은 방식으로 설정 파일 하나(예: `.yunhee.toml`의 `[tobe.components]` — `SearchBar = ["search"]`)로 "이 컴포넌트는 버튼 N개를 그린다"를 줄 수 있게 한다(다른 부품이 생겨도 코드 수정 없이).

**기대 (검증 ID `031-1`)**
```
yunhee analysis ui Sys90_Tab_AfterServiceAdmin --tobe frontend/src/pages/sys
→ Sys90_Tab_AfterServiceAdmin 버튼 1/1
```
- pytest: ① `<SearchBar onSearch>` → search 1 ② `onReset`만 있어도 +0 ③ `extra`의 `<Button>` 계산 ④ 설정으로 컴포넌트→버튼 수 지정.

## 2. `analysis ui`가 AS-IS/TOBE **수만** 보여 주고 어떤 E-id가 빠졌는지는 안 보여 줌

**재현**
```
yunhee analysis ui Sys90_Tab_AfterServiceAdmin --tobe frontend/src/pages/sys
→ Sys90_Edit_BoardAdmin 이벤트 13/12, Sys90_Grid_ApprFile 3/2, Sys10_Lookup_ListFileViewer 9/8, Sys10_Lookup_FileViewer 2/1
```
- 어느 E가 TOBE에 없는지 알려면 AS-IS 이벤트 목록과 코드의 `// [E…]` 주석을 사람이 대조해야 했다(차이 4곳 모두 "E0 화면 열림"·"중복 Change"·"일부러 생략"이었다).

**수정**
1. 클래스마다 **AS-IS에만 있는 E-id 목록**을 한 줄로 낸다: `13/12 · 없음: E6, E11`.
2. TOBE 주석의 `// [E6 생략] 사유`·`[E… 생략]`을 인식해 "생략(사유 있음)"과 "미구현(주석 없음)"을 나눈다.
3. 생성자 초기화(`[E0] 화면 열림`)는 기본으로 "이벤트 아님"으로 보고 합계에서 뺄 수 있는 옵션(`--no-e0`)을 준다(대부분 `useEffect`라 주석이 없다).

**기대 (검증 ID `031-2`)**
```
Sys90_Edit_BoardAdmin | 이벤트 13/12 | 없음: E6(생략), E11(생략)
```

## 3. `analysis screen --section services`가 SQL 이름을 변수로 고르는 서비스 호출에서 SQL ID를 비움

**재현**
```
yunhee analysis screen Sys90_Tab_AfterServiceAdmin --section services
```
- `retrieve()`가 `service.retrieve("sys.Sys90_AfterService." + sql, …)`(`sql`은 `if`로 `selectByIncomplete`/`selectByAdmin`)라서 표에 **목록 SQL 행이 아예 없다**. 가장 중요한 조회 SQL이라 `analysis method retrieve -o code`로 직접 찾아야 했다.

**수정**: 서비스 이름이 `"…" + 변수`이면 그 변수에 대입되는 문자열 리터럴을 모아 후보를 모두 표에 낸다(`sys.Sys90_AfterService.{selectByAdmin | selectByIncomplete}`), 조건도 한 줄로(`if (checkBox01.getValue())`).

**기대 (검증 ID `031-3`)**: `sys90_after_service.selectByAdmin`·`selectByIncomplete` 두 행이 표에 나온다(`(동적 이름)` 표시).

## 4. 매퍼에 없는 SQL을 부르는 서비스가 눈에 안 띔

**재현**
```
yunhee analysis screen Sys27_Tab_LoginManage --section services
→ `sys.Sys27_LoginManage.updateCollapse` … `sys27_login_manage.updateCollapse`(없음)
yunhee analysis sql sys27_login_manage.updateCollapse
→ [ERROR] statement를 찾을 수 없습니다
```
- 표에 `(없음)`은 있지만 일반 SQL 행과 똑같이 보여서 지나치기 쉽다. 이 호출은 **원본에서도 실패**하는 코드(감추기 버튼)라 변환 방침(옮기지 않음)을 정하는 핵심 정보다.

**수정**
1. `(없음)` 행에 `⚠ 매퍼에 SQL 없음 — 원본에서도 실패`를 붙이고, 화면 요약(`analysis screen`의 첫 부분)에도 "미정의 SQL 호출 N개"를 보인다.
2. `analysis method <메서드> --server` 요약에도 같은 경고를 낸다.

**기대 (검증 ID `031-4`)**: `analysis screen Sys27_Tab_LoginManage` 상단에 `⚠ 미정의 SQL 호출 1개: updateCollapse (Sys27_Tab_LoginManage:239)`.

## 5. 버튼 type이 `unknown`으로 나오는 것이 많고, 등록되지 않은 문구인지 구분이 안 됨

**재현**
```
yunhee analysis screen Sys90_Tab_AfterServiceAdmin --class Sys90_Edit_BoardAdmin --section buttons
→ 파일등록 type="unknown", 파일관리 type="unknown"
yunhee analysis screen Sys90_Tab_AfterServiceAdmin --class Sys90_Lookup_Remarks --section buttons
→ 닫기 type="unknown"
yunhee analysis screen Emp00_Lookup_SelectSingle --section buttons
→ 전체·공통 type="unknown"
```
- `docs/button-types.md`에는 `close`(닫기)·`upload`(파일업로드)·`view`(첨부파일관리)가 있는데 `ColorButtonBar` 제목이 다른 클래스에서는 `close`로 풀리고 이 클래스들에서는 `unknown`이다(원본 코드에서 버튼 생성 방식이 달라서일 가능성). `전체`는 button-types에 없는 문구다.

**수정**
1. `unknown`일 때 이유를 붙인다: `unknown (button-types 미등록 문구)` / `unknown (제목 인식 실패 — 생성 코드 L…)`.
2. 가장 가까운 등록 type을 후보로 낸다(`닫기→close`, `파일등록→upload`, `파일관리→view`; 문구 부분 일치·유사도).
3. 같은 문구가 클래스마다 다르게 풀리는 경우(닫기)를 일관되게 한다.

**기대 (검증 ID `031-5`)**: `type="unknown" /* 후보: upload (파일업로드) */`, `전체 → unknown (미등록 문구)`.

## 6. 화면이 부르는 **overload**를 알 수 없음 (`open` 변형 9개)

**재현**
```
yunhee analysis method Emp00_Lookup_SelectSingle.open
→ 후보 9개 (open(Date,String,Boolean,cb) … open(Long companyId, Date, cb) … open(Date, cb))
```
- 변환 대상 화면(`Sys27_Tab_LoginManage`)이 `open(Long.parseLong(…), new Date(), callback)`으로 부르는데, 어느 후보인지 알려면 호출부와 시그니처를 사람이 맞춰야 했다. 큰 공통 조회창은 변형이 9개이고 각각이 다른 단추·초기값을 만든다(`open#7`이 `nullButton`을 더하고 `open(Date, cb)`를 부르는 식의 체인).

**수정**
1. `analysis method <클래스>.<메서드> --called-from <호출 클래스>`: 호출 클래스 코드에서 그 메서드를 부르는 곳의 인자 타입으로 overload를 고른다.
2. 선택된 overload가 다른 overload를 부르는 **체인**(`#7 → #9`)을 한 번에 요약한다(추가되는 버튼·필드 설정 포함).

**기대 (검증 ID `031-6`)**
```
yunhee analysis method Emp00_Lookup_SelectSingle.open --called-from Sys27_Tab_LoginManage
→ open(Long, Date, cb) L124 → open(Date, cb) L165 : 단추 확인·전체·취소, 그리드 SINGLE …
```

## 7. 클래스 **필드 초기값**을 볼 수 없음

**상황**: A21 사원찾기 재직구분에 "겸직" 항목이 있는지는 `isSeparateAddTitle` 필드의 기본값에 달렸는데, `analysis method`·`screen`·`grid`로는 필드 선언(`private Boolean isSeparateAddTitle = …`)을 볼 수 없어 다른 화면(`Emp00_Lookup_SelectMulti`)과 같게 가정했다(작업기록 제안으로 남김).

**수정**: `yunhee analysis screen <화면> --class <클래스> --section fields` — 필드 이름·타입·초기값·사용하는 메서드 줄(읽는 곳/쓰는 곳). 위젯 필드(`TextField` 등)는 생략하고 상태 필드만.

**기대 (검증 ID `031-7`)**: `isSeparateAddTitle Boolean = true (L40) ← open L139 설정, retrieve L331 읽음`.

## 8. `outline`·`analysis tobe`가 타입(interface) 필드와 API 함수 인자를 보여 주지 않음

**상황**: TOBE 참고 코드를 볼 때 `grep -n … -A14`·`cat`·`sed`가 훅에 막힌다. 그런데 `yunhee outline frontend/src/types/emp.ts`는 `L 2: export interface TransInfo`만 보여 주고 **필드**는 없어서 결국 `Read(offset/limit)`로 열었다(A21, `TransInfo.personId`·`korNm` 확인). `outline api/sys.ts`도 함수 인자는 있지만 반환 타입이 없다.

**수정**
1. `yunhee outline <파일> --members` (또는 `--symbol TransInfo`)로 interface·type의 필드 이름과 타입을 한 줄씩 낸다(주석 첫 줄 포함).
2. API 함수는 `이름(인자): 반환` 형태로.

**기대 (검증 ID `031-8`)**: `yunhee outline types/emp.ts --symbol TransInfo` → `transId: number, personId: number, transDate?: string|null, …`.

## 9. 확인이 필요한 것 (원인 미확인)

- `yunhee api --log`의 SQL 줄에서 `PUT /api/v1/sys/after-services/admin` 요청의 3번째 줄이 `k.c.k.a.b.s.m.S.selectById (specificMenuId=202509099027311)`로 찍혔다(실제로는 `SysAfterServiceMapper.selectById(afterServiceId=…)`가 돌았고 응답 데이터도 맞다). **namespace 약어(`…m.S`)로 매퍼가 구분되지 않고 파라미터 이름이 다른 매퍼의 것으로 보인다.** 재현: A30 저장 API 호출 직후 `--log`. 로그 파서가 statement ID를 줄여 쓰다 같은 이름(`selectById`)의 다른 매퍼 줄과 섞는지 확인해 달라.
- `yunhee api GET /v1/sys/after-services/admin`(앞에 `/api` 없음)이 `404 No static resource v1/sys/after-services/admin`을 줬고 `/api/v1/…`는 200이었다(첫 호출이 배포 직후라 겹쳤을 수 있음). 404 본문이 `No static resource`이고 경로가 `/api`로 시작하지 않으면 "`/api` 접두가 필요한가요?" 힌트를 한 줄 붙여 달라.
