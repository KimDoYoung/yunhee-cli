# 수정사항 032 — `index-src` 소스 기준 커밋 기록, `yunhee drift`(원본 변경 감지), 변환 시점 기준(baseline), 다중 PC 커밋 불일치 경고 (대상 0.3.7)

- 작성: 2026-10-16, yunhee **0.3.7** 기준. 반영하면 **0.3.8**.
- 계기: AssetERP 원본(`~/work/IDMS-IC`, git 저장소, 브랜치 `ioc`)은 **지금도 매일 수정·추가된다**(2026-10-09~16: 18커밋, 바뀐 Java 81개). 그런데 `index-src` 색인에는 "어느 시점의 소스로 만들었는지"가 없고, 이미 TOBE로 만든 화면(A01~C03 등)이 그 뒤 원본에서 바뀌었는지 알 방법이 없다. 지금은 사람이 `git log`를 손으로 치거나, 아예 모른 채 지나간다.
- 목표: ① 색인과 변환 결과에 **기준 시점**을 남긴다. ② **바뀐 화면만** 골라 보여 준다. 재변환은 사람이 바뀐 화면만 diff를 보고 한다(전체 재변환 안 함).
- 우선순위: **1 > 2 > 3 > 5 > 4 > 6**.
- 새 top-level 명령은 `drift` **1개만** 만든다(사용자 요청). 나머지는 기존 명령의 출력·옵션 추가다.
- 하지 않는 것: 소스 자동 `git pull`, TOBE 코드 자동 수정, 소스 저장소에 쓰기(전부 읽기 전용).

## 0. 전제 (현재 상태)

- `yunhee index-src [src_root] [-t …] [--menus …] [--db-index …]`는 실행마다 출력 폴더의 `*.md`를 지우고 다시 만든다(`docs/as-is/src/`: `menus.md`, `{도메인}/screens/{클래스}.md`, `README.md` …). 화면 파일에는 함께 쓰는 클래스·서비스 → 서버 메서드(파일:줄) → SQL ID → 테이블, `## UI` 절이 있다. **소스 버전 정보는 없다.**
- 원본은 git 저장소다(`git -C ~/work/IDMS-IC rev-parse HEAD` 등이 동작). 단 사무실 PC(T3600)와 집 PC(OMEN)가 각자 clone하므로 **PC마다 HEAD가 다를 수 있다**(5번).
- 옛 색인에는 기준 정보가 없다. 하위 호환이 필요하다(1의 마지막).

## 1. `index-src`가 소스 기준을 색인에 기록 (가장 중요)

**재현**
```
cd ~/work/IDMS-IC && git log -1 --format='%h %cd'      # 546a87d42 Fri Oct 16 17:13:21 2026
yunhee index-src ~/work/IDMS-IC --menus docs/as-is/menus.tsv
head docs/as-is/src/README.md                          # 소스 커밋·일시 어디에도 없음
```
- 색인을 다시 만들면 어제 색인과 오늘 색인이 무엇이 다른지, 이 색인이 소스의 어느 시점인지 알 수 없다.

**수정**
1. **저장소 수준 기록**. `index-src`가 소스 루트에서 아래를 읽어 `{target}/README.md` 머리와 `{target}/_source.json`(기계용)에 쓴다.
   - `commit`(40자)·`commit_short`, `branch`, `commit_time`(KST), `dirty`(추적 파일에 미커밋 변경이 있는지), `remote`(origin URL), `indexed_at`(KST), `yunhee_version`.
   - git이 아니면 `vcs: none`, 파일 mtime 최댓값과 아래 파일 해시만 기록하고 "git 아님"을 한 줄 표시한다(실패시키지 않는다).
   - `dirty: true`이면 README에 경고 한 줄: "미커밋 변경이 색인에 포함됨 — 기준 커밋만으로 재현 불가".
2. **화면 파일 수준 기록**. 화면 파일(`screens/{클래스}.md`) 맨 위 frontmatter에 추가한다.
   ```yaml
   ---
   source_commit: 546a87d42a…          # 저장소 HEAD(전체 해시)
   indexed_at: 2026-10-16T21:50:00+09:00
   source_files:                       # 이 화면이 의존하는 파일 → git blob 해시
     application/src/main/java/myApp/sys/client/Sys27_Tab_LoginManage.java: 3f9a1c0…
     application/src/main/java/myApp/sys/server/Sys27_LoginManage.java: 81be2d7…
     application/src/main/resources/…/Sys27_LoginManage.xml: c40d9e1…
   ---
   ```
   - `source_files`에는 **색인이 이미 아는 연관 파일 전부**를 넣는다: 화면 클래스, 함께 쓰는 클래스(탭·팝업·그리드·모델), 서비스 인터페이스, 서버 구현, 해당 SQL ID가 있는 매퍼 XML. (AS-IS 분석에서 이미 이 목록을 만들고 있으므로 새 분석은 필요 없다.)
   - 다른 도메인의 공용 컴포넌트(예: 전자결재 `Apr01_Edit_ApprDoc`)는 링크만 있는 기존 규칙대로 **링크 대상의 해시는 넣지 않고** `shared_links:` 목록에 클래스명만 둔다(그 컴포넌트 변경이 이 화면에 미치는 영향은 6번의 역인덱스로 처리).
3. **해시 방식**: git이면 **blob 해시**(`git ls-files -s`·`git ls-tree -r HEAD`로 한 번에 읽음, 파일을 읽어 해시 계산하지 않아 빠르고 `git diff`와 바로 연결된다). git이 아니거나 `dirty` 파일이면 파일 내용의 **sha256**을 계산하고 값 앞에 `sha256:`을 붙여 구분한다.
4. **역인덱스**: `{target}/_files.json`에 `파일경로 → [화면 클래스 …]`를 남긴다(2의 `drift`가 공유 서비스·매퍼 변경을 영향받는 화면 전체에 전파하는 데 쓴다).
5. **하위 호환**: frontmatter가 없는 옛 색인은 읽을 수 있어야 한다. `drift`는 그런 화면을 "기준 없음"으로 따로 센다(색인을 다시 만들라고 안내).
6. 색인 출력 크기: 화면당 수십 줄의 frontmatter가 붙는다. `yunhee analysis screen …` 출력에는 frontmatter를 **섞지 않는다**(토큰 절약). 기준 정보는 `analysis screen <화면> --section source`로만 본다(아래 기대).

**기대 (검증 ID `032-1`)**
```
yunhee index-src ~/work/IDMS-IC --menus docs/as-is/menus.tsv
→ 소스 546a87d (ioc, 2026-10-16 17:13) clean · 화면 N개 · 의존 파일 M개 기록

head -8 docs/as-is/src/README.md
→ - 소스: IDMS-IC @ ioc 546a87d42a… (2026-10-16 17:13 +0900) clean
→ - 색인: 2026-10-16 21:50, yunhee 0.3.8

yunhee analysis screen Sys27_Tab_LoginManage --section source
→ source_commit 546a87d · 의존 파일 7개 (client 3 · server 1 · service 1 · mapper 2)
```
- pytest: ① 임시 git repo에서 index → `_source.json`의 commit이 HEAD ② 화면 frontmatter의 blob 해시가 `git ls-tree`와 일치 ③ 비git 폴더면 `vcs: none`·`sha256:` 값 ④ 추적 파일을 고쳐 두면 `dirty: true`와 경고 ⑤ 옛 색인(frontmatter 없음)을 `drift`가 읽어도 죽지 않는다 ⑥ `analysis screen`의 기본 출력에 frontmatter가 안 섞인다.

## 2. 새 명령 `yunhee drift` — 기준 이후 바뀐 화면 찾기

**필요**: "내가 만든 화면들 중 원본이 그 뒤에 바뀐 것이 어느 것이고 얼마나 바뀌었나"를 **한 번에, 짧게** 본다.

**명령**
```
yunhee drift [화면 …] [--all] [--src <root>] [--base <index|baseline|커밋>] [--done-only]
             [--min-lines N] [-o table|diff|json] [--new]
```
- 화면 인자를 생략하고 `--all`을 주면 색인 전체를 비교한다. `--src` 기본값은 `YUNHEE_ASIS_SRC_DIR`.
- `--base`:
  - `index`(기본): 색인 frontmatter의 `source_files` 해시와 **현재 소스**를 비교한다. 즉 "마지막으로 색인을 만든 뒤 바뀐 것".
  - `baseline`: 3번의 "변환 시점 기준"과 비교한다. 즉 "내가 변환한 뒤 바뀐 것". 화면에 baseline 기록이 없으면 `기준 없음`으로 표시.
  - `<커밋>`: 임의 커밋과 비교(`git diff --numstat <커밋>..HEAD -- <files>`).
- `--done-only`: 01 변환목록처럼 "완료한 화면"만 본다. 완료 판정은 `.yunhee.toml`의 `[drift] done_from = "docs/01-변환목록.md"` 같은 설정 또는 baseline 기록이 있는 화면으로 한다(기본은 baseline 기록 있는 화면).
- `--new`: 메뉴 TSV에는 있는데 색인에 없는, 또는 소스에 새로 생긴 `*.java` 화면 클래스를 따로 나열한다.
- 읽기 전용이다. 소스·색인·TOBE 아무것도 쓰지 않는다.

**상태 판정** (화면별, 의존 파일 단위로 합산)
| 상태 | 뜻 |
|:---|:---|
| 변경 | 파일 해시가 다르다 |
| 삭제 | 파일이 소스에 없다(`git log --diff-filter=D`로 삭제 커밋을 한 줄 표시) |
| 이동 | 같은 blob이 다른 경로에 있다(`git diff -M`) — 변경으로 세지 않고 새 경로를 표시 |
| 신규 | 색인에 없는 파일/화면(`--new`) |
| 동일 | 모두 같다 — 기본 출력에서 생략하고 합계만 센다 |

**기본 출력** (토큰 절약: 한 화면 한 줄, 변경 큰 순)
```
$ yunhee drift --all --base baseline --done-only
기준 대비 변경 7개 / 완료 화면 43개 (동일 36 · 기준 없음 0) — 소스 HEAD 546a87d, 기준 커밋 범위 9c1f2aa..546a87d

화면                         파일  +/-줄      마지막 커밋
Sys27_Tab_LoginManage         3   +41/-12    10-14 김○○ 로그인 관리 MAC 중복 검사
Emp02_Others                  1   +3/-1      10-12 이○○ 기타정보 주민번호 마스킹
Sys06_Menu                    2   +120/-8    10-09 박○○ 메뉴 정렬 컬럼 추가
…
공유 변경(영향 화면 수): Sys00_Common.java (12) · Emp00_TransInfo.xml (5)
→ yunhee drift Sys27_Tab_LoginManage -o diff   # 파일별 diff
```
- 작성자는 git `%an` 그대로 쓴다(마스킹은 yunhee 쪽 일반 규칙에 따른다).
- `-o diff`: 바뀐 파일마다 `git diff --stat` 한 줄 + 통합 diff를 **`--context 3`** 으로 출력(큰 파일은 `--max-lines 200`에서 자르고 "…(N줄 생략, 원문 -o full)").
- `-o json`: 스크립트·주간 점검용(`screen`, `status`, `files[]`, `added`, `removed`, `last_commit{hash,date,subject}`).
- 공유 파일 전파(1-4 역인덱스): 서비스·매퍼·공통 클래스가 바뀌면 그 파일에 의존하는 **모든 화면에 "공유"로 표시**하되, 화면별 줄 수에는 중복 합산하지 않고 마지막 줄에 "공유 변경(영향 화면 수)"로 모은다.

**종료 코드**: 변경 없음 0, 변경 있음 0(정보 명령이므로 실패가 아님). 옵션 오류·소스 없음 2. 스크립트에서 쓰려면 `--fail-on-drift`가 변경 있을 때 1을 낸다.

**기대 (검증 ID `032-2`)**
- 임시 repo에서: 화면 A는 클래스만, 화면 B는 공유 매퍼, 화면 C는 변경 없음으로 만들고 index → 매퍼 한 줄 수정 + A의 클래스에 3줄 추가 → `drift --all` 결과가 A `+3/-0`(1파일), B(공유 1), C 동일.
- pytest: ① 변경/삭제/이동/신규 네 상태 ② 이동은 변경으로 세지 않는다 ③ 공유 파일이 영향 화면 모두에 전파되고 줄 수는 한 번만 합산 ④ `--min-lines`로 걸러짐 ⑤ `-o json` 스키마 ⑥ `--fail-on-drift` 종료 코드 ⑦ git이 아닌 소스는 sha256 비교(커밋·줄 수 열은 `-`) ⑧ 기준 없는 옛 색인 화면은 "기준 없음"으로 센다.

## 3. 변환 시점 기준(baseline) 기록 — "내가 만든 시점"과 비교

**필요**: 색인은 하루에도 여러 번 다시 만들 수 있어, `--base index`는 "마지막 색인 이후"만 알려 준다. 정말 필요한 것은 **"TOBE 화면을 완성한 시점의 원본"** 대비 변경이다.

**수정**
1. `yunhee drift --record <화면 … | --id A21>`: 지정한 화면의 **현재 색인 기준**(`source_commit`, `source_files` 해시)을 baseline으로 저장한다. 저장 위치는 TOBE 저장소의 `.yunhee/baseline.json`(화면 → {commit, files, recorded_at, note}). `.yunhee/`는 git-ignored라 공유되지 않으므로 **추적 가능한 위치**를 옵션으로 둔다: `[drift] baseline = "docs/as-is/baseline.json"`(`.yunhee.toml`).
2. 같은 내용을 사람이 읽는 형태로도 남긴다. `--note-file docs/work/A21-작업기록.md`를 주면 그 파일 머리의 `AS-IS 기준:` 줄을 만들거나 갱신한다.
   ```
   AS-IS 기준: IDMS-IC 546a87d42a… (ioc, 2026-10-16) · 의존 파일 7개 해시는 docs/as-is/baseline.json
   ```
3. `--record`는 항상 **색인이 최신인지**(소스 HEAD와 `_source.json` commit 일치, `dirty: false`) 먼저 확인하고, 아니면 "색인이 오래됨 — `index-src` 먼저" 오류(Exit 2)로 막는다(오래된 색인을 기준으로 삼으면 의미가 없다).
4. 재변환 후 갱신: 같은 명령을 다시 실행하면 baseline을 덮어쓰고 이전 값은 `history`에 한 줄 보관한다(언제 누가 어떤 커밋에서 갱신했는지).
5. 조회: `yunhee drift <화면> --show-baseline`.

**기대 (검증 ID `032-3`)**
```
yunhee drift --record Sys27_Tab_LoginManage --note-file docs/work/A21-작업기록.md
→ baseline 기록: Sys27_Tab_LoginManage @ 546a87d (의존 7개) · 작업기록 머리에 'AS-IS 기준:' 줄 추가

yunhee index-src …   # 소스가 바뀐 뒤 다시 색인
yunhee drift Sys27_Tab_LoginManage --base baseline
→ 변경 2파일 +10/-2 (baseline 546a87d → HEAD 7b21c90)
```
- pytest: ① record 후 baseline.json 내용 ② 색인이 오래되면 거부 ③ 재기록 시 history ④ `--note-file` 줄 중복 없이 갱신 ⑤ `--base baseline`이 색인 재생성 후에도 baseline 기준으로 비교(색인 기준과 다른 결과).

## 4. `index-src` 재실행 시 이전 기준 보존 — "지난 색인 대비" 비교

**현상**: `index-src`는 출력 폴더의 `*.md`를 지우고 다시 만들므로 이전 기준 정보가 사라진다.

**수정**
1. 다시 만들기 직전에 이전 `_source.json`과 화면별 `source_files` 해시를 `{target}/_prev/`(git-ignored 하위)에 한 세대만 보관한다.
2. `yunhee drift --base prev-index` 또는 `index-src` 끝에 요약 한 줄: `지난 색인(…a1b2c3d) 대비 변경 화면 N개, 신규 M개, 삭제 K개`.
3. `_prev`가 없으면(최초) 이 줄은 출력하지 않는다.

**기대 (검증 ID `032-4`)**: 소스를 한 파일 고치고 `index-src`를 두 번 실행하면 두 번째 끝 줄에 `지난 색인 대비 변경 화면 1개`가 나오고, 세 번째(소스 무변경)는 `변경 0개`.
- pytest: ① 세대 보관 ② 최초 실행엔 요약 없음 ③ 신규·삭제 화면 개수.

## 5. 여러 PC에서 소스 커밋이 다를 때 경고

**배경**: 사무실(T3600)과 집(OMEN)이 각자 `IDMS-IC`를 clone한다. 한쪽에서 `git pull`을 안 하면 같은 색인이 서로 다른 소스를 가리킨다. 그 상태에서 만든 baseline은 PC마다 다르다.

**수정**
1. `index-src`·`drift`·`config`가 시작할 때 **소스 HEAD와 색인/baseline의 commit이 다르면 경고**를 한 줄 낸다.
   ```
   ⚠ 소스 HEAD(7b21c90)가 색인 기준(546a87d)과 다릅니다 — 색인을 다시 만들거나 git pull 상태를 확인하세요
   ```
2. 소스 저장소에 **원격 뒤처짐**이 있는지는 `git fetch`를 실행하지 않고(읽기 전용 원칙) 로컬의 `origin/<branch>` 기준 `ahead/behind`만 보여 준다: `yunhee config`에 `소스 브랜치: ioc (origin/ioc 대비 behind 3)`.
3. baseline.json이 git으로 공유되면 PC 간 비교가 되므로, `drift --base baseline`은 baseline commit이 현재 소스 이력에 **없는** 경우(다른 브랜치·pull 안 함)를 "기준 커밋을 소스에서 찾을 수 없음 — git fetch 필요"로 따로 표시한다(오류 아님, 해시 비교로 대체).

**기대 (검증 ID `032-5`)**: 소스에서 커밋을 하나 더하고 색인을 안 만든 채 `yunhee drift`를 실행하면 위 경고가 첫 줄에 나온다. `git reset --hard`로 baseline 커밋이 이력에서 사라지게 하면 3의 메시지가 나온다.
- pytest: ① 경고 문구 ② baseline 커밋이 이력에 없는 경우 해시 비교로 동작 ③ `behind` 표시(원격 추적 브랜치가 있는 픽스처).

## 6. 안내 문구·문서

1. `yunhee agent-guide`와 `changelog`에 `drift`·`--record`·`analysis screen --section source`를 넣는다. 새 사용 규칙 한 줄: "화면을 완성하면 `drift --record`, 주 1회·`git pull` 직후 `drift --all --base baseline --done-only`".
2. `yunhee analysis --list`에 `drift`가 없어도 된다(top-level 명령이므로). 대신 `yunhee --help`에 `drift`를 넣는다.
3. AssetERP 쪽 문서(`docs/05-작업방법.md` §7 명령표, `docs/work/{id}-작업기록.md` 템플릿의 `AS-IS 기준:` 줄, 세션 시작 시 `drift` 확인)는 yunhee 반영 **뒤** 우리 쪽에서 고친다 — 이 문서의 범위가 아니다.

**기대 (검증 ID `032-6`)**: `yunhee --version` → `0.3.8`, `yunhee changelog --since 0.3.7`에 위 4개 항목, `yunhee agent-guide`에 `drift` 사용 시점.

## 7. 구현 순서(제안)와 위험

1. `_source.json`·README 기록(1-1) → 화면 frontmatter(1-2, 1-3) → 역인덱스(1-4). 색인 생성 속도가 눈에 띄게 느려지면 안 된다: blob 해시를 `git ls-tree -r HEAD` **한 번**으로 읽는다(파일마다 `git` 호출 금지).
2. `drift`(2) 기본 `--base index` → `-o diff`·`json` → 공유 전파.
3. baseline(3), `_prev`(4), 경고(5), 안내(6).
- **위험**
  - 의존 파일 목록이 부정확하면 변경을 놓친다. 색인이 이미 만드는 "함께 쓰는 클래스·서비스·서버·매퍼" 목록과 정확히 같은 출처를 쓰고, 목록이 비면 `기준 불완전`으로 표시한다.
  - 줄 번호가 바뀌는 단순 포맷 변경이 노이즈가 된다. `--ignore-space`(공백 무시, `git diff -w`)를 옵션으로 둔다. 기본은 끔.
  - `dirty` 상태 색인은 재현 불가. 1-1의 경고로 알리고, `--record`는 dirty이면 거부한다.
- 이 문서가 다룬 것을 반영하면, 우리 쪽 사후 시험은 `AssetERP/tools/yunhee-0.3.8-check.sh`와 `docs/work/yunhee-0.3.8-수정사항체크.md`(0.2.5 체크 문서 형식)로 만든다. 결과는 `수정사항033.md`에 적는다.
