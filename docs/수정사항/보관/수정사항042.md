## 1. `port-sql`이 바깥 SELECT 열과 `<choose>` 분기를 잃는다 (1순위)

**어떤 경우**
- 서브쿼리 `FROM ( SELECT … ) t`를 바깥 SELECT가 `t.*`와 계산 열로 감싼 SQL이고, 안쪽에 `<choose><when test="exctId != null">` 같은 동적 분기가 있는 statement.
- 예: `tdm51_chck_org.selectDashboardExct`, `selectDashboardOrg`.

**재현**
```bash
yunhee port-sql tdm51_chck_org.selectDashboardExct \
  --cols exctName,roleName,progRate,monthCheckCnt,monthManlUndoneCnt,monthCheck1Cnt,monthCheck2Cnt,monthCheck9Cnt \
  --package kr.co.kfs.asseterp.biz.tdm.dto
```

**기대한 결과**
- 바깥 SELECT의 열(`t.*` 확장 + `… AS tdm51_prog_rate`)이 모두 별칭 변환되어 나오고, 안쪽 `<choose><when test="exctId != null">` 분기도 그대로 나온다. DTO record에 `--cols`의 8개 필드가 모두 채워진다.

**실제 결과**
- 매퍼 조각이 `SELECT <include refid="chckOrgColumns"/> FROM ( … ) t`가 되었고 `chckOrgColumns`에는 `ROW_NUMBER() … AS chck_org_id` **한 열만** 들어 있다(`t.*`와 `tdm51_prog_rate`가 사라짐).
- 모든 `--cols`가 `⚠ SQL 열 없음: exctName; …`로 찍히고, DTO record는 8개 필드가 전부 `String`에 `// ⚠ SQL 열 없음` 주석으로 나온다(`progRate`, `monthCheckCnt`도 String).
- 안쪽 `<choose>`는 살아 있었다(`exctId` 분기 포함) — 열 쪽만 문제.

**원인 추정**
- 바깥 SELECT 목록을 "SELECT 뒤 첫 열 = 대표 열"처럼 `<sql id="…Columns">`로 뽑을 때 `t.*`와 뒤따르는 계산 열을 버린다. 서브쿼리 안쪽 별칭(`tdm51_exct_nm AS …`)을 바깥 열로 연결하지 못한다.

**수정 제안**
1. 바깥 SELECT 목록 전체를 열 단위로 파싱한다. `t.*`이면 안쪽 SELECT의 별칭 목록으로 확장한다.
2. 안쪽/바깥 별칭 접두사(`tdm51_`)를 일괄 제거하는 규칙을 바깥에도 적용한다.
3. 열 매핑을 못 하면 조각을 만들지 말고 `⚠ 서브쿼리 t.* 확장 실패 — 수동 작성 필요`를 한 줄로 낸다(지금은 틀린 조각이 "정상처럼" 나온다).

**합격 기준**
- 위 재현에서 DTO record에 `exctName, roleName: String` / `progRate: Double` / `monthCheck*Cnt: Long` 등 `--cols` 8개가 타입과 함께 채워진다.

## 2. `compare`가 `--param` 값을 AS-IS SQL에 반영하지 못해 거짓 실패를 낸다

**어떤 경우**
- `compare`의 `--param`으로 동적 분기(`<when test="exctId != null">`)를 켜는 조회. API 쪽은 `-p exctId=…`로 받아 분기가 켜졌다.

**재현**
```bash
K=202601209259551
yunhee compare GET /api/v1/tdm/dashboard/undone -c prod_s1 \
  -p checkYm=2026.08 -p statusType=1 -p exctId=202604019585337 \
  --sql tdm52_chck_manl.selectDashboardUndone \
  --param companyId=$K --param checkYm=2026.08 --param statusType=1 --param exctId=202604019585337 \
  --grid Tdm50_Tab_DashboardExct#buildGrid04
```

**기대한 결과**
- API 788행, SQL 788행 ✅ (같은 값으로 `yunhee analysis sql … --count`를 돌리면 788).

**실제 결과**
```
API rows=788, SQL rows=0 ❌  fields ⊇ grid cols ✅
```
- 같은 파라미터로 `yunhee analysis sql tdm52_chck_manl.selectDashboardUndone --param … --count` → **788**, `yunhee mapper-run …#selectDashboardUndone -p … --compare tdm52_chck_manl.selectDashboardUndone` → **TOBE 788, AS-IS 788 ✅**. 즉 TOBE는 맞고 `compare`의 SQL 쪽 숫자만 틀렸다.
- 다른 경우: 같은 SQL에 `retrieveType`을 `--param`으로 주지 않으면 `-- 필요: retrieveType`만 찍고 끝난다(동적 분기에서 안 쓰는 값인데도 필수 취급).
- `--param searchText=%%`처럼 `%` 값을 줄 때도 확신이 없다(결과 5=5로 통과했으나 렌더 SQL을 볼 수 없다).

**수정 제안**
1. `compare`가 SQL 쪽을 `analysis sql --count`와 같은 렌더러(분기 포함)로 돌리게 한다. 지금은 분기 평가 없이 `exctId`가 null인 채 `AND`가 빠지는 쪽으로 동작하는 것으로 보인다(0행이 나온 이유는 불명 — 확인 필요).
2. 결과 줄에 실제 사용한 `--param` 값(분기 켜짐 여부)을 한 줄 출력한다: `SQL params: companyId=…, exctId=… (branch: exctId ON)`.
3. 분기 안에서만 쓰는 값은 필수로 보지 않는다(`-- 필요:` 대신 `-- 선택:`).
4. API 행수와 SQL 행수가 다를 때 `mapper-run --compare` 결과를 힌트로 안내한다.

**합격 기준**
- 위 재현에서 `API rows=788, SQL rows=788 ✅`.

## 3. `analysis ui`의 AS-IS 수가 [보기] 팝업 클래스를 합산해 화면 자체 수와 어긋난다

**어떤 경우**

**실제 결과**
```
Tdm50_Tab_Dashboard       | 24/0 | 15/3 · 없음: E3(미구현) … E14(미구현) | 10⚠/3
```

2. "없음: E3(미구현)" 판정은 같은 클래스에 속한 이벤트에만 적용하고, 연결 클래스 이벤트는 `(연결: Tdm54_Lookup_ChckInsuffCmnt)`처럼 출처를 표기한다.
3. TOBE 쪽: `--tobe` 폴더 안에서 같은 폴더의 `*_Common.tsx`·`import`된 조각의 `<Button>`·`[E…]` 주석을 따라가 세거나, 못 따라가면 `TOBE 버튼 0 (공통 조각 파일 사용?)` 경고를 낸다.

**합격 기준**
- 위 재현에서 `Tdm50_Tab_Dashboard` 줄이 `1/1 · 3/3 · 3/3`(+ 연결 클래스 요약 한 줄)로 나온다.

## 4. 색인 화면 파일이 없는 연결 컴포넌트를 `analysis screen`이 못 연다 (재현 반복)

**어떤 경우**
- 다른 클래스가 부르는 조회창으로, 색인에 `screens/{클래스}.md`가 없는 것(`Tdm01_Lookup_SelectSingle`). 수정사항 026에서 "연결 컴포넌트(components/ 직접)"를 고쳤다고 했으나 이 클래스는 해당되지 않았다.

**재현**
```bash
yunhee analysis screen Tdm01_Lookup_SelectSingle --list
→ [ERROR] 색인 화면 파일을 찾을 수 없습니다: Tdm01_Lookup_SelectSingle.md

yunhee analysis method Tdm01_Lookup_SelectSingle.retrieve   # 이건 된다
```

**합격 기준**
- 위 재현에서 `--list`가 버튼 3(조회·확인·닫기)·이벤트 5·그리드 1을 낸다.

## 5. `analysis method -o code`로 생성자 레이아웃 코드를 볼 수 없다

**어떤 경우**
- 화면의 구조(위젯 배치, 모니터 스타일 문자열, 마진·높이)가 **생성자** 안에 있는 GXT 화면.

**재현**
```bash
yunhee analysis method Tdm50_Tab_Dashboard.Tdm50_Tab_Dashboard -o code   # 생성자
yunhee analysis screen Tdm50_Tab_TotalDashboard --class Tdm50_Tab_Dashboard --section layout
```

**기대한 결과**
- `--section layout`이 `HorizontalLayoutData(0.2, 140, Margins(10))`, 모니터 3칸의 flex 정렬(`justify-content:flex-end`, 글자 50px), 툴바 `ButtonBar`의 요소 순서(점검년월·QuickMoveField·라디오·[새로고침]·마감 문구)까지 낸다.

**실제 결과**
- `--section layout`은 컨테이너 크기·비율(`vlc: {buttonBar} 1×50 | {monitorHlc} 1×140 …`)까지만 나오고, 툴바 요소 순서·스타일 문자열·라디오 폭 75 같은 값은 없다. 생성자는 `method`에서 `-o code`로도 나오지 않아(요약 `- this.callback = …` 수준) `Read`로 소스를 직접 읽었다(약 130줄 × 3 클래스).

**수정 제안**
1. `--section layout`에 툴바 순서(`buttonBar.add(...)` 나열)와 위젯의 폭·빈 칸 추가(`new LabelToolItem("")` 횟수)를 포함한다.
2. 생성자 메서드는 `analysis method <클래스>.<클래스명> -o code`가 원문을 낸다(오버로드 후보 포함).
3. 문자열 상수(`private String monitorStyle01 = "<div style=…"`)는 필드 선언 요약에 값을 낸다.

**추가 재현 (N15·N16)**
- 생성자뿐 아니라 **익명 핸들러·`buildGrid()` 안의 `LookupTriggerField.addTriggerClickHandler`** 본문도 `analysis method`/`--section methods`에는 `- 조회창 …` 요약 한 줄이거나 아예 없어서 `Read(offset/limit)`로 열었다(`Tdm40_Tab_ManlJob` L163-292, `Tdm41_Tab_ManlDutyOrg` L126-274·L313-339, `Tdm41_TabPage_ManlDutyOrg` L136-261). 이 핸들러들이 화면의 검사 메시지·분기를 대부분 가지고 있어, 요약에서 빠지면 "이벤트 15개 중 몇 개가 어떤 분기를 갖는지"를 원본을 열어야만 안다.
- 제안 추가: `analysis method <클래스>.<메서드> -o code`가 **익명 클래스 핸들러 본문**(`new SelectHandler(){…}`·`new TriggerClickHandler(){…}`)도 호출 메서드와 함께 잘라 내지 않고 낸다. 이벤트 절의 `→ 인라인 L144-151 (new SelectHandler() { @Override publi…)`처럼 잘린 항목은 본문 줄 범위를 그대로 보여 준다.

**합격 기준**
- 위 재현에서 툴바 요소 순서와 라디오 폭 75, 모니터 스타일 상수가 출력된다.

## 6. `analysis grid`가 묶음 헤더·고정 열·헤더 색·런타임 헤더 변경을 보여 주지 않는다

**어떤 경우**
- `addHeaderGroupMap(new HeaderGroupMap(0, 6, new HeaderGroupConfig(…, 1, 4)))`로 묶음 헤더를 만들거나 `setFrozenNum`/`addTextFrozen`으로 앞 열을 고정하는 그리드. 예: `Tdm50_Tab_DutyProgress`(N02), `Tdm01_Lookup_HrChangeInfo`(N04, 변동 전/후).

**재현**
```bash
yunhee analysis grid Tdm50_Tab_DutyProgress
yunhee analysis grid Tdm01_Lookup_HrChangeInfo
```

**기대한 결과**
- 표 아래에 `묶음 헤더: 메뉴얼 확정(1424) = 열 6~9 · 점검주기별 항목수 = 열 10~16 · 월별점검항목수 = 열 17~28`, `고정 열: 1~3`, 열별 헤더 색(`"456EA6"`)이 나온다. 코드가 런타임에 헤더를 바꾸면(`changeMonthHeader`가 `getColumn(17).setHeader(…)`) `동적 헤더: 열 17~28 (기준월부터 12개월)`을 알려 준다.

**실제 결과**
- 열 표(속성·폭·제목·메서드·렌더링·편집기·숨김·컬럼 검증)만 나온다. `GridBuilder 메서드` 칸의 `addTextFrozen`으로 고정을 짐작할 수 있을 뿐이고, 묶음 헤더 범위·색·제목·동적 헤더는 없다. 세 화면 모두 `Read`로 `buildGrid()` 30~50줄을 직접 읽어 `gb.group(…)`·`headerStyle`을 만들었다.

**수정 제안**
1. `HeaderGroupMap(행, 시작 열, config(…, 행수, 열수))`를 읽어 `묶음 헤더` 표(제목·색·열 범위·행수)를 낸다.
2. `setFrozenNum`·`addTextFrozen` 열을 `고정 열: …`로 낸다.
3. 열 인자의 색 문자열(`"0069B4"`)을 `헤더색` 칸으로 낸다.
4. `grid.getColumnModel().getColumn(n).setHeader(…)` 같은 런타임 헤더 변경이 있으면 `동적 헤더` 절에 메서드와 대상 열을 알린다(지금 `동적 숨김 호출` 절과 같은 방식).

## 14. `compare --param`이 숫자처럼 보이는 문자열 값을 정수로 바인딩해 SQL 오류를 낸다

- 추가: 2026-10-24, 0.5.0. 계기: AssetERP **N09 책무담당자 등록**(`Tdm08_Tab_Manager`) 적용기간 조회 API 대조.
- 처음에는 `--grid 'Tdm08_Tab_Manager#manageBuildGrid'` 인자 오류로 잘못 기록했으나 다시 돌려 보니 원인은 `--grid`가 아니라 `--param` 바인딩이다(`--grid`는 SQL 실행 뒤 단계라 거기까지 가지도 못한다).

**어떤 경우**
- `varchar` 열(`tdm08_manager_type`, 값 `'21'`)을 숫자처럼 보이는 `--param` 값으로 비교하는 SQL.

**재현**
```bash
cd AssetERP
yunhee compare GET /api/v1/tdm/managers/infos -c kfstest -p managerType=21 -p orgId=29022 \
  --sql tdm08_manager_info.selectByManagerType \
  --param companyId=28000 --param managerType=21 --param orgId=29022 \
  --grid 'Tdm08_Tab_Manager#manageBuildGrid'
```

**기대한 결과**
- `API rows=1, SQL rows=1 ✅` (API는 `-p managerType=21`로 1행을 돌려준다).

**실제 결과**
```
[ERROR] SQL 실행 실패: operator does not exist: character varying = integer
LINE 8:    AND tdm08_manager_type = 21
```
- `--param managerType=21`이 따옴표 없는 정수 `21`로 SQL에 들어간다. `--grid`를 `#manageGrid`로 바꿔도 같다.
- 같은 증상이 08 교훈 L07·L08에 이미 있다(`yearText=2024`, `mapper-run -p k=1`). 이번에 `compare`에서도 재현됐다. 대조를 못 해 결과확인 항목 3에 "미확인"으로 남겼다.

**수정 제안**
1. `--param` 값은 기본 문자열로 바인딩한다(`analysis sql`의 바인딩 모델이 있으면 그 파라미터 타입을 쓴다). 정수가 필요한 열은 DB가 `varchar → numeric` 암묵 변환을 하지 않으므로 오류가 난다.
2. 타입을 지정하는 문법을 둔다: `--param managerType=s:21` / `--param companyId=n:28000`.
3. 위 오류가 나면 `숫자처럼 보이는 값은 정수로 바인딩됩니다 — --param k=s:값 으로 문자열 지정`을 한 줄로 안내한다.

**합격 기준**
- 위 재현이 `API rows=1, SQL rows=1 ✅`로 끝난다(또는 `s:` 지정으로 끝난다).

**기대한 결과**
```bash
yunhee api POST /api/v1/sys/files -p parentId=202610249885378 -F file=@/tmp/t.txt
→ HTTP 200, Data: {fileId, fileNm, …}
```

**수정 제안**
1. `-F/--form <이름>=@<경로>` 반복 옵션(curl 문법). `@`로 시작하면 파일 파트, 아니면 문자열 폼 필드. 파일 파트의 `Content-Type`은 확장자로 추정하고 `;type=…`로 덮어쓸 수 있다.
2. `--body`와 `-F`는 함께 못 쓴다(함께 주면 오류).
3. 구현: `tools/api_client.py`의 `request_api()`에 `files`/`form_data`를 받아 `httpx.request(..., files=…, data=…)`로 넘긴다(JSON 본문일 때만 `json=`). `Content-Type: multipart/form-data` 경계는 httpx가 만들므로 기본 JSON 헤더를 이 경우에만 빼야 한다. 세션 만료 재로그인 재시도 두 곳(L462·L499 부근)에도 같은 인자를 넘기고, 파일은 재시도 때 다시 열어야 하므로 경로로 보관한다.
4. 응답 요약은 기존 `summarize_response` 그대로(`Data: {…}`). 파일 크기·이름을 `요청:` 줄에 한 줄로 표시한다.
5. `cli.py` `api` 명령의 `--body` 옆에 옵션을 추가하고 도움말(L963 부근 예시)에 업로드 예를 더한다.

**합격 기준**
- 위 기대한 결과대로 업로드가 200으로 끝나고, `sys10_file`에 행이 생긴다. 시험은 올린 `fileId`로 `DELETE /api/v1/sys/files/{fileId}`까지 해서 흔적을 지운다.
