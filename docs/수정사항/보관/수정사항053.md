## 1. `yunhee run "gradle test …"` 요약이 마지막 시험 클래스만 센다 (우선순위 높음)

| 재현 | 출력 | 실제 (`build/test-results/test/TEST-*.xml`, `analysis run last --tests`) |
|:---|:---|:---|
| `cd backend && yunhee run "gradle test --tests '*NoticeSmsSenderDbTest' --tests '*EmpMyLeaveDbTest' --tests '*EmpBenefitDbTest'"` | `✅ … · tests 4 (fail 0, skip 0)` | 3개 클래스 **14건**(4 + 4 + 6), 실패 0. `analysis run last --tests` → `전체 14 · 실패 0` |
| `yunhee run "gradle test --tests '*EmpLeaveCancelDbTest' --tests '*PayExpenseConfirmDbTest' --tests '*AprApprActionDbTest'"` | `… · tests 2 (fail 0, skip 0)` | 14건, 실패 0 |

- "4건만 돌았다"로 읽히거나, 앞 클래스의 실패가 요약에 안 잡힐 위험이 있다(이번엔 실패 0이라 숫자만 틀림).
- 고칠 것: 요약은 `TEST-*.xml` 전체(이번 실행에 바뀐 파일)를 합산. `tests 14 (fail 0, skip 0) · 클래스 3`.

### 1-2. `analysis run last --tests`가 실패한 클래스만 보이고 메서드·문구가 없다

| 재현 | 출력 | 필요했던 것 |
|:---|:---|:---|
| (`EmpLeaveCancelDbTest`가 실패한 실행 뒤) `yunhee analysis run last --tests` | `실패 1` / `❌ kr.co.kfs.asseterp.biz.emp.EmpLeaveCancelDbTest` | 실패 메서드 `상신하지_않은_휴가와_다른_회사_휴가는_취소할_수_없다()`와 첫 줄 `NullPointerException: Cannot invoke "Object.equals(Object)" because "o" is null at ImmutableCollections$Set12.contains` — XML을 직접 파싱해서 찾았다 |

- 고칠 것: 실패 테스트마다 `클래스.메서드` + `failure message` 첫 줄 + 첫 `kr.co.kfs` 스택 한 줄.

## 2. `trace-crud`: 같은 `INSERT … SELECT`를 AS-IS 쪽만 대상 테이블을 R로도 센다 (중간)

| 재현 | 출력 | 실제 |
|:---|:---|:---|
| `trace-crud --screen '#1033'` | `apr99_appr_del: ASIS CR / TOBE C  ⚠ TOBE에 R 없음` | AS-IS `apr01_appr.insertApprDel`(apr01_appr.xml:3112)과 TOBE `AprApprActionMapper.xml#insertApprDel`(L302-)은 같은 SQL — `INSERT INTO apr99_appr_del SELECT … FROM apr01_appr WHERE apr01_appr_id = …`. 이 화면에서 apr99를 읽는 SQL은 없다(`analysis sql apr01_appr.selectById` 테이블에 apr99 없음) |

- 다른 점은 줄바꿈뿐: AS-IS는 `INSERT` / `  INTO	apr99_appr_del` 두 줄, TOBE는 `INSERT INTO apr99_appr_del` 한 줄. AS-IS 파서가 `INTO`를 `INSERT`와 다른 줄에서 만나면 대상 테이블을 SELECT 쪽(R)에도 넣는 것으로 보인다(추정).
- 고칠 것: `INSERT … INTO t … SELECT … FROM u`는 줄바꿈과 상관없이 t = C, u = R. AS-IS·TOBE 같은 규칙.

### 2-2. 글자(C·R·U·D)의 근거를 볼 방법이 없다

- `## evidence`가 늘 `(없음)`이고 `-o json`에도 근거 SQL이 없다. 위 apr99 R처럼 "어느 SQL이 이 R을 만들었나"를 찾으려고 후보 SQL을 하나씩 `analysis sql`로 열었다.
- 고칠 것: `--why <테이블>`(또는 json에 `sources`) — 테이블·글자마다 `ASIS sqlId(파일:줄)` / `TOBE 매퍼#id`.

## 3. `compare` (중간)

### 3-1. API 파라미터(`-p`)를 SQL 파라미터로 넘기지 않는다

| 재현 | 출력 |
|:---|:---|
| `compare GET /api/v1/emp/my-leaves -c kalpa -u 401 -p stdYear=2026 --sql emp20_leave.selectByPersonId --param companyId=… --param personId=… --param leaveY=2026` | `⚠ 값 없음: stdYear` · `AS-IS SQL 실행 실패: syntax error at or near ":"` · `SQL 필수 파라미터 누락 (-- 필요: stdYear)` |

- `-p stdYear=2026`을 줬는데 `--param stdYear=2026`도 따로 줘야 했다. `empId`·`orgId`·`companyId`는 로그인에서 채우면서 이름이 같은 API 파라미터는 안 넘긴다.
- 고칠 것: `--param`에 없으면 같은 이름의 `-p` 값을 쓴다(쓴 것은 `SQL params:` 줄에 `(← -p)` 표시).

### 3-2. 그리드가 아닌 조회에 그리드 열 대조를 자동으로 붙인다

| 재현 | 출력 |
|:---|:---|
| `compare GET /api/v1/emp/my-leaves/days -c kalpa -u 401 -p stdYear=2026 --sql emp20_leave.selectByDays --param personId=… --param stdYear=2026 --param apprCheckYn=false` (`--grid` 안 줌) | `API rows=1, SQL rows=1 ✅  fields ⊇ grid cols ⚠️ (Emp20_Tab_Leave#buildGrid, 17컬럼) (missing: apprStatusCd, …, startDate)` |

- `selectByDays`는 아래 요약 칸(총·사용·잔여) 한 줄이라 그리드와 상관없다. ⚠️가 결과를 틀린 것처럼 보이게 한다.
- 고칠 것: `--grid`를 안 주면 SQL이 그 그리드의 조회 SQL(`GridRetrieveData`의 sqlId)일 때만 자동 대조, 아니면 `grid: -`. `--no-grid`도.

## 4. 메뉴가 없는 클래스(편집 폼·탭 페이지)를 못 찾는다 (낮음)

| 재현 | 출력 | 우회 |
|:---|:---|:---|
| `analysis ui Emp20_Edit_Leave` | `[ERROR] 색인 화면 파일을 찾을 수 없습니다: Emp20_Edit_Leave.md` | `analysis method Emp20_Edit_Leave`(목록)로 메서드를 하나씩 |
| `drift Sys01_TabPage_Info04 --base baseline` | `[ERROR] 오류: 화면 'Sys01_TabPage_Info04'을(를) 색인에서 찾을 수 없습니다.` | `drift Sys01_Tab_Company`(부모 화면)로 보고 `git log -- …/Sys01_TabPage_Info04.java`로 확인 |

- 두 클래스 모두 색인이 이미 알고 있다: `screen-desc 1032`가 `Emp20_Edit_Leave`를 "AS-IS 연결 클래스"로, `analysis screen Sys01_Tab_Company --class Sys01_TabPage_Info04`가 이벤트까지 보여 준다.
- 고칠 것: 화면 파일이 없으면 그 클래스를 연결 클래스로 가진 화면을 찾아 `--class`로 처리(`analysis ui`), `drift`는 그 클래스 파일만의 변경을 보여 준다.
