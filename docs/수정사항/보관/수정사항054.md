## 0. 문제 — 화면·파일 단위라서 결과 대부분이 공통 파일 잡음

| 재현 | 출력 | 실제 |
|:---|:---|:---|
| `yunhee drift --all --done-only --base baseline --ignore-space -o json` | 421화면 중 **변경 271** | 자기 파일이 바뀐 화면은 **32**, 나머지 **239**는 공유 파일(`shared: true`)만 바뀜. 바뀐 파일은 129개 |
| (같은 결과에서 파일별 화면 수) | `Sys99_Print.java` 95화면, `apr01_appr.xml` 95, `Apr01_Appr.java` 90, `Sys00_Common.java` 89, `sys01_company.xml` 51 | `git diff -w` hunk: `Sys99_Print`는 출력 메서드 몇 개(L1371·L3377 +50·L3841 +45), `apr01_appr.xml`은 1줄 + **새 SQL 하나**(L1074 +61). 대부분의 화면은 그 메서드·SQL을 쓰지 않는다 |

- 화면 → 메서드·SQL ID는 이미 색인(`docs/as-is/src/.../screens/*.md`의 서버 메서드 파일:줄, SQL ID)에 있다. **이 정보로 hunk를 메서드·SQL ID에 매달면** 잡음이 빠진다.

## 1. `drift-unit` — 바뀐 파일을 SQL ID·메서드 단위로 (높음)

```
yunhee drift-unit [--base baseline|index|<커밋>] [--done-only] [--kind SQL,LOGIC,…] [-o table|json]
```
- 매퍼 XML: hunk가 걸친 `<select|insert|update|delete id=…>` → 단위 `ns.id` (상태: 변경 / 새로 생김 / 없어짐).
- Java: hunk가 걸친 메서드(`클래스#메서드`). import·필드만 바뀐 것은 `ETC`.
- 화면 클래스(client/vi …Tab_·Lookup_ 등): 단위 = 클래스, 종류 `UI`. 모델(`*Model*.java`)은 `MODEL`.
- 단위마다: **쓰는 화면(메뉴 번호 `#1029`, 번호 없으면 여는 화면 번호)** + **TOBE 대응**(`trace-pair` 매칭과 같은 근거: AS-IS 주석, 같은 SQL ID, 같은 테이블) + 변경 줄 수 + 마지막 커밋(해시·날짜·제목).
- 표 예:
  ```
  종류  단위                                   변경   화면                     TOBE 대응                         커밋
  SQL   apr01_appr.selectXxx                   새로   (없음)                   (없음)                            ff05be9ff 11-05 …
  LOGIC Sys99_Print#printXxx()                 +50    #1201 #1202              PrintController#…                 …
  ```
- "쓰는 화면 없음"인 단위(새 SQL·안 쓰는 메서드)는 `--all-units` 없이는 접어서 끝에 건수만.

## 2. 파일·단위 기준선 + `drift-done` (높음)

- 지금 `baseline.json`은 **화면마다** 파일 해시를 들고 있다. 공통 파일 하나를 반영해도 `drift --record <화면>`을 95번(또는 95개 인자) 해야 하고, 빠뜨리면 같은 변경이 계속 뜬다.
- 고칠 것: 기준선에 **단위(또는 파일) 기준**을 함께 둔다. `drift-done <키…|단위…>`가 그 단위 기준을 지금 커밋으로 옮기면, 그 단위를 쓰는 모든 화면이 "동일"로 바뀐다.
- `drift`(화면 단위)는 "화면 기준 OR 단위 기준" 중 새것과 비교 — 기존 `--record` 결과와 호환.

## 3. `drift-list` — 대장에 덧붙이기 (중간)

```
yunhee drift-list docs/3-변경반영/변경반영-대장.md [--base baseline] [--dry-run]
```
- `drift-unit` 결과를 대장 표 끝에 `대기`로 덧붙인다. 키는 `CH-` 다음 번호를 이어서.
- 같은 단위가 이미 `대기`로 있으면 커밋·요약만 갱신, `반영`·`해당없음`인데 다시 바뀌었으면 **새 줄**.
- 칸: 키 · 발견일 · AS-IS 커밋 · 종류 · 단위 · 변경 요약(빈칸 가능) · 영향 화면 · TOBE 대응 · 상태 · 처리일 · 비고 (양식은 `변경반영-대장.md` "칸").
- `drift-done CH-0012 --status 반영|해당없음 --note "…"`가 그 줄의 상태·처리일·비고를 쓰고 §2 기준을 옮긴다.

## 4. `drift-diff <단위>` — 반영 판단 한 화면 (중간)

```
yunhee drift-diff apr01_appr.selectXxx [--base baseline]
yunhee drift-diff 'Apr01_Appr#update'
```
- AS-IS 전후(SQL은 `trace-diff`처럼 정규화 diff, 메서드는 그 메서드 범위만) + 지금 TOBE 대응 본문(매퍼 id·서비스 메서드)을 나란히.
- 화면 UI 단위는 `analysis ui` 수(버튼·이벤트·그리드) 전후 + TOBE 수.

## 5. `drift-db` — DB 구조 차이 (중간)

```
yunhee drift-db [--from <이전 dbml>] [--to <새 dbml>]
```
- `check-git.sh --db-index`는 DB 색인을 덮어써서 "무엇이 바뀌었나"가 남지 않는다. 직전 dbml 스냅샷을 두고(예: `.yunhee/asseterp-dbml.prev.md`) 테이블·열(타입·NOT NULL·기본값)·함수 본문의 추가/변경/삭제.
- 바뀐 열마다 그 열을 쓰는 AS-IS SQL과 TOBE 매퍼(`trace-column`과 같은 근거).

## 6. `drift-log` — 들어온 커밋 (낮음)

```
yunhee drift-log [--since baseline|<커밋>|<날짜>]
```
- 커밋마다 파일과 종류(DB·SQL·LOGIC·MODEL·UI·ETC) 한 줄. 매일 알림(ntfy)에 쓰는 요약용. `git log --stat`를 종류로 접은 것.

- framework-sprt `AssetERP/make-change-docs.sh`(처리는 `tools/make_change_docs.py`)가 §1·§3·§7 우회를 한다. 아래는 그것이 하는 순서.
