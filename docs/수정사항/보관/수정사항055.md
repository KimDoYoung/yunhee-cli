# 수정사항 055 — `drift-done`: 대장 칸 밀림, `확인` 칸, 파일 기준선 범위 / `drift-diff`: SQL ID 하나가 아니라 파일 전체 diff

- 시급도: §1 높음(대장을 망가뜨림 — 지금은 대장 복사본을 `--ledger`로 넘겨 기준선만 옮기는 식으로 피하고 있다), §2 중간, §3 중간, §3a 중간(같은 날 BIZ 묶음에서 발견).
- 재현은 `cd ~/work/framework-sprt/AssetERP`에서. 대장 칸 규칙은 `docs/3-변경반영/README.md` "상태"·"반영 완료 조건", 칸 설명은 `변경반영-대장.md` "## 칸".

## 1. 대장 칸이 한 칸씩 밀린다 (높음)

대장은 **12칸**이다(2026-11-11에 `확인` 칸이 생김):

```
| 키 | 발견일 | AS-IS 커밋 | 종류 | 단위 | 변경 요약 | 영향 화면 | TOBE 대응 | 확인 | 상태 | 처리일 | 비고 |
```

`drift-done`은 `확인` 칸이 없던 11칸 양식을 가정하고 칸 위치로 쓰는 것 같다.

| 재현 | 결과 |
|:---|:---|
| `yunhee drift-done CH-0220 --status 반영 --note "…"` | `확인` 칸에 `반영`, `상태` 칸에 `2026-11-11`, `처리일` 칸에 note, 원래 `비고`는 그대로 남음 |

전 → 후 (실제 diff):
```
-| CH-0220 | … | +3 −1줄 | (못 찾음) |  |  | 대기 |  | 쓰는 화면을 색인에서 못 찾음 — 확인 필요 |
+| CH-0220 | … | +3 −1줄 | (못 찾음) |  | 반영 | 2026-11-11 | TOBE 최근결재선 …(note) | 쓰는 화면을 색인에서 못 찾음 — 확인 필요 |
```

- 고칠 것: 칸 위치를 고정하지 말고 **표 머리줄(`| 키 | … |`)에서 칸 이름으로 위치를 찾는다**(`상태`·`처리일`·`비고`, 아래 §2의 `확인`). 이름을 못 찾으면 쓰지 말고 오류로 멈춘다.
- 줄의 칸 수가 머리줄과 다르면(셀 안 `|` 등) 그 줄은 건드리지 말고 경고.
- `drift-ledger`(대장에 덧붙이기)도 같은 머리줄 기준으로 새 줄을 만드는지 확인 — 지금 대장의 `대기` 줄은 12칸이 맞다(우리 임시 스크립트가 만든 것).
- `--dry-run`: 바꿀 줄의 전·후를 보여 주고 쓰지 않음(대장을 건드리는 명령이라 있으면 좋다).

## 2. `확인` 칸을 채울 수 없다 (중간)

- 규칙: 상태 `반영`은 `확인` 칸(무엇으로 확인했나 — `compare 일치(3조합)`, 테스트 클래스 이름, `api 200·필드 확인`, `화면 확인(사용자)`)이 비면 안 된다.
- 제안:
  - `--check "<문구>"` → `확인` 칸에 씀.
  - `--status 반영`인데 `--check`가 없고 그 줄의 `확인` 칸도 비어 있으면 **경고하고 멈춤**(`--force`로만 진행). `해당없음`·`보류`·`넘김`은 `확인`이 없어도 된다.
  - `--tobe "<파일·id>"` → `TOBE 대응` 칸(지금 자동 후보가 틀리거나 빈 경우가 많아 반영할 때 고쳐 씀).
- `--note`는 `비고`를 **덮어쓸지 덧붙일지** 정해서 도움말에 적는다(지금 동작이 불분명 — 위 재현에서는 `비고`를 안 건드렸다). 제안: 기본 덮어쓰기, `--note-append`면 ` · `로 덧붙이기.

## 3. 단위 하나를 처리해도 파일 전체 기준선이 옮겨진다 (중간)

| 재현 | `docs/baseline.json`에 생긴 것 |
|:---|:---|
| `yunhee drift-done CH-0220 --status 반영` (단위 `emp00_trans_info.xml · getPersonId`) | `__units__["server/emp/mapper/emp00_trans_info.xml · getPersonId"]` **그리고** `__files__["server/emp/mapper/emp00_trans_info.xml"]` (둘 다 `반영`, 커밋 `3aabbd415`) |

- 같은 파일에 같은 기준 이후 바뀐 단위가 더 있었다: `selectSmsNoticeTarget`(CH-0015, 그때 아직 `대기`).
- 실제로 다시 생김(같은 날 #1133): `drift-done CH-0004 CH-0006 CH-0008 CH-0009 CH-0012 …` → `__files__`에 `biz01_promo.xml`·`biz90_limit.xml`이 생겼는데, 두 파일에 `대기` 단위가 7개 남아 있었다(CH-0005·0007·0010·0011·0013·0014·0216). 손으로 `__files__`에서 지웠다.
- 0.8.7 changelog대로 "파일 또는 연관 단위가 drift-done이면 화면 변경 목록에서 제외"라면, CH-0015를 처리하기 전에도 그 SQL을 쓰는 화면이 `drift`에서 "동일"로 보였을 수 있다. 이번에는 바로 CH-0015도 처리해서 실제로 빠진 것은 없지만, **빠지는 것은 안 된다**는 것이 대장의 원칙이라 막아야 한다.
- 고칠 것:
  - `__files__`는 **그 파일의 바뀐 단위가 모두 처리됐을 때만**(대장에 그 파일 단위 중 `대기`가 없을 때) 옮긴다. 남아 있으면 `__units__`만 옮기고 "파일 기준선 보류: 대기 단위 n (CH-…)"을 한 줄 출력.
  - 단위·파일 이름을 직접 줄 때(키가 아닌 경우)도 같은 검사.
  - `drift`가 화면을 "동일"로 볼 때는 파일 기준선이 아니라 **그 화면이 쓰는 단위**가 모두 처리됐는지로 판단(파일 기준선은 단위로 못 나눈 파일 — `ETC`·새 파일 등 — 에만).

## 3a. `drift-diff <ns.id>`가 그 SQL만이 아니라 파일 전체 diff를 보여 준다 (중간)

`drift-diff`는 "단일 SQL ID 또는 Java 메서드의 AS-IS hunk diff"를 보여 주는 명령인데(0.8.7 changelog), SQL ID를 주면 **그 매퍼 파일 전체 diff**가 나온다.

| 재현 | 결과 |
|:---|:---|
| `yunhee drift-diff biz01_promo.selectByCard` | `selectByCard`와 무관한 hunk까지 모두: 공통 resultMap(`@@ -29`·`@@ -57`), `selectByPersonDay`의 한도 조건(`@@ -206,89 +211,23`), 지운 옛 `selectByPersonYear` 주석 블록 등 |
| `yunhee drift-diff biz01_promo.selectById` | 위와 **글자 하나 다르지 않은 같은 출력** |
| `yunhee drift-diff biz01_promo.selectByCardExcel` | 역시 같은 출력 |
| `yunhee drift-diff emp00_trans_info.getPersonId` | `getPersonId`의 hunk(799 → 899)와 **다른 SQL `selectSmsNoticeTarget`이 새로 생긴 hunk**가 함께 |

- 그래서 `selectByCard`에서 실제로 무엇이 바뀌었는지는 `drift-diff`로 알 수 없었다. 결국 기준 커밋의 매퍼에서 `<select id="selectByCard">…</select>`를 직접 잘라 지금 것(`analysis sql biz01_promo.selectByCard -o code`)과 `diff -w`해서 알았다: 열 4개(`biz01_target_cnt`·카드 사용자명·`biz01_appr_status_cd/nm`) + 조인 2개(`apr01_appr`·`crd03_trans`) + `apprCheck`·`accountId` 조건. 파일 diff로는 이 내용이 다른 SQL 변경 사이에 섞여 보이지 않았다.
- Java 메서드 단위(`Emp00_TransInfo#selectSmsNoticeTarget`)는 그 메서드 hunk만 나와서 괜찮았다.
- `TOBE 대응 문장`도 이름만으로 고른다: `biz01_promo.selectById` → 모든 `*.selectById`(`ActAccountCodeMapper`·`ActAccountNumMapper`·… 10개 넘게)를 늘어놓았다. 매퍼 주석의 `AS-IS biz01_promo.selectById`처럼 **네임스페이스까지 맞는 것**만, 없으면 "없음"이 맞다.

고칠 것:
- SQL 단위는 **기준 커밋과 지금의 그 `<select|insert|update|delete id=…>` 블록만** 뽑아 비교한다(hunk 걸침이 아니라 블록 대 블록). 블록이 새로 생겼으면 "새로 생김" + 지금 블록 전체, 없어졌으면 옛 블록 전체.
- 그 SQL이 `<include refid>`로 쓰는 `<sql>` 조각이 바뀌었으면 그 조각의 diff를 따로 덧붙인다(예: `selectBase`). resultMap이 바뀐 것은 한 줄 요약만("resultMap +3: apprId·targetCount·apprStatusCode").
- `-w`(공백 무시)를 기본으로.
- TOBE 대응은 네임스페이스까지 맞춘다(§위). 후보가 여럿이면 근거(주석·같은 id·같은 테이블)를 함께.

## 4. 받아들임 기준

1. 12칸 대장에서 `drift-done CH-xxxx --status 반영 --check "…" --note "…"` → `확인`·`상태`·`처리일`·`비고`가 제 칸에 들어감. 칸 순서를 바꾼 대장에서도 같음.
2. `--status 반영`에 `확인`이 없으면 멈춤, `해당없음`은 그냥 됨.
3. 같은 파일에 `대기` 단위가 남아 있으면 `__files__`가 생기지 않고 보류 줄이 출력됨. 남은 단위까지 처리하면 그때 `__files__`가 생김.
4. `--dry-run`은 대장과 `baseline.json`을 바꾸지 않음.
5. `drift-diff biz01_promo.selectByCard`와 `drift-diff biz01_promo.selectById`의 출력이 서로 다르고, 각각 그 SQL 블록의 변경만 보임(`selectByCard`: 열 4·조인 2·조건 2). `drift-diff emp00_trans_info.getPersonId`에 `selectSmsNoticeTarget`이 나오지 않음.

## 참고: 이번에 피해 간 방법

- 대장은 직접(칸 이름 기준 임시 스크립트) 채우고, `drift-done … --ledger <대장 복사본>`으로 기준선만 옮겼다. §1·§2가 고쳐지면 이 우회는 필요 없다.
