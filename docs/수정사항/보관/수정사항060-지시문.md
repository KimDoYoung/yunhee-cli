# 수정사항060 구현 지시문 (구현하는 에이전트에게 그대로 준다)

너는 `~/work/yunhee-cli`(Python, typer CLI, uv)에서 **수정사항060**을 구현한다. 요청 문서는 `docs/수정사항/수정사항060.md`다. 그 문서가 정답이고, 이 지시문은 일하는 순서와 지킬 규칙이다.

## 시작할 때 (한 번)

1. `cd ~/work/yunhee-cli && git switch fix060-biz && git status --short` — 브랜치가 `fix060-biz`이고 바뀐 파일이 없는지 본다. main에서 일하지 않는다.
2. `CLAUDE.md`(이 저장소 규칙)를 읽는다. 특히 `WORK_DIR`(yunhee를 실행한 폴더)과 `YUNHEE_DIR`(설치 위치)을 구분하는 규칙.
3. `docs/수정사항/수정사항060.md`의 머리말과 "우선순위 · 구현 순서" 표까지 읽는다. 절(#1~#8)은 **그 절을 구현할 때** 읽는다.
4. `uv run pytest -q`를 한 번 돌려 지금 통과하는 상태를 기록한다(실패가 이미 있으면 그 이름을 적어 두고, 네 작업 탓이 아님을 구분한다).

## 일하는 순서

**#1 → #2 → #3 → #4 → #5 → #6 → #7 → #8**, 한 번에 한 절만 한다. 절마다:

1. 문서의 그 절(재현·사용법·구현·테스트·확인 방법)을 끝까지 읽는다.
2. 문서가 "재사용"하라고 한 기존 함수(`src/yunhee/tools/trace/tobe.py`의 `parse_controller`·`parse_service`·`_body`·`parse_api_ts`·`field_types`, `src/yunhee/tools/api_client.py`의 `request_api`·`resolve_user_credentials`·`login`, `src/yunhee/tools/sql_runner.py`의 `guard_statement`)를 **먼저 읽고** 시그니처를 확인한다. 새로 비슷한 것을 만들지 않는다.
3. 테스트부터 쓴다: `tests/test_fix060.py`에 그 절의 `class TestBizXxx`. 가짜 소스는 `tests/fixtures/biz060/` 아래. HTTP·DB는 monkeypatch한다(기존 `tests/test_api_client.py`·`tests/test_sql_runner.py`가 하는 방식을 따라 한다 — 먼저 열어 본다). **테스트에서 실제 서버(8082)·실제 DB에 붙지 않는다.**
4. 구현: 로직은 `src/yunhee/tools/biz/<파일>.py`, 명령은 `src/yunhee/cli.py` **파일 끝부분**에 `@app.command(name="biz-…")` 함수로만(옵션 받고 biz 모듈 함수 부르기, 10~30줄).
5. `uv run pytest tests/test_fix060.py -q` → 통과. 이어서 `uv run pytest -q` 전체 → 시작 때보다 실패가 늘지 않았는지. `uv run ruff check src tests` → 새 경고 없음.
6. 문서 그 절의 "확인 방법"을 실제로 해 본다(아래 "실제 확인" 규칙). 결과를 그 절 끝에 `### 구현 결과 (날짜)` 로 3~6줄 적는다: 무엇을 했는지, 확인 명령과 실제 출력 요약, 문서와 다르게 한 것과 이유.
7. 커밋: `git add -A && git commit -m "수정사항060 #N: <명령> 구현"`. 한 절 = 한 커밋.

한 절이 막히면(정보 부족·문서와 소스가 다름) 추측해서 진행하지 말고 그 절 끝에 `### 막힘` 으로 무엇이 왜 막혔는지 적고 다음 절로 간다. #2가 막히면 #3·#4·#8이 #2에 기대므로 사용자에게 알린다.

## 꼭 지킬 것

- **`pyproject.toml`의 버전과 `src/yunhee/CHANGELOG.md`는 고치지 않는다.** (다른 PC에 아직 합치지 않은 0.8.9~0.9.2가 있다. 버전은 main에 합칠 때 사람이 정한다.)
- `cli.py`의 기존 명령·옵션을 바꾸지 않는다. 예외는 #1의 `api` 명령에 `--password`(와 #1의 `--force-login`)를 **더하는 것**뿐이다.
- 기존 동작을 깨지 않는다: `-u admin`의 로그인, `YUNHEE_TEST_ACCOUNTS`, 세션 재사용(`_load_session`/`_save_session`)은 그대로 되어야 한다.
- 테이블·열 이름을 추측하지 않는다. 문서에 "확인됨"이라고 적힌 것만 그대로 쓰고, 나머지는 구현 전에 `uv run yunhee sql "select column_name from information_schema.columns where table_name='<표>'"`로 확인한다(이 명령은 읽기 전용이라 안전하다).
- `docs/help/index.md`에는 끝에 "업무분석(biz-*)" 절 하나만 더하고, 명령별 설명·예시는 새 파일 `docs/help/biz.md`에 쓴다(마지막 절을 끝낸 뒤 한 번에).
- 문서·주석·출력 문구는 한국어. 절 번호를 가리킬 때 `§` 같은 특수문자를 쓰지 않고 `#1`처럼 쓴다.
- push하지 않는다(사람이 한다).

## 실제 확인 (서버·DB를 쓰는 확인)

- 실제 확인은 `cd ~/work/framework-sprt/AssetERP`에서 한다. 브랜치 코드를 쓰려면 이 저장소에서 `uv tool install --editable .`로 설치한 뒤 `yunhee --help | grep biz-`로 새 명령이 보이는지 본다.
- 계정: 가상 회사 `kalpa`, 직원 사번 `401`·`402`(일반 사원)·`301`(경영관리 과장)·`100`(대표), 회사 관리자 `admin`, KFS 관리자는 `-u admin -c admin`. **모든 비밀번호 `1111`.**
- **로그인 실패를 반복하지 않는다.** 직원 계정은 5회 실패로 잠긴다. 한 번 실패하면 같은 계정으로 다시 부르지 말고 원인(사번이 다른 회사 사원으로 잡혔는지, 비밀번호 출처)을 먼저 찾는다.
- DB를 바꾸는 확인(#4 결재, #5 저장, #7 쓰기) 전에는 `~/work/framework-sprt/AssetERP/tools/db_dump_backup.sh`를 돌린다. 시험으로 만든 행은 확인 뒤 되돌리고, 못 되돌린 것은 `### 구현 결과`에 ID와 함께 적는다.
- #3 `biz-authz`의 `--probe-write`, #7 `biz-db-write`는 **localhost DB에서만** 시험한다.
