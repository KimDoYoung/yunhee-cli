## #4 `biz-appr --pre` — 상신 행을 먼저 만드는 업무

- 현상: 급여대장(A02)·퇴직정산(A05)은 결재문서를 쓰기 전에 업무 쪽 "상신 행"을 만들어 그 ID를 `refId`로 쓴다. 지금은 `yunhee api POST …`로 따로 불러 ID를 받아 `--ref`에 넣어야 한다.
  - A02: `POST /api/v1/pay/relate-apprs/month` 본문 `{payCode, payDate}` → `data` = 상신 행 ID
  - A05: `POST /api/v1/pay/relate-apprs/retire` 본문 `{monthId}` → `data` = 상신 행 ID
- 고칠 것: `--pre '<METHOD> <path> <json>'` 옵션. 주면 먼저 부르고 응답 `data`(숫자)를 `ref`로 쓴다. `--ref`와 `--pre` 중 하나는 필수.
  링크 표(#3)에 `pre` 기본값을 둘 수도 있다(A02는 `--pay-code 01 --pay-date 2026-11-25`처럼 값만 받기).
- 함께: 결재 **완료된** 상신 행에 다시 상신하려 하면(같은 구분·지급일의 `GET /api/v1/pay/relate-apprs?payCode=&payDate=` 상태가 10·20·30) 화면처럼 "이미 상신 중입니다"로 멈춘다 — 서버가 이 검사를 안 해서(업무분석 의심 #78) 도구가 실수로 완료 건 연결을 덮어쓰지 않게 하려는 것.
- 확인(A02, 반려 문서로 시험): `yunhee biz-appr A02 --pre 'POST /api/v1/pay/relate-apprs/month {"payCode":"01","payDate":"2026-12-24"}' -u 301 -c kalpa --approver 100 --dry-run`.

## #6 `biz-authz --probe-appr` — 결재 ID 바꿔치기 시험

- 배경: 업무분석 의심 #66·#69·#78·#90이 **같은 모양**이었다. 업무 행의 "결재 ID 기록" API(`…/{id}/appr-id`, `…/{id}/appr`)가 문서가 있는지·내 문서인지·링크코드·상태를 보지 않아,
  결재 **완료**된 행의 결재 ID를 없는 값으로 바꾸면 그 행의 수정 잠금이 풀린다. 이벤트마다 손으로 3~4번 호출해 확인했다.
- 고칠 것: `biz-authz <도메인> --probe-appr -u <과장> -c kalpa`
  1. `biz-endpoints`에서 경로가 `/appr-id` 또는 `/appr`로 끝나는 PUT을 고른다.
  2. 같은 리소스의 목록 GET에서 결재 상태 30인 행 하나(`apprId`·`statusCode` 칸)를 찾는다. 없으면 `건너뜀(완료 행 없음)`.
  3. 원래 `apprId`를 기억 → `apprId = 1`로 PUT → 같은 리소스의 저장 PUT을 **`--dry-run`처럼 값을 바꾸지 않고 그대로** 보내 본다(또는 목록 GET의 잠금 표시만 다시 읽는다) → **반드시 원래 `apprId`로 되돌린다**(try/finally).
  4. 판정: 1로 바꾸는 PUT이 200이면 `⚠ 결재 ID 검사 없음`, 되돌리기 실패면 빨간 경고와 되돌릴 명령을 출력.
- 확인: `yunhee biz-authz pay --path tax-withholdings --probe-appr -u 301 -c kalpa` → `⚠ 결재 ID 검사 없음` 1줄, 실행 뒤 `pay40_income_tax_withholding.pay40_appr_id`가 원래 값.

## #8 `compare`가 경로의 쿼리 문자열을 빠뜨린다 (PAY-BZ-0007·0010에서 발견)

- 현상 1(PAY-BZ-0007): `yunhee compare GET "/api/v1/pay/insure-applies?gubun=1&startDate=…&closeDate=…" --sql pay31_insure_apply.selectByCompanyId -p …` →
  서버 로그 `Required request parameter 'gubun' … is not present`(400). 같은 경로를 `yunhee api`로 부르면 200·6행.
- 현상 2(PAY-BZ-0010): `yunhee compare GET "/api/v1/pay/expenses?startDate=2026-11-01&closeDate=2026-11-30&managerYn=false&statusCheckYn=false" --sql pay50_expense.selectExpenseAppr -u 301 -c kalpa -p personId=<301> …`
  → `API rows=1, SQL rows=0 ❌`. 같은 경로를 `yunhee api … --log`로 부르면 `Rows: 0`(TOBE = AS-IS). 즉 compare가 `managerYn=false`를 빼고 불러 기본값(true)의 행을 셌다 — **틀린 ❌를 낸다**.
- 짐작: `-p`로 받은 값으로 쿼리를 다시 만들면서 경로에 있던 쿼리 문자열을 버리거나, `-p`에 없는 키를 지운다.
- 고칠 것: 경로의 쿼리 문자열을 먼저 파싱해 API 호출에 **그대로** 쓰고, `-p`는 SQL 파라미터(및 같은 이름이면 API 쿼리 덮어쓰기)로만 쓴다. 출력의 `API params:` 줄에 실제로 보낸 쿼리를 찍는다.
- 확인: 위 현상 2 명령이 `API rows=0, SQL rows=0 ✅`.

## #9 `biz-appr` — 여러 업무 행을 한 문서로 묶는 결재(A63·A64 등)

- 현상(PAY-BZ-0010): #1385 지출결의서는 지출 **여러 줄을 한 결재문서**로 상신한다(링크코드 A63). `biz-appr`는 `--ref` 하나·연결 본문 `{apprId}`만 알아서 쓰지 못했다. 손으로 한 순서(API 5회 + 본문 조립 python 1회):
  1. `GET /api/v1/apr/apprs/new-id`
  2. `GET /api/v1/apr/apprs/link-seed?linkCode=A63&refId=<첫 지출>&classTreeId=<분류>&ids=<지출1,지출2,…>` → 제목 `지출결의서(고객 미팅 다과)`·본문 표
  3. `PUT /api/v1/apr/apprs/{apprId}`(mode request, linkCode A63, 시드의 title·content, 결재선)
  4. `PUT /api/v1/pay/expenses/appr-id` 본문 **`{ids:[…], apprId}`**
  5. `POST /api/v1/apr/apprs/{apprId}/confirm` `{action:confirm}`
- 고칠 것:
  1. `--ref`를 여러 개 받기: `--ref 101,102,103`(첫 값이 `refId`). 링크 시드 호출에 `ids=<전부>`를 붙인다(프런트 `Pay50_Tab_ExpenseManager.tsx` L385 `args: { ids: linkDoc.ids.join(',') }`와 같음).
  2. `--link-style`에 `ids-body`를 더한다: 연결 PUT 본문을 `{"ids": [<ref들>], "apprId": <id>}`로 보낸다.
  3. 링크 표(#3)에 넣기:

     | 링크코드 | 업무 | 연결 경로 | 스타일 |
     |:---|:---|:---|:---|
     | A63 | 사업비 지출결의서(#1385·#1407) | `/api/v1/pay/expenses/appr-id` | `ids-body` |
     | A64 | 자금집행결의서(#1386) | `/api/v1/pay/expenses/settle-appr-id` | `ids-body` |

     (#1407 직원 화면은 시드에 `isManager: 'false'`를 더 보낸다 — `Pay50_Tab_Expense.tsx` L271. `--seed-arg isManager=false`처럼 시드 쿼리를 더 붙이는 옵션이면 충분.)
  4. 상신 전에 묶은 행들이 같은 회사·같은 결의자인지, 이미 다른 결재문서(진행·완료)에 붙어 있지 않은지 조회해 보고 걸리면 멈춘다 — 서버가 이 검사를 안 해서(업무분석 의심 #95) 도구가 실수로 완료 문서에 엉뚱한 행을 붙이지 않게.
- 확인: `yunhee biz-appr A63 --ref <지출1>,<지출2> -u 301 -c kalpa --approver 100 --confirm` → `연결 PUT /api/v1/pay/expenses/appr-id {ids:[2개]} → 200`, `승인 100 → 30 완료`, 두 줄의 `pay50_expense_appr_id`가 같은 문서.
