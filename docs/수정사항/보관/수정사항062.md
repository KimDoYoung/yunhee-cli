- 재현은 `cd ~/work/framework-sprt/AssetERP`. Tomcat 8082, 가상 회사 `kalpa`(회사 ID `202611109046432`), 사번 301(사원 ID `202611109048638`, 조직 `202611109048610`)·401, 모든 비밀번호 `1111`. `export YUNHEE_TEST_ACCOUNTS="301:1111,401:1111"`.
- **바꾸지 말 것**(잘 된 것): `api --track`의 "N → M (+k: id=…)" 줄, `api --log`의 SQL 목록, `compare`의 "API rows=a, SQL rows=b ✅/❌" 한 줄과 `(branch: …)` 표시, `sql`의 "💡 비슷한 열" 안내, `biz-endpoints`의 `⚠없음` 표시.

## #1 `compare`가 원본 서버의 파라미터 가공을 모름 — 거짓 ❌

- 현상: #1091 고유자산 거래처리 목록. 원본 화면 `Ast06_Tab_TrIntrinsic.retrieve` L389-437은 종목·거래유형·거래처를 안 고르면 `classTreeId`·`trCodeId`·`corpId`에 **0**을 보낸다.
  원본 서버 `Ast06_Tr.selectByPayCode` L43-107이 0이면 `astClassTreeId`·`trCodeId`·`corpId`를 **null**로 바꿔 SQL에 넘긴다(이름도 `classTreeId` → `astClassTreeId`로 바뀜).
  화면의 `addParam`대로 `--param classTreeId=0 --param trCodeId=0 --param corpId=0`을 주면 SQL이 `ast05_tr_code_id = 0`으로 돌아 0행 → `API rows=1, SQL rows=0 ❌`. 셋을 빼야 `1 = 1 ✅`.
- 재현:
  ```bash
  yunhee compare GET /api/v1/ast/trs/intrinsic -p startDate=2026-11-01 -p closeDate=2026-11-30 -p windowClassName=Ast06_Tab_TrIntrinsic \
    --sql ast06_tr.selectByPayCode --param companyId=202611109046432 --param startDate=2026-11-01 --param closeDate=2026-11-30 \
    --param userId=202611109048638 --param orgId=202611109048610 --param searchText=% --param classTreeId=0 --param trCodeId=0 --param corpId=0 \
    --param payCode=% --param assetType=1 --param abroType=1 --param windowClassName=Ast06_Tab_TrIntrinsic -u 301 -c kalpa --no-grid
  # → API rows=1, SQL rows=0 ❌   (세 0을 빼면 ✅)
  ```
- 같은 날 두 번째 사례(AST-BZ-0009): 원본 서버 `Ast06_Tr.selectEvalList`가 `closeDate` → `holdDate`, `accountId` → `keepAccountId`, `classTreeId` → `astClassTreeId`로 이름을 바꾸고 `abroType`을 만든다. 화면 `addParam`대로 주면 `SQL 필수 파라미터 누락 (-- 필요: holdDate)`.
- 고칠 것(둘 중 하나, 앞이 좋음):
  1. `--from-server <서버클래스.메서드>`(또는 SQL ID에서 서버 메서드를 찾아 자동): 서버 메서드가 `request.getXxxParam("a")`를 읽어 `param.put("b", …)`로 넘기는 것을 정적으로 뽑아, `--param`을 **서버가 SQL에 넘기는 이름·값**으로 바꾼다. 최소한 `if(x == 0L) param.put("y", null)` 꼴(0 → null)과 이름 바꾸기만 알아도 된다.
  2. 그게 어려우면 경고만: SQL에 `<when test="trCodeId != null">`이 있는데 `--param trCodeId=0`이 들어오면 "서버가 0을 null로 바꾸는지 확인하세요(`analysis method <서버메서드> -o code`)"를 출력.
- 확인: 위 명령이 세 0을 준 채로 `1 = 1 ✅`, 또는 경고 한 줄.

## #2 `compare` 로그인 파라미터 — `userId`도 채우고, 손으로 준 값과 다르면 경고

- 현상: `compare`는 로그인 사원으로 `empId`·`orgId`를 SQL 파라미터에 더한다(출력 `SQL params: … empId=…, orgId=…`). 그런데 원본 SQL이 쓰는 이름은 화면마다 `userId`·`personId`·`empId`로 다르다.
  `ast06_tr.selectByAccrued`·`selectByPayCode`는 `userId`·`orgId`를 쓴다 → `userId`를 손으로 넣어야 했다.
  또 `--param orgId=202611099190504`(다른 이벤트 문서에서 옮긴 틀린 값)를 주니 그대로 덮어써 조회 결과가 달라졌다. 로그인한 301의 조직은 `202611109048610`인데 경고가 없었다.
- 고칠 것:
  1. SQL이 참조하는 파라미터 중 `userId`·`personId`·`empId`·`loginPersonId`가 있고 `--param`에 없으면 로그인 사원 ID로 채운다. `orgId`·`orgCodeId`도 같게. `companyId`도(이번엔 늘 손으로 넣었다 — 이미 자동이면 그대로).
  2. 손으로 준 값이 로그인 값과 다르면 `⚠ orgId=202611099190504 (로그인 사원 301의 조직은 202611109048610)` 한 줄.
- 확인: `yunhee compare GET /api/v1/ast/settles/accrueds --sql ast06_tr.selectByAccrued --param assetType=1 --param abroType=1 --param payCode=02 --param trCode=% --param searchText= -u 301 -c kalpa --no-grid` 가 `companyId`·`userId`·`orgId` 없이 API와 같은 행 수(2026-11-12 마지막 상태는 0 = 0, AST-BZ-0007 결제 전이면 1 = 1).

## #3 `sql`(읽기 전용)에서 쓰기 함수가 조용히 NULL

- 현상: `yunhee sql "select f_create_seq()"` → `None`. `--rollback`이면 `202611129141763`.
  `f_create_seq`는 `nextval('seq')`를 부르고 `EXCEPTION WHEN OTHERS THEN RETURN NULL`이라, 읽기 전용 트랜잭션의 오류를 삼킨다.
  이번엔 이게 TOBE 버그(의심 #108: `@Transactional(readOnly = true)` 조회 SQL의 `COALESCE(id, f_create_seq())`가 NULL)의 단서였지만, 모르고 보면 "함수가 원래 NULL을 준다"로 오해한다. `mapper-run`도 같다.
- 고칠 것: 읽기 전용 실행에서 SQL(또는 펼친 매퍼 SQL)에 `nextval(`·`f_create_seq(`·`setval(`, 또는 프로젝트 설정에 적은 쓰기 함수 이름이 있으면 결과 아래에 한 줄:
  `⚠ 읽기 전용 실행: nextval/f_create_seq는 실패해 NULL일 수 있음 — 같은 값을 보려면 --rollback`.
  (가능하면 결과 열이 전부 NULL일 때만.) `.env.yunhee`에 `YUNHEE_WRITE_FUNCS=f_create_seq,f_create_journal_no` 같은 목록을 둘 수 있게.
- 확인: `yunhee sql "select f_create_seq()"` → `None` + 경고 1줄. `yunhee mapper-run "backend/src/main/resources/mapper/AstBookRealMapper.xml#selectByHoldDate" -p companyId=202611109046432 -p holdDate=2026-11-12 -p "searchText=%우리%"` → 경고 1줄.

## #4 `api`에서 값 하나를 셸 변수로 받기

- 현상: 저장 API가 새 ID를 돌려주면(예 `PUT /api/v1/ast/trs/deposits` → `data: 202611129141725`) 다음 호출(분개 생성 `POST /api/v1/act/journals/create {trId}`)에 넣어야 한다.
  요약 출력은 머리줄이 여럿이라 `--raw | grep -o '"data":[0-9]*' | cut -d: -f2`로 뽑았다. `-o json`은 없다(`No such option: -o`). 이벤트 하나에 이런 연결이 3~5번 있다.
- 고칠 것: `--get <경로>` — 응답 JSON에서 그 값만 **한 줄, 머리말 없이** 출력(`data`, `data.0.trId`, `data[].journalId`). 실패(HTTP ≥ 400 또는 `success:false`)면 표준오류에 메시지, 종료코드 1.
  ```bash
  TR=$(yunhee api PUT /api/v1/ast/trs/deposits -u 301 -c kalpa -b '{…}' --get data)
  yunhee api POST /api/v1/act/journals/create -u 301 -c kalpa -b "{\"trId\":$TR,\"trCode\":\"9005\",\"procType\":\"P\",\"exceptYn\":true}"
  ```
- 확인: 위 첫 줄이 숫자만 돌려주고, 잘못된 본문이면 빈 출력 + 종료코드 1.

## #5 DB 함수 본문 보기 — `analysis function`

- 현상: 분개·예금잔고는 DB 함수가 한다(`f_create_journalExpense`, `f_create_journalExpense_sub`, `f_create_depositBook`, `f_create_depositBook_run`, `f_create_seq`).
  본문은 색인 `docs/as-is/db/functions/<이름>.md`에 있는데, `grep -n` 문맥 보기가 framework-sprt 훅에 막히고(AS-IS 색인 직접 읽기 금지) `yunhee grep`은 패턴 줄만 준다. 결국 `Read`로 줄 범위를 짐작해 읽었다.
  `analysis --list`에는 `method sql model grid screen ui tobe run save-script servlet callers`만 있고 함수가 없다.
- 고칠 것: `yunhee analysis function <이름> [-o md|code] [--grep <패턴>]`
  - `md`: 인자·반환·줄 수, 읽는 테이블·쓰는 테이블(INSERT/UPDATE/DELETE), 부르는 함수, `RAISE`·`RETURN` 줄과 메시지(예: `'회계마감 되었습니다.'`), `EXCEPTION WHEN OTHERS THEN RETURN NULL` 같은 오류 삼킴 표시.
  - `code`: 본문(줄 번호), `--lines a-b`로 일부.
  - 이 함수를 부르는 매퍼 SQL ID 목록(역참조)도 있으면 좋다.
- 확인: `yunhee analysis function f_create_depositBook_run` 의 md에 "기간: p_std_date ~ f_today()"가 보이는 `v_CLOSE_DATE := f_today()` 줄(L32)과 INSERT 대상 `ast09_book`.

## #6 `biz-endpoints` — 요약에 `⚠없음`, 컨트롤러 이름으로도

- 현상: `yunhee biz-endpoints ast --path relate-apprs`의 표는 `PUT …/{relateApprId}/appr-id`의 검사를 `⚠없음`으로 정확히 보여 준다(의심 #107). 그런데 끝줄 요약은 `'회사'만 1 ← biz-authz 후보`뿐이라 `⚠없음`이 눈에 덜 띈다. 조회 `GET /api/v1/ast/settles/by-tr`(의심 #109)도 `⚠없음`인데 쓰기가 아니라 요약에 아예 안 잡힌다.
  또 `yunhee biz-endpoints AstRelateApprController` → "조회된 엔드포인트가 없습니다"(도움말은 "도메인명 또는 컨트롤러 .java 파일 경로"라 맞는 동작이지만 클래스 이름이 더 자연스럽다).
- 고칠 것: 끝줄을 `엔드포인트 N개 · ⚠없음 K개(쓰기 a·조회 b) · 쓰기 중 'KFS관리자' … '회사'만 …`으로. 대상에 `…Controller`(확장자 없음)를 주면 그 파일을 찾는다.
- 확인: `yunhee biz-endpoints ast` 끝줄에 `⚠없음` 건수(최소 2), `yunhee biz-endpoints AstRelateApprController` 표 3줄.
- 참고(사람 쪽): 이번 AST 작업에서 `biz-*`를 쓰지 않았다. 도메인을 시작할 때 `yunhee biz-endpoints <dom>`을 먼저 돌렸으면 #107·#109를 시험 전에 찾았다 — framework-sprt 업무분석 README에 "도메인 시작 때 `biz-endpoints`" 한 줄을 넣는 것은 그쪽에서 한다.
