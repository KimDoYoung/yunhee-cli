# 수정사항 015 — AssetERP_1 A01·A15 작업에서 나온 요청 (2026-10-07, 기준 0.1.8)

`framework-sprt/AssetERP_1`에서 실제 AssetERP 원본의 sys 화면을 변환하면서 나온 문제와 요청이다.
1부는 **고칠 것**(잘못 알려 주거나 빠뜨려서 작업을 틀리게 할 수 있음), 2부는 **새 기능**(백엔드 작업을 돕는 것)이다.
모두 **LLM 없이 결정적으로** 동작하게 한다(qwen 요약은 쓰지 않는다).

각 항목은 증상 → 원인 → 수정 → 검증 순서다. 검증의 예시 값은 asseterpdb와 `~/oms-data/src/Asset-ERP` 기준이다.

# 1부. 고칠 것

## 1. index-src: `UpdateDataModel` 저장을 "SQL 없음(-)"으로 보여 준다 — 가장 중요

**증상**
`docs/as-is/src/sys/screens/Sys01_Tab_Company.md` 서비스 표:
```
| `sys.Sys01_Company.update` | Sys01_Edit_Company:228, … | [`Sys01_Company.java:165`] | - |
| `sys.Sys01_Company.delete` | Sys01_Tab_Company:260     | [`Sys01_Company.java:189`] | - |
```
SQL 칸이 `-`라서 "저장은 SQL이 없다"로 읽힌다. 실제로는:
- `UpdateDataModel.updateModel(sqlSession, list, "sys01_company", result)`가 **DB 컬럼 메타로 동적 INSERT/UPDATE**를 만들고, 행마다 `sys01_company.selectById`로 다시 읽는다.
- 게다가 `UpdateDataModel.java` L92 `if ("sys01_company".equals(tableName))` 안에서 **회사 초기화 13단계**(15개 테이블 INSERT + `call dcr01_import_from_admin(?)`)를 한다.
  색인만 보면 이 부수 효과를 전혀 알 수 없다. 이번에는 원본을 직접 읽어서 찾았다.
- 원본 서버 클래스 **425개**가 `UpdateDataModel`을 쓴다. 저장·삭제 서비스 대부분이 같은 문제다.

**원인**
`tools/as_is/src_indexer.py`가 서버 메서드 본문에서 `sqlSession.selectList/insert/update("ns.id")` 문자열만 SQL로 모은다. `UpdateDataModel` 호출과 그 클래스 안의 테이블별 분기는 따라가지 않는다.

**수정**
1. 서버 메서드에서 `UpdateDataModel` 호출을 찾는다.
   - `new UpdateDataModel<…>()` 변수의 `.updateModel(sqlSession, <list>, <table>, result)` → 동적 INSERT/UPDATE
   - `.deleteModel(sqlSession, <list>, <table>, result)` → 동적 DELETE
   - `<table>`은 문자열 리터럴이거나 필드(`private String mapperName = "sys01_company";`)다. 필드면 값으로 바꾼다.
   - `this.mapperName + ".x"`처럼 이어 붙인 것도 같은 방법으로 푼다(이미 하고 있으면 같은 함수를 쓴다).
2. SQL 칸에 다음처럼 적는다.
   ```
   `UpdateDataModel(sys01_company)` 동적 INSERT/UPDATE → [`sys01_company.selectById`](…) ; 부수 효과: 아래 "저장 시 부수 효과"
   ```
   테이블 칸에도 그 테이블을 넣는다.
3. `server/utils/db/UpdateDataModel.java`를 한 번 파싱한다.
   - `if ("<table>".equals(tableName)) { … }` 블록마다 안의 `sqlSession.insert/update/selectOne("ns.id")`와 `prepareStatement("call <proc>(?)")`를 **나오는 순서대로** 모은다.
   - 주석 처리된 줄(`//`)은 뺀다.
   - 그 테이블을 `UpdateDataModel`로 저장하는 화면 파일에 절을 하나 더 만든다.
     ```markdown
     ## 저장 시 부수 효과 (UpdateDataModel)
     `sys01_company`를 새로 INSERT하면 (UpdateDataModel.java L92-224) 이어서:
     1. `dbConfig.getSeq` → `org01_code.insertOrg01Code` (L106)
     2. `dbConfig.getSeq` → `org02_info.insertOrg02Info` (L123)
     3. `sys09_code.insertFromSys09` (L129)
     4. `call dcr01_import_from_admin(?)` (L152, DB 프로시저 → [db/functions/dcr01_import_from_admin.md])
     5. `ast02_detail.insertFromAst02` (L162)
     … (pay04_formula.insertFromAdmin, ics02_manager.insertFromIcs02, act01_account_code.insertFromAct01,
        ics30_compliance.insertFormIcs30, ics33_compliance_answer.insertFormIcs30, bbs12_application_form.insertFormBbs12,
        pay51_expense_form.insertFormPay51, com11_form_mapping_multi.insertFormCom11)
     ```
     각 SQL ID는 다른 SQL처럼 SQL 색인 링크와 테이블을 붙인다.
4. 같은 SQL ID가 매퍼 두 곳에 있으면 표시한다(예: `pay04_formula`는 `pay04_formula.xml`과 `pay04_formula_20230620.xml`이 namespace가 같다). 이때 "같은 namespace 매퍼 2개" 경고를 SQL 색인에 남긴다.

**검증**
- `yunhee index-src ~/oms-data/src/Asset-ERP -t /tmp/idx` 후 다음을 확인한다.
  - `/tmp/idx/sys/screens/Sys01_Tab_Company.md`의 `sys.Sys01_Company.update` 줄 SQL 칸에 `UpdateDataModel(sys01_company)`가 있다.
  - "저장 시 부수 효과" 절에 위 13개(+getSeq 2개)가 원본 순서대로 있다.
  - `Sys04_Tab_Role.md`의 `sys.Sys04_Role.update`·`delete`에 `UpdateDataModel(sys04_role)`가 있다. 부수 효과 절은 없다(분기 없음).
- 테스트: `UpdateDataModel` 리터럴 / 필드 / 이어 붙이기 세 가지 형태의 작은 Java 예제.

## 2. events / index-src Grid Spec: SQL이 계산한 컬럼을 `⚠DB없음`으로 뺀다

**증상** (`Sys01_Tab_Company.md` Grid Spec)
```
// ⚠DB없음 L215 leaveMonthName 80 "휴가결산<br>(월)" (sys01_leave_month_nm 컬럼 없음)
// ⚠DB없음 L204 fullAddress 350 "주소" (sys01_full_address 컬럼 없음)
```
같은 식으로 6개가 더 있다(dcrNumberingName, icsCheckCycleName, icsComplyCycleName, taxTypeName, accountCloseMonthName, ownerCapitalApplyName).
그런데 이 컬럼들은 `sys01_company.selectByName`이 계산해서 내보낸다.
```sql
f_cdnm('MonthsCode', sys01_leave_month_cd, …) AS sys01_leave_month_nm
CONCAT(sys01_zip_addr, ' '||sys01_zip_detail)  AS sys01_full_address
```
AS-IS 화면에 실제로 보이는 컬럼이다. 표시를 믿고 뺐다면 화면에서 컬럼 8개가 빠졌을 것이다.

**원인**
`tools/as_is/events.py` L926-935는 resultMap의 column이 **테이블 컬럼(table_cols)에 있는지만** 본다. 매퍼 SELECT의 별칭은 보지 않는다.

**수정**
1. 그 resultMap을 쓰는 매퍼 XML의 모든 `<select>`에서 `AS <별칭>`을 모은다(대소문자 무시, `<include>` 펼친 뒤).
   이것을 `alias_cols`로 만든다.
2. 판정을 셋으로 나눈다.
   - 테이블 컬럼에 있음 → 지금처럼 `gb.…(…)`
   - 테이블에는 없고 `alias_cols`에 있음 → `gb.…(…)`로 내보내고 주석으로 표시: `// L215 SQL 계산 컬럼(selectByName: f_cdnm …)`. 식 앞 40자 정도를 붙이면 좋다.
   - 둘 다 없음 → 지금의 `⚠DB없음`
3. 화면이 쓰는 조회 SQL ID를 알면(서비스 표의 SQL), 그 SELECT의 별칭만 본다. 모르면 매퍼 전체에서 본다.
4. index-src의 `## UI` 요약 줄(`- leaveMonthName 80 …`)에도 같은 판정을 쓴다.

**검증**
- `yunhee events Sys01_Tab_Company`의 Grid Spec에서 위 8개가 `gb.text(…)`로 나오고, `⚠DB없음`은 0개다.
- `Sys01_TabPage_Info01`의 `erpProductName`(`f_cdnm('ErpProductCode', …) AS sys01_erp_product_nm`)도 계산 컬럼으로 나온다.
- `Sys54_Lookup_SpecificMenuHistory`의 `fileName`(sys54_file_nm)은 정말 없는 컬럼인지 확인한다. 별칭에도 없으면 `⚠DB없음`이 그대로 남아야 한다.

## 3. index-src: `getSeq` 서비스가 "(없음)"

**증상**
```
| `getSeq` | Sys01_Edit_Company:86 | **(없음)** | - |
```
**원인**
클라이언트 `new ServiceRequest("getSeq")`는 서버 클래스가 아니라 디스패처 특수 경로다. 실제로는 `server/utils/db/mapper/DBConfig.xml` L13 `<select id="getSeq">`를 쓴다. `client/service/GridInsertRow.java`, `DBUtil.java`도 같은 것을 쓴다.
**수정**
서비스 이름이 `getSeq`이면 서버 칸을 `(공통) 채번`으로, SQL 칸을 `dbConfig.getSeq`(→ `f_create_seq()`)로 적는다. 디스패처에 다른 특수 이름이 있으면 같이 처리한다.
**검증**
위 줄의 서버 칸이 `(공통) 채번`, SQL 칸이 `dbConfig.getSeq`다.

## 4. api: 작업 폴더마다 주소가 다르다 / `-c`만 주면 회사가 안 바뀐다

**증상**
- `.env.local`의 `YUNHEE_API_BASE_URL`이 `http://localhost:8082/OMS` 하나뿐이다. AssetERP_1에서는 매번 `--base http://localhost:8082/AssetERP_1`을 줘야 한다. 빠뜨리면 **OMS를 시험하고도 성공처럼 보인다**(두 앱의 API가 같아서).
- `yunhee api GET /api/v1/sys/roles --base … -c kfstest`는 admin 회사 8행을 돌려준다(kfstest 11행이어야 함). `-t admin -c kfstest`를 같이 줘야 맞다.
  Host가 `localhost`라서 서버가 admin 테넌트 로그인으로 보지 않고 `companyCode`를 무시하기 때문이다.

**수정**
1. 작업 폴더 설정 파일을 둔다. 현재 폴더부터 위로 `.yunhee.toml`을 찾고, 있으면 `.env.local`보다 먼저 쓴다.
   ```toml
   # AssetERP_1/.yunhee.toml
   [api]
   base = "http://localhost:8082/AssetERP_1"
   tenant = "admin"          # 기본 테넌트
   ```
   `yunhee config`는 어느 파일에서 읽은 값인지 함께 보여 준다.
2. `-c/--company`를 주고 `-t`가 없으면 기본 테넌트(`.yunhee.toml` 또는 `YUNHEE_TEST_COMPANY`)를 자동으로 붙인다. 테넌트가 정해지지 않으면 "회사 선택 로그인은 admin 테넌트에서만 됩니다: -t admin" 경고를 낸다.
3. 응답 요약 첫 줄에 실제로 부른 base와 테넌트를 적는다: `[AssetERP_1 · tenant=admin · company=kfstest]`.

**검증**
- `AssetERP_1/` 안에서 `yunhee api GET /api/v1/sys/roles`(옵션 없음) → 8행, 첫 줄에 `AssetERP_1`이 보인다.
- `yunhee api GET /api/v1/sys/roles -c kfstest` → 11행.
- 저장소 루트(`.yunhee.toml` 없음)에서는 지금처럼 OMS를 부른다.

# 2부. 새 기능 — 백엔드 작업 돕기

화면 하나를 변환할 때 Claude가 손으로 하는 일 중 **기계적인데 토큰이 많이 드는 것**이다. A15 1단계는 레코드 DTO 32필드, SELECT 별칭 32줄, INSERT·초기화 SQL 15개를 손으로 옮겨 적었다. 입력(읽기)도 출력(쓰기)도 많았다.
우선순위 순서다.

## 5. `yunhee sql` — 읽기 전용 조회와 롤백 시험 (우선 1)

지금은 DB 데이터 확인(행 수 비교, 중복 검사)과 "저장 SQL이 이 DB에서 도는지"를 psql로 직접 한다.
```bash
yunhee sql "select count(*) from sys01_company where coalesce(sys01_use_yn,'true')='true'"
#  → rows=1  count=12          (최대 N행만 표 출력, 기본 5행, --limit)
yunhee sql -f init.sql --rollback
#  → BEGIN … ROLLBACK. 문장마다 "INSERT 208", "CALL ok" 한 줄. 마지막 SELECT 결과 표. 남은 변경 없음
```
- 기본은 `BEGIN READ ONLY` + `statement_timeout`(예: 10초)으로 연다.
- `--rollback`이면 쓰기를 허용하되 **반드시 ROLLBACK**한다. 파일 안의 `COMMIT`·`END`·DDL(`CREATE/ALTER/DROP/TRUNCATE`)은 실행 전에 거부한다.
- 접속은 `LOCAL_DB`(yunhee config의 Local DB). 비밀번호는 출력하지 않는다.
- psql `\set`·`\gset` 정도의 변수 하나는 지원하면 좋다(`SELECT f_create_seq() AS cid \gset` → `:cid`). 어려우면 `--var cid="select f_create_seq()"`.

## 6. `yunhee sql-check --tobe <mapper 폴더>` — TOBE 매퍼를 서버 띄우기 전에 검사 (우선 2)

TOBE 매퍼 XML(`backend/src/main/resources/mapper/*.xml`)을 asseterpdb에서 EXPLAIN한다. 지금 `sql_checker.py`가 AS-IS 매퍼에 하는 것과 같다.
컬럼 오타, 없는 함수, 별칭 실수를 **컴파일·배포·API 호출 없이** 바로 잡는다.
```bash
yunhee sql-check --tobe AssetERP_1/backend/src/main/resources/mapper
#  → SysCompanyMapper.searchCompanies ✅ / insertCompany ✅ / insertOrgCode ❌ column "org01_open_dt" does not exist (L98)
```
- namespace는 Java 인터페이스 FQN이다. `#{x}`는 null 또는 타입에 맞는 더미 값으로 바꾼다. `<if>`·`<foreach>`는 지금 펼치기 규칙을 쓴다.
- INSERT·UPDATE·DELETE·CALL도 EXPLAIN만 하고 실행은 하지 않는다. CALL은 EXPLAIN이 안 되므로 `pg_proc`에 그 프로시저와 인자 수가 있는지만 본다.
- 추가: `resultType`이 record면 SELECT 별칭(snake → camel)과 record 필드 이름을 비교한다. 빠진 필드나 남는 별칭을 경고한다. map-underscore-to-camel-case 기준이다.

## 7. `yunhee port-sql <ns.sqlId>` — AS-IS SQL을 TOBE 매퍼 조각과 레코드 DTO로 (우선 3)

```bash
yunhee port-sql sys01_company.selectByName --cols companyNm,locNm,useYn,leaveMonthNm,noticeDate
```
출력은 두 덩어리다(복사해서 쓴다).
1. **매퍼 조각**
   - `<include>`를 펼친다.
   - `SELECT *`이면 resultMap 컬럼으로 SELECT 목록을 만든다. `--cols`를 주면 화면 컬럼만 넣는다.
   - 컬럼마다 `AS snake_별칭`을 붙인다. 접두어 `sys01_`은 뺀다. 이 규칙은 색인 Grid Spec의 TOBE 프로퍼티 이름 규칙과 같게 한다.
   - 계산 식(`f_cdnm(...) AS sys01_leave_month_nm`)은 식을 그대로 두고 별칭만 바꾼다.
   - `#{x}`, `${x}`, `<choose>`는 그대로 두고 파라미터 목록을 주석으로 단다.
   - `--getter-defaults`: AS-IS 모델 getter가 null일 때 돌려주는 값을 `COALESCE(컬럼, 값)`으로 넣는다. 예: `getUseYn()` → false.
     (`client/vi/{dom}/model/*Model.java`의 `if(x == null) { return <값>; }` 패턴)
2. **record DTO**: 필드 이름은 camelCase, 타입은 DB 타입에서 정한다.

   | DB 타입 | Java 타입 |
   |:---|:---|
   | numeric (id·정수 컬럼) | Long |
   | numeric (소수가 있을 수 있는 컬럼) | BigDecimal |
   | varchar / text | String |
   | timestamp | LocalDateTime |
   | date | LocalDate |

   계산 컬럼은 식의 결과 타입으로 정하고, 모르면 String으로 한다.

**검증**
- `port-sql sys04_role.selectByName` 결과가 `AssetERP_1/backend/src/main/resources/mapper/SysRoleMapper.xml`의 `roleColumns`, `RoleRes` 필드와 같다(f_get_company_nm 포함).

## 8. `yunhee port-save <table> --cols a,b,c [--company-col x]` — UpdateDataModel 대신 쓸 명시 SQL (우선 4)

AS-IS 저장이 `UpdateDataModel`이면 TOBE는 명시 INSERT/UPDATE/DELETE를 쓴다(05 §6 규칙).
```bash
yunhee port-save sys04_role --cols role_nm,seq,note --company-col sys04_company_id
```
출력:
- `INSERT`: id + company + cols
- `UPDATE`: cols만 SET, WHERE에 id와 company 조건
- `DELETE`: `<foreach>` ID 목록 + company 조건
- `selectNextId`(`SELECT f_create_seq()`)
- 1번의 "저장 시 부수 효과"가 있는 테이블이면 그 SQL들을 원본 순서대로 매퍼 조각으로 덧붙인다. 각 원본 SQL을 펼친 것을 그대로 쓰고, `${companyId}` → `#{companyId}`로 바꾼다.

## 9. `yunhee compare` — 조회 API와 AS-IS SQL 행 수 비교 (우선 5, 06 확인 항목 3)
```bash
yunhee compare GET /api/v1/sys/companies -p useYn=true --sql sys01_company.selectByName --param companyName=% --param useYn=true
#  → API rows=12, SQL rows=12 ✅  fields ⊇ grid cols ✅
```
- api 쪽은 4번 설정(base·테넌트·회사)을 따른다. SQL 쪽은 5번의 읽기 전용 실행을 쓴다.
- 서버가 세션에서 넣는 값(회사 등)은 `--param companyId=28000`처럼 직접 준다.
