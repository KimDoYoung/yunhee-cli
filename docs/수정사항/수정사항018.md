# 수정사항 018 — 분석 명령 하나로 묶기(`yunhee analysis`)와 MyBatis 펼치기 통합 (2026-10-08)

`framework-sprt/AssetERP_1`에서 C01(사원정보 관리 `Emp00_Tab_TransInfo` 1단계, emp·org 도메인 처음)과 A03(권한그룹별 사용자 맵핑 `Sys05_Tab_UserRole`)을 한 세션에서 0.2.1로 했다.
`run`·`sql`·`sql-check --tobe`·`api`·`table`은 잘 동작했다. 하지만 세션 토큰의 약 32%(Bash 출력 172k + 파일 읽기 147k / 437k)가 **같은 모양의 `sed`·`grep`·`cat`** 이었다.
그 반복은 대부분 yunhee가 이미 파싱하는 정보(색인의 메서드 줄 범위, 매퍼 statement, resultMap, GridBuilder 호출)를 원본에서 다시 찾은 것이다.

이 문서는 두 가지를 요청한다.
- **A. 분석 명령을 `yunhee analysis <type> <대상> [-o 형식]` 하나로 묶는다.** 새 분석은 명령이 아니라 유형(type)으로 늘린다.
- **B. MyBatis SQL 펼치기 코드 3벌을 하나로 합친다.** 지금 `port-sql`·`compare`가 다른 namespace의 `<include>`를 못 펼쳐 실패한다(버그). `analysis sql`도 이것을 쓴다.

항목마다 증상(이번 세션에서 실제로 한 일) → 원인 → 수정 → 검증 순서다. 검증 값은 asseterpdb와 `~/oms-data/src/Asset-ERP`(최신 pull 아님)에서 2026-10-08에 손으로 확인한 값이다.

## A. `yunhee analysis` — 분석 명령 하나

### A-0. 공통 규칙

```
yunhee analysis <type> <대상> [옵션…] [-o md|json|code|sql] [--limit N]
yunhee analysis --list              # 유형 목록: 받는 대상, 출력 형식, 예
yunhee analysis <type> --help       # 유형별 옵션
```

1. **유형 = 파이썬 모듈 하나.** `src/yunhee/tools/analysis/<type>.py`에 아래 셋을 둔다. `cli.py`에는 `analysis` 명령 하나만 등록하고, 유형은 레지스트리(`analysis/__init__.py`의 dict)에서 찾는다.
   - `resolve(target, opts) -> 대상 객체`
   - `render(obj, fmt) -> str`
   - `FORMATS = ("md", …)`
2. **기본 출력은 요약 md.** 원문은 `-o code`·`-o sql`처럼 직접 고를 때만 낸다. 이번 세션의 낭비는 대부분 "원문을 넉넉히 받은 것"이었다.
3. **대상이 모호하면 고르게 한다.** 같은 이름이 여럿이면(오버로드, 클라이언트·서버 같은 클래스 이름, 여러 도메인) 후보를 `번호 · 파일:줄 · 시그니처`로 보여 주고 Exit 2.
   - 다시 부를 때는 `#번호`(예: `Org00_Lookup_SelectSingle.open#3`) 또는 `--server`/`--client`로 고른다.
4. **AS-IS 위치는 색인 데이터로 찾는다.** 매번 원본 3,000개 파일을 파싱하지 않는다 → A-9.
5. **AS-IS 소스 루트·색인 폴더**는 `port-sql`처럼 `-s/--src`, `--src-index`로 받는다. 없으면 `.yunhee.toml [as_is] src, src_index`, 그다음 지금의 자동 탐지(`find_as_is_dir`)를 쓴다.
   - AssetERP_1은 색인이 `AssetERP_1/docs/as-is/src`라서 지정할 수 있어야 한다.
6. **기존 명령은 남긴다.** `table`·`outline`·`events`는 안에서 해당 유형을 부르게 바꿔도 되지만 이름은 지금처럼 둔다. 문서·agent-guide에는 `analysis`를 먼저 안내한다.
   - 생성·실행 명령(`port-sql`·`port-save`·`sql`·`compare`·`api`·`run`·`sql-check`)은 분석이 아니므로 따로 둔다.

### A-1. `method` — AS-IS 메서드 본문 (클라이언트·서버)

**이번 세션에서 한 일 (20회 이상)**
```bash

sed -n 395,520p …/server/emp/Emp00_TransInfo.java               # 서버 메서드는 끝 줄을 몰라 넉넉히(실제 L395-492)
sed -n 92,237p  …/client/vi/sys/Sys05_Page_UserRole.java        # 메서드 4개를 한 번에
```

**제안**
```
yunhee analysis method <클래스>.<메서드>[#n] [--server|--client] [-o md|code]
```
- **대상 찾기**
  - 클라이언트 클래스: `src_indexer.parse_client`의 `ClientClass`
  - 서버 클래스: `parse_server`의 `ServerClass`/`ServerMethod`
  - 메서드 줄 범위: `find_methods`(시작·끝 줄을 이미 계산함)
- **`-o code`**: 본문 원문. 첫 줄에 `파일:시작-끝`.
- **`-o md`(기본)**: 처리 순서 요약. 그대로 옮겨야 하는 것만 원문으로 뽑는다.
  - 부르는 서비스 문자열(`"emp.Emp03_Trans.update"`)과 `addParam` 키·값식
  - 메시지 문자열(`new SimpleMessage("…")`, `HtmlMessageBox("…","…")`, `setEmptyText`)
  - 조건 분기 줄(`if (…) {` / `return`)
  - 부르는 다른 메서드 이름과 줄
  - 서버 메서드는 `sqlSession.xxx("ns.id")`, `UpdateDataModel(테이블)`, `getSeq`, `commit()`
- **`--with-events`**: 이 메서드를 부르는 이벤트(E-id, 핸들러 줄)도 함께 낸다. 색인 `#### 이벤트`와 같은 출처다.

### A-2. `sql` — 매퍼 statement 하나 (펼치기 포함)

**이번 세션에서 한 일 (10회 이상 + 펼치기 스크립트 2개)**
```bash
grep -n 'id="selectByText"' -A45 …/emp/mapper/emp03_trans.xml       # 끝 줄을 몰라 넉넉히
sed -n 1372,1546p …/utils/db/mapper/Common.xml                      # include 대상 조각을 따로
python3 asis_sql.py 100 > asis_100.sql; yunhee sql -f asis_100.sql  # include·bind·choose를 손으로 펼쳐 AS-IS 행 수 세기
```

**제안**
```
yunhee analysis sql <ns.id> [--param k=v …] [-o md|sql|code]
```
- **`-o code`**: statement 원문(`<select …>`~`</select>`) + `파일:줄`. include는 펼치지 않고, 대상 조각의 `파일:줄`을 주석으로 붙인다.
- **`-o sql`**: B의 공통 렌더러로 펼친 **실행 가능한 SQL**. `--param`으로 받은 값을 넣는다.
  - 값이 없는 `#{x}`는 NULL로 넣고 stderr에 `⚠ 값 없음: x`를 낸다.
  - 결과를 `yunhee sql -f`에 바로 넣을 수 있어야 한다.
- **`-o md`(기본)**: 요약.
  - 파라미터 목록(`#{}`·`${}`·`<bind>`·test 식에 나온 이름)
  - include 목록(`파일:줄`)
  - choose/if 분기와 각 test 식
  - 테이블·DB 함수
  - 최상위 SELECT 별칭 목록
  - ORDER BY
- `--count`: `-o sql` 결과를 `SELECT count(*) FROM (…) z`로 감싸 바로 실행하고 행 수만 낸다. `yunhee sql`과 같은 읽기 전용 경로를 쓴다.

**검증 (asseterpdb, kfstest=28000)**
| 명령 | 기대 |
|:---|:---|
| `sql emp00_trans_info.selectByText --param companyId=28000 --param searchText=%% --param transCode=100 --param transDate=2026-10-08 --param isSeparateAddTitle=true --count` | 48 |
| 같은 명령, `transCode=000` / `800` / `900` | 66 / 3 / 15 |
| `sql emp03_trans.selectByText --param companyId=28000 --param searchText=%% --param transDate=2026-10-08 --count` (isSeparateAddTitle 없음 → false 분기) | 52 |
| `sql sys05_user_role.selectByRoleId --param roleId=28120 --count` | 8 |
| `sql org00_org_info.selectByKorName --param companyId=28000 --param korName=% --param baseDate=2026-10-08 --count` | 24 |
| `sql emp00_trans_info.selectByText -o md` | include 2개: `common.emp00_trans_info`(Common.xml L1372), `common.org00_org_info`(L1511). bind 3개(`emp00CompanyId`·`org00CompanyId`·`emp00TransDateString` ← `companyId`·`companyId`·`transDate`). 본문 choose 3개(`isSeparateAddTitle == true`, `orgCodeId != null`, ORDER BY의 `transCode == '900'`)와 include별 choose 목록 |

### A-6. `ui` — UI 대조표 (단계별)

**이번 세션에서 한 일**: `tools/ui-count.sh`로 26개 클래스를 센 뒤, 1단계에서 한 것과 남은 것의 합계를 손으로 계산했다. 한 번 틀렸다(남은 버튼 58 → 실제 62).

**제안**
```
yunhee analysis ui <화면클래스> [--done <클래스,…>] [--later "2단계=<클래스,…>"] [--tobe <TOBE 파일·폴더>] [-o md]
```
- 클래스별 `버튼 | 이벤트(└ 하위 포함) | 그리드` 표와 그룹(이번·다음 단계·남은 것) 합계.
- `--tobe`를 주면 TOBE 파일에서 셈해 `AS-IS/TOBE` 칸을 채운다.
  - `// [E3] …`, `// [E3 생략] …` 주석 수와 `<Button` 수, 그리드 컴포넌트 수

## B. MyBatis 펼치기 통합 — `port-sql`·`compare` 버그 수정

### 증상
```bash
yunhee port-sql emp00_trans_info.selectByText -s ~/oms-data/src/Asset-ERP --cols …
#  → <select id="selectByText" resultType="…LicenseRes">
#       SELECT <include refid="licenseColumns"/> FROM emp08_license WHERE emp08_person_id = emp01_person_id …
#     record LicenseRes(String retireDate)
# (실제 SELECT 목록 대신 emp08_license 서브쿼리를 메인 쿼리로 잡았다)

yunhee compare GET /api/v1/emp/trans-infos … --sql emp00_trans_info.selectByText --param …
#  → [ERROR] SQL 실행 실패: syntax error at or near ","   LINE 1: , org00 as ()
```
- `compare`는 같은 이유로 `emp03_trans.selectByText`(include `common.org00_org_info_with`)도 실패했다. 손으로 펼친 SQL로 대신 셌다(C01 48/66/3/15, A03 사원찾기 52).

### 원인
yunhee 안에 MyBatis 렌더러가 **세 벌** 있고, 셋 다 일부만 한다.

| 위치 | 다른 namespace include | `<bind>` | choose·if를 파라미터로 판정 | 쓰는 곳 |
|:---|:---|:---|:---|:---|
| `tools/as_is/sql_porter.py` `expand_includes` L244 | ❌ 같은 파일 `<sql>`만. `common.x`는 `x`로 같은 파일에서 찾고 없으면 `""` | ❌ | ❌(태그 그대로 남김) | port-sql, port-save |
| `tools/comparator.py` `_render_node_with_params` L68 | ❌ 같은 파일만, 없으면 `""` | ❌ → `emp00CompanyId != null`이 거짓이 되어 **회사 조건이 빠짐** | ✅(단, `x == true` 같은 따옴표 없는 비교는 "변수 있음"으로 처리) | compare |
| `tools/as_is/sql_checker.py` `render` L98 | ✅ `load_statements`로 전체 매퍼 | 무시 | ❌ 첫 when만(EXPLAIN용) | sql-check |

- `port-sql`이 엉뚱한 SELECT를 잡은 이유: include가 `""`가 되어 첫 `SELECT … FROM`이 `CASE WHEN (SELECT COUNT(*) FROM emp08_license …)` 서브쿼리 안에서 잡혔다(`port_sql` L307 정규식이 최상위 깊이를 보지 않음).
- `compare`가 `, org00 as ()`가 된 이유: `<include refid="common.emp00_trans_info"/>`(WITH 절 전체)와 `common.org00_org_info`가 둘 다 `""`.

### 수정
1. **공통 렌더러 `tools/as_is/mybatis_render.py`** 하나로 합친다.
   - 노드 트리: `sql_checker.parse_xml`·`Node`
   - statement·조각 찾기: `sql_checker.load_statements`를 확장해 `<sql>` 조각도 `ns.id`로 담는다
   - 파라미터 판정: `comparator._eval_test_condition`
   - 함수 하나: `render(key, params, mode)`
     - `mode="explain"`: 지금 sql-check 동작(첫 when, 값은 NULL)
     - `mode="params"`: 파라미터로 판정하고 값을 넣는다
     - `mode="structure"`: 태그를 남기고 include만 펼친다(port-sql의 `<choose>` 보존용)
2. **`<bind name="a" value="b"/>`**: `value`가 파라미터 이름이면 `params[a] = params[b]`. OGNL 식(`'%' + x + '%'`)은 `+` 문자열 연결만 지원한다. 그 밖의 식은 경고하고 건너뛴다.
3. **test 식**: `x == true`/`x == false`(따옴표 없는 boolean), `x != null and y == 'a'`(and/or), `x.size() > 0`(리스트 파라미터)을 지원한다. 모르는 식은 `⚠ 판정 못한 test: …`를 내고 거짓으로 둔다(지금은 "변수 있음"이면 참이라 조용히 틀린다).
4. **`port-sql`**:
   - 렌더러를 `mode="structure"`로 써서 include를 펼친 뒤 SELECT 목록을 최상위 깊이에서 찾는다(`sql_checker._depth0_matches` 재사용).
   - 최상위가 `WITH …` CTE면 마지막 본 SELECT를 대상으로 하고, CTE는 매퍼 조각에 그대로 둔다.
   - 그래도 SELECT 목록을 못 찾으면 **엉뚱한 조각을 내지 말고** 실패로 끝내며 "include·CTE를 펼친 원문은 `yunhee analysis sql <id> -o sql`"을 안내한다.
5. **`compare`**: 렌더러를 `mode="params"`로 쓴다. `--param`에 없는 `#{x}`가 남으면 실행 전에 `⚠ 값 없음: x`를 낸다.
6. `port-save`의 부수 효과 SQL 펼치기(L687 `sequenceNextVal` 치환 포함)도 같은 렌더러를 쓴다.

### 검증
- `compare GET /api/v1/emp/trans-infos -p transCode=100 -p transDate=2026-10-08 -c kfstest --sql emp00_trans_info.selectByText --param companyId=28000 --param searchText=%% --param transCode=100 --param transDate=2026-10-08 --param isSeparateAddTitle=true` → `API rows=48, SQL rows=48 ✅` (`transCode` 000/800/900 → 66/3/15)
- `port-sql emp00_trans_info.selectByText` → SELECT 별칭이 `trans.*`·`emp01_person.*`·… 최상위 항목이고, `LicenseRes`가 나오지 않는다. 못 하면 실패 + 안내(엉뚱한 조각 0건)
- 기존 테스트 유지: `tests/test_sql_porter.py`, `test_comparator.py`, `test_as_is.py`. 그리고 `sql-check` 전체 결과(통과 2901 / 스키마 차이 77 / DB 환경 차이 149 / 기타 50)가 같다.
- 새 테스트: `<bind>`, 다른 namespace include, `== true`, and/or 조합, 모르는 test 식 경고

## 참고: 이번 세션에서 잘 동작한 것
- **`sql-check --tobe`**: 새 매퍼 5개(EmpTransInfo·EmpPerson·EmpTrans·OrgInfo·SysUserRole)를 컴파일 전에 확인했다. 매퍼 SQL 오류로 다시 빌드한 적 0회.
- **`sql`**: 프로토타입 SQL, 코드값·조직·FK·유일 인덱스 확인을 psql 없이 했다. `-f` 파일 실행이 펼친 AS-IS SQL 대조에 유용했다.
- **`run`**: 빌드·테스트·배포·화면 스크립트 모두. 실패 요약만으로 원인을 찾았다(import 줄바꿈, 트랜잭션 abort, useRef 타입).
- **`table`**: 유일 인덱스(사번, 발령, 사원·권한그룹)를 미리 보고 중복 검사를 설계에 넣었다.
- **`compare`**: include가 없는 SQL(`sys05_user_role.selectByRoleId`)은 행 수 8 = 8을 한 줄로 확인했다.
