# 수정사항 037 — AssetERP E07 변환에서 확인한 분석·이식 도구의 빈틈 (대상 0.4.1)

- 작성: 2026-10-17, yunhee **0.4.1** 기준. 반영하면 **0.4.2**(036과 같은 릴리스에 묶어도 된다).
- 계기: AssetERP E07(일일점검내역 관리, `Chk02_Tab_DailyListAdmin`, 클래스 4, 이벤트 26) 변환 중 `analysis model --sql`·`port-sql`·`analysis method`에서 **원본·DB를 따로 확인해야 했던 것**. 새 명령은 없다. 전부 읽기 전용 분석·이식 출력의 보강이다.

## 1. `analysis model --sql`의 `SQL 존재 ✅(테이블.*)`가 실제 열 존재를 확인하지 않음 (037-1)

**재현**
```
yunhee analysis model Chk02_DailyListModel --sql chk02_daily_list.selectByAdmin
```
- `reason | chk02_reason | ✅(chk02_daily_list.*)` 로 나온다. SQL이 `SELECT chk02_daily_list.*`라서 ✅를 주는데, **`chk02_daily_list` 테이블에 `chk02_reason` 열이 없다**(`yunhee table chk02_daily_list`로 확인). 그리드의 `설명` 열이 이 속성을 보여 줘서 원본에서도 항상 빈칸인 버그인데, 도구는 ✅라고 말해 놓쳤다. `writeGroupName`·`answerCode` 등 같은 방식의 ✅도 실제로는 없는 열이다.

**수정**: `테이블.*`·`*`로 ✅를 줄 때 DB 색인(`docs/as-is/db`)에서 그 테이블의 열을 찾아 **없으면 `⚠ 테이블에 열 없음`**으로 구분한다. `*`가 조인으로 여러 테이블에 걸리면 FROM/JOIN 테이블 전부에서 찾는다. 계산 getter·`@Path`가 아닌 평범한 속성에서만 판정한다.

**기대 (검증 ID `037-1`)**: 위 명령에서 `reason`, `answerCode`, `confirmYn`, `note`(chk02에 없는 열) 줄이 `⚠`로 나오고 `classTreeId`·`content`·`seq`는 ✅로 남는다.

## 2. `analysis grid`가 그리드 열의 속성이 SQL·테이블에 없을 때 알려 주지 않음 (037-2)

**재현**
```
yunhee analysis grid Chk02_Tab_DailyListAdmin
```
- `reason | 설명 | addTextArea`가 그대로 표에 나온다. 위 037-1과 같은 원인으로 이 열은 항상 빈칸이다. 그리드 표에서 **그 클래스가 쓰는 조회 SQL(`analysis screen`의 서비스 표)과 모델을 이어** 열이 비는지 한눈에 보여 주면 좋다.

**수정**: `analysis grid <클래스> --check-columns`(또는 기본 켬)로 각 열의 속성이 모델 resultMap → 그 화면 조회 SQL → 테이블 열에 이어지는지 `✅ / ⚠ SQL에 없음 / ⚠ 테이블에 없음` 칸을 더한다. 화면에 조회 SQL이 둘 이상이면 `--sql <ns.id>`로 고른다.

**기대 (`037-2`)**: 위 명령에서 `설명` 열(`reason`)이 `⚠ 테이블에 없음`.

## 3. `port-sql`이 계산 getter 열(`adminYn` 등)을 `SQL 열 없음`으로만 알림 (037-3)

**재현**
```
yunhee port-sql chk02_daily_list.selectByAdmin --cols adminYn,classTreeName,content,explan,cutoff,windowNo,seq,useYn --getter-defaults --package kr.co.kfs.asseterp.biz.chk.dto
```
- `// ⚠ SQL 열 없음: adminYn`을 내고 record DTO에 `String adminYn`을 만든다. 실제로 `adminYn`은 모델 getter(`companyId == 0 || adminDailyListId != 0`)가 계산한 값이라 SQL에서 식으로 만들어야 하는데, 도구가 그 식을 알려 주지 않아 `analysis method <모델>.getAdminYn -o code`를 따로 열었다. 타입도 `Boolean`이어야 하는데 `String`으로 나온다.

**수정**: `--cols`에 계산 getter가 있으면 (a) 그 getter 본문을 주석으로 붙이고(`// getAdminYn L146-149: companyId == 0 || adminDailyListId != 0`), (b) 단순 비교식이면 SQL 별칭 후보(`(chk02_company_id = 0 OR COALESCE(chk02_admin_daily_list_id,0) <> 0) AS admin_yn`)를 제안하고, (c) record 필드를 getter 반환 타입(`Boolean`)으로 만든다.

**기대 (`037-3`)**: 위 출력의 `adminYn`이 `Boolean`이고 getter 본문 주석이 붙는다.

## 4. `analysis method`가 오버로드를 고를 때 후보 시그니처만 보여 줌 (037-4)

**재현**
```
yunhee analysis method GridInsertRow.insertRow -o code     # Exit 2, 후보 2개
```
- 후보 목록(`insertRow(Grid, GridDataModel)`, `insertRow(Grid, GridDataModel, InterfaceCallbackResult)`)이 나오고 `#번호`로 다시 불러야 한다. 이 경우 두 번째가 **첫 번째를 부르는 한 줄 위임**(`this.insertRow(grid, insertModel)`)이라 첫 번째만 보면 되는데, 두 번 호출했다(031-5에서 같은 제안이 있었음).

**수정**: 후보의 본문이 5줄 이하이면 후보 목록 아래에 **본문을 같이 보여 준다**(`-o code`일 때). 본문이 다른 오버로드를 부르는 위임이면 `→ #1 위임` 표시.

**기대 (`037-4`)**: 위 명령 출력에 후보 2개의 본문(후보 2는 `→ #1 위임`)이 함께 나오고 Exit 0.

## 5. `analysis ui --tobe`가 `[E0]` 주석 누락을 "미구현"으로만 표시 (037-5)

**재현**: TOBE 편집 창에 `// [E0] 화면 열림 …` 주석이 없으면 `이벤트 5/4 · 없음: E0(미구현)`으로 나온다. 생성자 E0은 대응 코드가 따로 없는 경우가 대부분이라(`useEffect` 초기화 등) 누락이 "미구현"인지 "주석만 빠졌는지" 구분이 안 된다. 결과는 맞게 잡았다(주석 한 줄 추가로 해결).

**수정(선택)**: `없음: E0`일 때 `E0은 생성자 이벤트 — 대응 코드 근처에 \`// [E0] …\` 주석을 달면 된다` 안내를 한 줄 붙인다.

**기대 (`037-5`)**: 안내 문구가 출력에 있다.

## 우선순위
1(037-1)이 가장 가치가 크다 — 원본 버그를 변환 단계에서 자동으로 잡는다. 2는 1의 재사용(같은 판정을 `analysis grid`에 노출). 3·4는 이식 편의, 5는 안내 문구만.
