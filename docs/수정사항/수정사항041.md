# 수정사항 041 — 매퍼 XML 정형 검사 · 기동 실패 감지 (대상 0.4.4)

- 작성: 2026-10-20, yunhee **0.4.4** 기준. 반영하면 **0.4.5**.
- 계기: AssetERP G13 작업 중 `CmpMailRoleMapper.xml`에 `<=`를 이스케이프 없이 써서(XML에서는 `&lt;=`) 첫 배포가 **앱 기동 실패**했다. 그런데 `sql-check`는 ✅, `yunhee run "./deploy.sh"`도 ✅, `log errors --since-deploy`도 처음엔 "기록 없음"이라 기동 실패를 `log tail --level WARN`의 `Application run failed`를 보고서야 알았다(재배포 1회, 약 10분 손실).

## 1. `sql-check`에 XML well-formed 검사 추가 (1순위)

**증상 및 재현**
```bash
# 매퍼 안에 AND x.emp03_trans_date <= f_sysdate()  (날것의 <=)
yunhee sql-check --tobe backend/src/main/resources/mapper --summary
→ CmpMailRoleMapper: ✅ 6 / ❌ 0     # 실제로는 XML 파싱 불가
```
- 0.4.3 평가(수정사항 G01 #1)에서 "매퍼 XML 정형은 안 본다"고 한계로만 적혀 있었으나, 실제로는 앱 전체가 안 뜨는 치명 오류로 이어진다.

**수정**
1. `sql-check --tobe`가 각 매퍼 XML을 먼저 XML 파서(`xml.etree`/`lxml`)로 열어 보고, 실패하면 해당 매퍼를 `❌ XML 오류: <파일>:<줄>:<열> <메시지>`로 표시하고 statement 검사는 건너뛴다(요약에도 `XML ❌ n`을 별도 열로 낸다).
2. 메시지에 흔한 원인 힌트를 붙인다: 본문의 `<`, `<=`, `<>`, `&` → `&lt;`, `&lt;=`, `&lt;&gt;`, `&amp;` 또는 `<![CDATA[ … ]]>`.
3. DOCTYPE의 외부 DTD(mybatis-3-mapper.dtd)는 네트워크로 받지 않는다(검사는 well-formed까지만).

**확인 (합격 기준)**
- 위 재현 매퍼에서 `sql-check`가 ❌와 줄·열 번호를 낸다. 정상 매퍼는 변화 없다.
- `sql-check --changed`도 같은 검사를 한다.

## 2. `log errors --since-deploy`가 기동 실패를 맨 위에 경고

**증상 및 재현**
- 앱이 `Application run failed`로 죽은 배포 직후 `yunhee log errors --since-deploy`를 실행하면, "배포 시각" 헤더가 기동 성공 기록(`Started … in N seconds`)을 못 찾아 이전 배포 시각이 잡히거나 `WARN/ERROR 선택 범위: 0줄`로 나온다. 실제 ERROR(`SpringApplication - Application run failed`, `UnsatisfiedDependencyException`, `XmlBeanDefinitionStoreException` 등)는 `log tail --since 15m --level WARN`에서만 보인다.

**수정**
1. `--since-deploy` 범위 계산 시 마지막 `./deploy.sh` 실행 이후 로그에서 `Application run failed`·`Error creating bean`·`Context initialization` 실패 줄을 먼저 찾는다.
2. 있으면 출력 맨 위에 `🚨 마지막 배포(HH:MM) 뒤 앱 기동 실패: <원인 요약 1줄(Caused by 마지막 줄)>`을 낸다. 원인 줄이 매퍼 파싱 오류면 매퍼 파일명을 함께 낸다.
3. 기동 성공 기록이 없고 실패 기록도 없을 때만 기존 `⚠ 앱 기동 기록 없음`을 낸다.

**확인 (합격 기준)**
- 1번 재현 매퍼를 배포한 직후 `yunhee log errors --since-deploy` 첫 줄이 🚨 기동 실패이고 원인 파일명이 나온다. 정상 배포 직후는 기존 출력과 같다.

## 3. `yunhee run "./deploy.sh"` 뒤 자동 헬스체크

**증상 및 재현**
- `deploy.sh`는 WAR 복사까지만 성공하면 exit 0이라, Tomcat에서 앱이 기동에 실패해도 `yunhee run`은 `✅ Execution Succeeded`로 끝난다.

**수정**
1. `yunhee run`이 명령에 `deploy`가 들어 있거나 `.yunhee.toml`의 `[run] deploy_cmds`에 등록된 명령이면, 종료 후 최대 N초(기본 90, `--health-timeout`) 동안 로그에서 `Started … in N seconds`(성공) 또는 위 2번의 기동 실패 패턴을 기다린다.
2. 성공 기록이면 요약 끝에 `✅ 앱 기동 확인 (N초)`, 실패 기록이면 **종료 상태를 실패로 바꾸고** `❌ 앱 기동 실패: <원인 1줄>`을 낸다(원 exit 코드는 요약에 병기). 시간 안에 둘 다 없으면 `⚠ 기동 확인 못 함`(실패로 치지 않음).
3. `--no-health`로 끌 수 있다.

**확인 (합격 기준)**
- 1번 재현 매퍼로 `yunhee run "./deploy.sh"` → `❌ 앱 기동 실패`와 매퍼 파일명, 종료 상태 실패. 정상 매퍼는 `✅ 앱 기동 확인`.
- `yunhee last-run`에도 헬스체크 결과가 남는다.
