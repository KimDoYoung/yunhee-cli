## 1. `analysis method`가 긴 서비스 메서드의 처리 순서를 주지 않는다 (1순위)

**어떤 경우**
- 한 메서드가 여러 SQL을 순서대로 부르고 반복·분기·실패 문구가 섞인 서버 메서드. 예: `Tdm51_ChckOrg.updateApprStatus`(약 230줄: 점검항목 반복 → 이력 insert, 승인자 반복(첫째만 상태 다름), 미흡 내역 반복, 실패 문구 1개), `updateFix`(검사 4개 + 쓰기 3개).

**재현**
```bash
yunhee analysis method Tdm51_ChckOrg.updateApprStatus --server
yunhee analysis method Tdm51_ChckOrg.updateFix --server
```

**기대한 결과**
- 순서가 있는 요약: `1. update tdm60.updateApprStatusByChckOrgId(checkStatusCode=19, apprStatusCode=10)` → `2. for each tdm52.selectByCheckStatusCode: update …, insert tdm55(relateTable=TDM52, procType=승인요청)` → `3. for each tdm58.selectApprStep (i==1이면 …): [분기] parentOrgId != 0 → select tdm59 … fail("승인자(…)의 승인처리가 완료되었습니다…")` 식으로, SQL ID·반복·분기·`result.fail` 문구·파라미터에 들어가는 값(상수 "19"/"10")이 한 번에 보인다.

**실제 결과**
- 서비스·SQL ID 목록과 일부 분기만 나오고 반복(`for`) 안의 호출 순서, 호출마다의 상수 파라미터(상태 코드 "19"→"20" 등), 첫 번째 반복에서만 다른 처리(`i==1`)가 안 나온다. 결국 원본 `Tdm51_ChckOrg.java` L103-417을 `Read(offset/limit)`로 통독했다.

**수정 제안**
1. `--server`일 때 SQL 호출을 "순서 + 반복 깊이" 목록으로 낸다(들여쓰기로 for/if 깊이).
2. SQL 호출의 리터럴 파라미터(`param.put("checkStatusCode", "19")` 등)를 호출 줄에 붙인다.
3. `result.fail(…)`/`new SimpleMessage(…)` 문구를 해당 분기 줄에 붙인다(지금도 클라이언트 쪽은 나오는데 서버 쪽은 빠지는 경우가 있다).

**합격 기준**
- 위 두 메서드 요약만 보고 TOBE 서비스를 쓸 수 있다(원본 통독 없이). 처리 순서와 실패 문구가 원문과 일치.

## 2. `GridGroupBuilder` 그리드를 `analysis grid`·`compare`·`analysis ui`가 못 읽는다

**어떤 경우**
- 첫 열 `title`로 그룹 머리글을 끼우는 `GridGroupBuilder`(`gridGroupBuilder.addText(…, 2, " ")`…)를 쓰는 탭 페이지. 예: `Tdm51_TabPage_CheckOrg`(N21), `Tdm41_TabPage_ManlDutyOrg`(N16).

**재현**
```bash
yunhee analysis grid Tdm51_TabPage_CheckOrg
yunhee compare GET /api/v1/tdm/check-manls -p chckOrgId=202607289814553 -c kfstest \
  --sql tdm52_chck_manl.selectByChckOrgId --param chckOrgId=202607289814553 --param searchText=% \
  --grid Tdm51_TabPage_CheckOrg
yunhee analysis ui Tdm51_Tab_CheckOrg --done Tdm51_TabPage_CheckOrg --tobe frontend/src/pages/tdm
```

**기대한 결과**
- 열 7개(selectYn·checkItem·checkerName·checkResultName·checkStatusName·상세·점검이력)와 폭·제목이 표로 나오고, compare가 그 열로 대조하고, ui 대조표의 그리드 수가 1이다.

**실제 결과**
- `analysis grid`: `rowNumberer` 한 줄만. `compare`: `⚠ 그리드 못 찾음: Tdm51_TabPage_CheckOrg`. `analysis ui`: AS-IS 그리드 `0/1`.

**수정 제안**
- `GridGroupBuilder`를 `GridBuilder`와 같은 메서드 목록(`addText`·`addBoolean`·`addTextArea`·`addCell`…)으로 파싱하고, 유형을 `SingleGrid(그룹)`으로 표시. 첫 열(폭 2)은 `그룹 열(보이지 않음)`으로 표기.

**합격 기준**
- 위 세 명령이 열 7개/대조 ✅/그리드 1을 낸다.

## 3. `analysis ui --tobe`가 `pages/<도메인>` 밖 TOBE 파일을 세지 못한다

**어떤 경우**
- 다른 도메인 조회창을 `frontend/src/components/lookup/`에 두는 규칙(예: `Emp00_Lookup_SelectSingleTdm`).

**재현**
```bash
yunhee analysis ui Tdm51_Tab_CheckOrg --done Emp00_Lookup_SelectSingleTdm --tobe frontend/src/components/lookup
```

**기대한 결과**: 그 클래스 행이 `3/3 · 6/6 · 1/1`로 나온다.

**실제 결과**: 행이 아예 출력되지 않는다(`--tobe`가 도메인 페이지 폴더 하나만 보는 것으로 보임). 직접 `[E0]`~`[E5]` 주석을 세었다.

**수정 제안**: `--tobe`를 여러 번 받거나(`--tobe A --tobe B`) 쉼표 목록을 허용하고, 클래스 이름과 같은 `.tsx`를 폴더 전체에서 찾는다.

**합격 기준**: 위 명령에 `Emp00_Lookup_SelectSingleTdm` 행이 나온다.

## 4. `analysis grid`가 `addLongCnt`의 색 인자 의미를 보여 주지 않는다

**어떤 경우**
- `addLongCnt`는 인자 4개 꼴 `(vp, w, header, color)`와 5개 꼴 `(vp, w, header, headerColor, color)`가 있고, 4개 꼴의 `color`는 값 색, 5개 꼴은 앞이 제목 색이다. 호출이 `"404040"`(# 없음)이면 CSS로 무효(기본 글자색)가 되는 점까지 의미가 다르다.

**재현**
```bash
yunhee analysis grid Tdm51_Tab_CheckOrg   # 렌더링 칸이 비어 있음
```

**실제 결과**: `addLongCnt` 행의 렌더링 칸이 비어 있어 `GridBuilder.java` L1546·L1588을 직접 읽었다.

**수정 제안**: 렌더링 칸에 `N건(0도 0건, 값색 #404040 / 제목색 456EA6)`처럼 적고, 색이 `#` 없는 값이면 `(무효 CSS)`를 붙인다.

**합격 기준**: 렌더링 칸으로 TOBE 셀 렌더러를 결정할 수 있다.

## 5. `run`이 테스트 컨텍스트 적재 실패의 원인을 요약에 주지 않는다

**어떤 경우**
- `@MybatisTest`가 Logback 로그 폴더 권한(`허가 거부`, 도커가 root로 만든 폴더)으로 컨텍스트를 못 띄움.

**재현**
```bash
yunhee run "bash -c 'cd backend && gradle test --tests kr.co.kfs.asseterp.biz.tdm.TdmCheckOrgDbTest'"
```

**실제 결과**: 요약은 `4 tests completed, 4 failed`, 케이스 메시지는 `Failed to load ApplicationContext`뿐. `analysis run last --stdout`은 `Caused by: IllegalStateException at LogbackLoggingSystem.java:291`까지만 나오고, 진짜 원인(`FileNotFoundException … (허가 거부)`)은 `build/test-results/test/*.xml`을 직접 열어야 보였다.

**수정 제안**: 컨텍스트 적재 실패면 XML에서 가장 깊은 `Caused by`와 그 메시지(또는 `ERROR in …` 줄)를 첫 실패 아래 2줄로 보여 준다.

**합격 기준**: 위 재현의 요약만으로 "로그 파일 열기 권한 거부 /home/…/logs/…log"가 보인다.

## 6. 0.5.1 `port-sql`의 남은 흠 (042-1 후속, 재확인)

- 안쪽 SELECT 본문이 들여쓰기 없이 평평하게 붙어 나와(`FROM tdm51_chck_org` 아래 `CROSS JOIN` 등) 길이가 긴 SQL은 읽기 어렵다.
- 바깥 `<sql id="…Columns">`가 `--cols`와 무관한 파생 열(`fix_yn`·`check_status_all10_yn`… 9~14열)까지 모두 펼친다 → 복사 후 지워야 한다. `--cols`에 없는 열은 접어서(`-- 생략 n열`) 보여 주면 좋다.
- 위치 `INSERT … SELECT`(열 이름 없음)는 여전히 조각을 만들지 못한다(`tdm60.insertByTdm58`·`tdm61.insertByTdm58`·`tdm55.insert`). 대상 테이블 열 이름으로 풀어 써 주면(`yunhee table` 정보 활용) 손으로 옮기는 일이 준다.

## 7. TOBE 파일을 부분만 보는 공식 수단이 없다 (훅과 충돌)

**어떤 경우**
- AssetERP 훅이 `cat`·`sed`·`head`·`grep -A/-B/-C`와 큰 파일 통읽기를 막고 `yunhee outline`/`analysis tobe` 후 `Read(offset/limit)`를 안내한다. 이 세션에서 훅 차단이 6번 났다(`cat DTO`, `grep -A` ×2, `sed -n` ×2, `Read` 통읽기 ×2).

**수정 제안**: `yunhee outline <파일> --range L1-60`처럼 "yunhee가 줄 범위를 직접 읽어 주는" 하위 명령이 있으면 훅과 부딪히지 않는다(Read 도구는 한 번에 한 파일). 여러 파일 범위를 한 번에: `yunhee cat a.java:1-30 b.xml:100-140`.

**합격 기준**: 훅을 건드리지 않고 한 호출로 여러 파일의 줄 범위를 읽을 수 있다.
