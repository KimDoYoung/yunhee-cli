## 1. `analysis method`가 긴 서비스 메서드의 처리 순서를 주지 않는다 (1순위)

**어떤 경우**
- 한 메서드가 여러 SQL을 순서대로 부르고 반복·분기·실패 문구가 섞인 서버 메서드. 예: `Tdm51_ChckOrg.updateApprStatus`(약 230줄: 점검항목 반복 → 이력 insert, 승인자 반복(첫째만 상태 다름), 미흡 내역 반복, 실패 문구 1개), `updateFix`(검사 4개 + 쓰기 3개).

**재현**
```bash
yunhee analysis method Tdm51_ChckOrg.updateApprStatus --server
yunhee analysis method Tdm51_ChckOrg.updateFix --server
```

**기대한 결과**
- 순서가 있는 요약: `1. update tdm60.updateApprStatusByChckOrgId(checkStatusCode=19, apprStatusCode=10)` → `2. for each tdm52.selectByCheckStatusCode: update …, insert tdm55(relateTable=TDM52, procType=승인요청)` → `3. for each tdm58.selectApprStep (i==1이면 …): [분기] parentOrgId != 0 → select tdm59 … fail("승인자(…)의 승인처리가 완료되었습니다…")` 식으로, SQL ID·반복·분기·`result.fail` 문구·파라미터에 들어가는 값(상수 "19"/"10")이 한 번에 보인다.

**실제 결과**
- 서비스·SQL ID 목록과 일부 분기만 나오고 반복(`for`) 안의 호출 순서, 호출마다의 상수 파라미터(상태 코드 "19"→"20" 등), 첫 번째 반복에서만 다른 처리(`i==1`)가 안 나온다. 결국 원본 `Tdm51_ChckOrg.java` L103-417을 `Read(offset/limit)`로 통독했다.

**수정 제안**
1. `--server`일 때 SQL 호출을 "순서 + 반복 깊이" 목록으로 낸다(들여쓰기로 for/if 깊이).
2. SQL 호출의 리터럴 파라미터(`param.put("checkStatusCode", "19")` 등)를 호출 줄에 붙인다.
3. `result.fail(…)`/`new SimpleMessage(…)` 문구를 해당 분기 줄에 붙인다(지금도 클라이언트 쪽은 나오는데 서버 쪽은 빠지는 경우가 있다).

**합격 기준**
- 위 두 메서드 요약만 보고 TOBE 서비스를 쓸 수 있다(원본 통독 없이). 처리 순서와 실패 문구가 원문과 일치.

## 2. `GridGroupBuilder` 그리드를 `analysis grid`·`compare`·`analysis ui`가 못 읽는다

**어떤 경우**
- 첫 열 `title`로 그룹 머리글을 끼우는 `GridGroupBuilder`(`gridGroupBuilder.addText(…, 2, " ")`…)를 쓰는 탭 페이지. 예: `Tdm51_TabPage_CheckOrg`(N21), `Tdm41_TabPage_ManlDutyOrg`(N16).

**재현**
```bash
yunhee analysis grid Tdm51_TabPage_CheckOrg
yunhee compare GET /api/v1/tdm/check-manls -p chckOrgId=202607289814553 -c kfstest \
  --sql tdm52_chck_manl.selectByChckOrgId --param chckOrgId=202607289814553 --param searchText=% \
  --grid Tdm51_TabPage_CheckOrg
yunhee analysis ui Tdm51_Tab_CheckOrg --done Tdm51_TabPage_CheckOrg --tobe frontend/src/pages/tdm
```

**기대한 결과**
- 열 7개(selectYn·checkItem·checkerName·checkResultName·checkStatusName·상세·점검이력)와 폭·제목이 표로 나오고, compare가 그 열로 대조하고, ui 대조표의 그리드 수가 1이다.

**실제 결과**
- `analysis grid`: `rowNumberer` 한 줄만. `compare`: `⚠ 그리드 못 찾음: Tdm51_TabPage_CheckOrg`. `analysis ui`: AS-IS 그리드 `0/1`.

**수정 제안**
- `GridGroupBuilder`를 `GridBuilder`와 같은 메서드 목록(`addText`·`addBoolean`·`addTextArea`·`addCell`…)으로 파싱하고, 유형을 `SingleGrid(그룹)`으로 표시. 첫 열(폭 2)은 `그룹 열(보이지 않음)`으로 표기.

**합격 기준**
- 위 세 명령이 열 7개/대조 ✅/그리드 1을 낸다.

## 4. `analysis grid`가 `addLongCnt`의 색 인자 의미를 보여 주지 않는다

**어떤 경우**
- `addLongCnt`는 인자 4개 꼴 `(vp, w, header, color)`와 5개 꼴 `(vp, w, header, headerColor, color)`가 있고, 4개 꼴의 `color`는 값 색, 5개 꼴은 앞이 제목 색이다. 호출이 `"404040"`(# 없음)이면 CSS로 무효(기본 글자색)가 되는 점까지 의미가 다르다.

**재현**
```bash
yunhee analysis grid Tdm51_Tab_CheckOrg   # 렌더링 칸이 비어 있음
```

**실제 결과**: `addLongCnt` 행의 렌더링 칸이 비어 있어 `GridBuilder.java` L1546·L1588을 직접 읽었다.

**수정 제안**: 렌더링 칸에 `N건(0도 0건, 값색 #404040 / 제목색 456EA6)`처럼 적고, 색이 `#` 없는 값이면 `(무효 CSS)`를 붙인다.

**합격 기준**: 렌더링 칸으로 TOBE 셀 렌더러를 결정할 수 있다.

## 6. 0.5.1 `port-sql`의 남은 흠 (042-1 후속, 재확인)

- 안쪽 SELECT 본문이 들여쓰기 없이 평평하게 붙어 나와(`FROM tdm51_chck_org` 아래 `CROSS JOIN` 등) 길이가 긴 SQL은 읽기 어렵다.
- 바깥 `<sql id="…Columns">`가 `--cols`와 무관한 파생 열(`fix_yn`·`check_status_all10_yn`… 9~14열)까지 모두 펼친다 → 복사 후 지워야 한다. `--cols`에 없는 열은 접어서(`-- 생략 n열`) 보여 주면 좋다.
- 위치 `INSERT … SELECT`(열 이름 없음)는 여전히 조각을 만들지 못한다(`tdm60.insertByTdm58`·`tdm61.insertByTdm58`·`tdm55.insert`). 대상 테이블 열 이름으로 풀어 써 주면(`yunhee table` 정보 활용) 손으로 옮기는 일이 준다.

## 7. TOBE 파일을 부분만 보는 공식 수단이 없다 (훅과 충돌)

**어떤 경우**
- AssetERP 훅이 `cat`·`sed`·`head`·`grep -A/-B/-C`와 큰 파일 통읽기를 막고 `yunhee outline`/`analysis tobe` 후 `Read(offset/limit)`를 안내한다. 이 세션에서 훅 차단이 6번 났다(`cat DTO`, `grep -A` ×2, `sed -n` ×2, `Read` 통읽기 ×2).

**수정 제안**: `yunhee outline <파일> --range L1-60`처럼 "yunhee가 줄 범위를 직접 읽어 주는" 하위 명령이 있으면 훅과 부딪히지 않는다(Read 도구는 한 번에 한 파일). 여러 파일 범위를 한 번에: `yunhee cat a.java:1-30 b.xml:100-140`.

**합격 기준**: 훅을 건드리지 않고 한 호출로 여러 파일의 줄 범위를 읽을 수 있다.

## 9. `getButtonBar().add(button)`로 붙는 창 단추를 "도달 불가"로 표시한다 (0.5.4, 1순위 — 세 번째 재확인)

- 계기: AssetERP **O02 기간별 업무일정 조회**(`Sch01_Tab_List`: 클래스 3, 새 API 4개) 변환 중(2026-10-26, yunhee **0.5.4**). 같은 한계가 N22·N23에서도 기록되어 이번이 세 번째다.

**어떤 경우**
- 창(Window)의 `init()`/생성자에서 `this.getButtonBar().add(closeButton)`으로 아래 버튼 줄에 붙이는 단추. 예: `Sch10_Lookup_Ipo`(L58-74). 같은 창 계열인 `Sch01_Lookup_InfoView`는 `this.addButton(closeButton)`으로 붙이는데 이쪽은 정상으로 나온다 — **`getButtonBar().add(…)` 형태만** 빠진다.

**재현**
```bash
cd AssetERP
yunhee analysis screen Sch01_Tab_List --class Sch10_Lookup_Ipo
yunhee analysis method Sch10_Lookup_Ipo.init -o code     # L58-74: this.getButtonBar().add(closeButton)
```

**기대한 결과**
- 이벤트 절: `[E1] closeButton[닫기].Select [callback != null] (L90) → hide()` (도달 불가 표시 없음).
- 버튼 절: `<Button type="close" onClick={hide}>닫기</Button>` (후보 주석이 아니라 확정).

**실제 결과**
- 이벤트 절 제목이 `#### 이벤트 (도달 불가: closeButton 컬럼·툴바 미연결)`, `[E1] … ⚠ 도달 불가 (closeButton 컬럼·툴바 미연결)`. 버튼 절은 `type="unknown" /* 후보: close (닫기) */`. `analysis ui`의 버튼 수는 1/1로 맞았고 이벤트 표시만 틀리다.
- 도달 불가를 "만들지 않아도 됨"으로 읽으면 [닫기]를 빠뜨린다. 이번에는 `init()` 원문을 보고 만들었다.

**수정 제안**
1. 도달 판정에서 `getButtonBar().add(x)`·`getButtonBar().insert(x, …)`도 `addButton(x)`와 같이 "화면에 붙음"으로 센다(창 아래 버튼 줄).
2. 그 단추의 `type` 추정(`close` 등)은 후보 주석 없이 낸다 — 이름이 `closeButton`이고 핸들러가 `hide()`이면 확정.

**합격 기준**
- 위 재현이 도달 불가 문구 없이 `[E1]`을 내고 버튼 절이 `type="close"`를 낸다. `Sch01_Lookup_InfoView`·`Bbs02_Lookup_File` 등 `addButton` 형태의 결과는 그대로.

## 10. `mapper-run`/`analysis sql`/`compare`에 NULL 파라미터를 줄 수 없다 (0.5.4)

**어떤 경우**
- "전체" 선택이 `null`로 가는 조회: `sch01_info.selectByCloseDate`의 `classId`(null이면 분류 조건 없음, 다른 가지는 `COALESCE(#{classId},1) = 1`).

**재현**
```bash
yunhee mapper-run backend/src/main/resources/mapper/SchInfoMapper.xml#selectByCloseDate \
  --compare sch01_info.selectByCloseDate --count \
  -p companyId=n:28000 -p personId=n:29049 -p orgId=n:0 -p startDate=s:2026-01-01 -p endDate=s:2026-12-31 \
  -p classId= -p shareType=s:% -p cycleCode=s:% -p dailyYn=s:false -p searchText=s:%%
```

**기대한 결과**: `classId`가 SQL NULL로 바인딩되어 "전체" 분기가 AS-IS와 같은 행 수로 대조된다.

**실제 결과**: `[ERROR] TOBE SQL 실행 실패: invalid input syntax for type integer: ""` / `LINE 157: AND COALESCE('',1) = 1` — 빈 값이 빈 글자 `''`로 들어가고, `-p`를 생략하면 "값 없음"이다. 그래서 "전체" 경로는 구체 분류 ID 여러 개로 갈음하고 결과확인에 `미확인`으로 남겼다(O02 결과확인 3).

**수정 제안**: 042-14의 타입 강제 접두사에 `null:`(또는 `-p classId=null:`)을 더해 SQL NULL로 보낸다. `analysis sql --param`·`compare --param`도 같은 접두사.

**합격 기준**: 위 재현에서 `classId=null:`을 주면 오류 없이 `TOBE rows=N, AS-IS rows=N ✅`가 나온다.

## 11. 그 밖에 O02에서 본 작은 흠 (0.5.4)

- **`port-sql`이 `<include refid>` 대상을 `<sql id="…">`로 본문에 펼친다**: `sch01_info.selectByCloseDate`의 `selectIpo`(L196, 이 statement에서 한 번만 쓰임)가 `FROM (<sql id="selectIpo"> … </sql>) ipo`로 나와 그대로 쓰면 MyBatis가 읽지 못한다. 한 번만 쓰이는 include는 그 자리에 펼쳐 주거나, 최소한 `<sql>` 태그를 빼고 `<!-- include selectIpo -->` 표시만 두면 좋다. (6번의 평탄한 들여쓰기도 같은 SQL에서 재확인: 350줄이 들여쓰기 없이 나옴.)
- **`port-sql`의 `--cols` 밖 열 펼침**: 이번에도 `--cols`에 준 20열 외에 바깥 별칭 `company_id`를 더해 DTO에 들어갔다(6번과 같은 현상 — 이쪽은 필요해서 도움이 되었지만 표시가 없다). `--cols`에 없는 열은 `-- 추가` 표시를 붙이면 좋다.
- **`yunhee api` 경로 보정이 서버에 404를 남기는 것으로 보인다**(추정): `ℹ 경로를 /api/v1/… 로 보정` 직후 `log errors --since-deploy`에 `No static resource sch/infos/#/view` 같은 WARN이 `/api/v1` 없는 경로로 쌓였다. 보정을 서버 호출 전에 하면 로그가 깨끗해진다.

## 14. `analysis method`가 주석 처리된 본문을 줄 중간에서 자른다

**어떤 경우**: 메서드가 `// public String getNote() {` 식 **주석 처리된 선언**으로만 보여, 실제 반환 본문(또는 부모 클래스 위임)을 알 수 없다. 모델 `Org01_CodeModel.getNote()`(L105-107: `// return note; // }`)를 `analysis model`이 "계산(getter L105-107)"로 표시해 열이 어디서 오는지 모른다.

**재현**
```bash
yunhee analysis method Org01_CodeModel.getNote --raw     # 주석 두 줄만, 메서드 본문 없음
yunhee analysis model Org01_CodeModel                      # note: orgInfoModel.note / 계산(getter L105-107)
```

**실제 결과**: 주석 줄만 나오고 "이 getter는 전부 주석 처리됨(실제 메서드 없음)"인지 알려 주지 않아, 원본을 `Read`(줄 범위)로 열어 확인했다.

**수정 제안**: 선언·본문이 모두 `//` 주석이면 `⚠ 주석 처리된 메서드(실제 정의 없음)`로 표시하고, `analysis model`은 그 속성을 `계산`이 아니라 `주석 처리(상위 클래스/경로 확인)`로 낸다.
**합격 기준**: 위 두 명령이 "주석 처리됨"을 명시한다.

## 15. `compare`가 원본 SQL이 이 DB에서 실패하는 이유를 TOBE와 구분해 주지 않는다 / 모호한 오류

**어떤 경우**: AS-IS SQL이 현재 DB 스키마에 없는 열을 쓴다. 예: `fnd01_fund_code.selectByFundName`이 `fnd25_terms.fnd25_fund_id`를 조인하는데 이 DB에는 그 열이 없다(`fnd25_terms` 열: `fnd25_terms_id`·`company_id`·`terms_type`·`seq`·`close_date`·`upd_nm`·`upd_date`).

**재현**
```bash
yunhee compare GET v1/fnd/fund-codes/plan-auths --sql fnd01_fund_code.selectByFundName \
  --param closeYn=false --param companyId=28000 --param 'fundName=%%' --param 'fundTypeCode=%' \
  --param 'classTypeCode=%' --param planYn=true --param 'icamYn=%' --grid Fnd08_Tab_OrgAuthTempFund
```

**실제 결과**: 첫 줄 `[ERROR] SQL 실행 실패: column "fnd25_fund_id" does not exist` 뒤에 바인딩한 **AS-IS SQL 전문 약 200줄**이 그대로 출력된다. 원인은 첫 줄 하나인데 `tail`로 보면 SQL 끝만 보여 `grep "API rows|ERROR"`로 다시 걸러야 했다. API 쪽 행 수(TOBE)도 같이 보여 주지 않아 "TOBE는 문제없음"을 별도 호출로 확인했다.

**수정 제안**: ① SQL 오류면 SQL 전문은 `-o sql`/`--verbose`에서만 내고 기본은 오류 한 줄 + "AS-IS SQL이 실패: 원본 쪽 문제(TOBE API는 rows=N)". ② `sql-check`의 `⚠DB없음`처럼, 실패 원인이 존재하지 않는 열이면 `원본 SQL이 현재 DB에서 실행 불가`라고 분류해 03 원칙 4 예외 후보로 표시한다.
**합격 기준**: 위 재현의 출력이 20줄 이내이고 TOBE 행 수와 "AS-IS 실행 불가" 문구가 보인다.

## 16. `analysis sql`/`-o sql`의 긴 출력을 도구가 파일로 돌릴 때 필요한 줄만 고르기 어렵다

- `analysis sql fnd01_fund_code.selectByFundName -o sql` + `selectByFundOrgAuth -o sql`을 한 호출에 묶자 32KB(약 520줄)가 되어 도구가 결과를 파일로 저장했다(대부분 CTE 11개 반복). 필요한 건 `WHERE` 이후 80줄뿐.
- **제안**: `analysis sql … --section where`(또는 `--no-cte`)로 CTE를 `-- CTE closeFund, fundType … (생략)`으로 접고 본 SELECT·WHERE만 내는 옵션. `getSystemCodeName` 같은 `include` CTE는 이름만.
- **합격 기준**: 위 두 SQL이 각 60줄 안팎으로 나온다.

## 17. `port-sql`/`port-save` 한계 재확인 (P01·P02)

- `SELECT t1.*, t2.*, … FROM fnd01_fund_code t1 JOIN fnd02_fund_info t2` 형태(`selectByFundPlan`): `port-sql`이 `--cols` 14개 중 **6개를 `⚠ SQL 열 없음`**(fundCode·orgCodeName·operator1·operator2·realFundCode·realFundName)으로 표시했다. 열은 `t1.*`/`t2.*`가 가져오는 테이블 열(`fnd01_fund_cd`·`fnd02_org_code_nm`…)이므로 `yunhee table`로 `t1.*`을 펼쳐 대응하면 해결된다. 이번에도 매퍼 문장을 손으로 옮겼다. (042-1이 서브쿼리 `FROM (…) t`의 `t.*`는 펼치는데, 같은 SELECT 목록의 **`t1.*, t2.*` 직접 조인**은 안 펼친다.)
- `port-save`: 복합 저장(두 테이블 · 새 ID 먼저 채번 · 열 일부만)은 INSERT/UPDATE 뼈대로 충분했다. 다만 `⚠ 회사 컬럼 없음` 출력은 `fnd02_fund_info`처럼 **부모 테이블로 회사가 정해지는 자식 테이블**이면 "부모(`fnd01_fund_code`)로 회사 확인 필요"까지 안내하면 보안 조건(INSERT/UPDATE에 회사 조건)을 놓치지 않는다.
- **합격 기준**: `t1.*, t2.*` 조인 SELECT에서 `--cols`가 모두 대응되고, 회사 열이 없는 자식 테이블에는 부모 테이블 조인 안내가 붙는다.

## 18. `compare -c`의 값은 회사 ID가 아니라 회사코드 — 도움말·오류 안내

- `-c 28000`(회사 ID)을 줬더니 `COMPANY_NOT_FOUND`로 로그인 실패. 도움말에는 `-c <회사코드>`로만 적혀 있어 처음 쓰는 사람이 ID를 넣기 쉽다(AssetERP 문서에는 있음).
- **제안**: 실패 시 `-c는 회사코드입니다(예: admin, kfstest). 회사 ID가 아닙니다`를 한 줄 더하고, 숫자만 주었으면 `companyId로 오해했나요?` 추정을 붙인다.
- **합격 기준**: `-c 28000` 실패 메시지에 위 안내가 나온다.

## 19. 배포 직후 첫 `api` 호출이 `TOKEN_EXPIRED` (재시도하면 성공)

- 두 번 모두(P01·P02) `./deploy.sh` 직후 첫 `yunhee api GET …`이 `HTTP 401 TOKEN_EXPIRED 인증 토큰이 만료되었습니다`를 냈고 바로 다시 호출하면 성공했다(`--wait-deploy`는 쓰지 않았음).

- **합격 기준**: 배포 직후 첫 호출이 사용자에게 오류 없이 성공한다.
