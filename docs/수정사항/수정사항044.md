  1. 명령어별 옵션 일관성 및 하위 디렉터리(--src-index) 경로 인식
      • 저장소 루트(framework-sprt)에서 실행할 때 yunhee analysis screen은 --src-index를 지원하지만, yunhee compare는 -
      ￺-src-index 옵션이 없고 docs/as-is/src만 바라보아 ⚠ 그리드 못 찾음이 발생했습니다.
      • cd AssetERP로 이동해서 실행해야 색인 기반 그리드 비교가 가능했습니다. 설정 파일(.env.yunhee 또는 .yunhee.
      ￺toml)의 색인 경로를 모든 명령어가 일관되게 참조하거나, 모든 분석/비교 명령어에 --src-index가 공통 지원되면
      좋겠습니다.
  2. 시험 데이터 원복(Clean-up) 지원 부재
      • 절대원칙 2("확인 작업은 데이터를 바꾸지 않고, 시험용 생성 행은 세션 안에 지운다")에 따라 rd-download API 호출로
      sys99_print에 들어간 716건의 임시 행을 삭제해야 했습니다.
      • 하지만 yunhee sql은 읽기 전용 강제(또는 트랜잭션 종료 시 ROLLBACK되는 --rollback만 지원)라, 이미 API 요청으로
      커밋된 시험 데이터를 삭제할 수 없어 결국 docker exec로 psql을 직접 호출해야 했습니다.
      • 예: 특정 테이블/조건의 시험 데이터를 안전하게 삭제할 수 있는 관리 명령(예: yunhee sql --allow-dml 또는 yunhee
      ￹clean-test-data)이 지원되면 절대원칙 준수가 훨씬 수월해질 것 같습니다.
  3. `compare --param k=b:true`가 불리언이 아니라 문자열로 전달됨 (AssetERP S03, 2026-10-28)
      • `yunhee compare GET /emp/directors … --sql emp31_director.selectByText --param endCheck=b:true`로 돌리면 AS-IS SQL 쪽 `<if test="endCheck != true">` 분기를 잘못 타서 API 12행 대 SQL 10행으로 ❌가 나왔습니다. 출력에는 `(branch: endCheck ON)`으로 표시되어 true를 준 것과 반대 분기입니다.
      • `--param endCheck=true`(접두사 없음)로 주면 12 = 12 ✅, `(branch: endCheck OFF)`가 됩니다. `b:` 접두사(타입 강제, 0.5.2의 042-14)가 불리언에는 문자열로 넘어가는 것으로 보입니다. `b:true`·`b:false`를 불리언으로 바인딩하고 분기 판정에도 쓰도록 고치거나, 안 되는 타입이면 경고를 내 주세요.
  4. `compare --grid <클래스>`가 엉뚱한 그리드를 고름 (AssetERP B15, 2026-10-28)
      • `yunhee compare GET /dcr/links/lookup --sql dcr30_link.selectByCompanyId --grid Dcr30_Lookup_Link`가 대조한 그리드는 3컬럼(`Dcr30_Lookup_Link#buildGrid`)이었고 `⚠ fields ⊇ grid cols (missing: classTreeFNm)`을 냈습니다. 같은 클래스의 실제 그리드는 6열 + `classTreeFullName`이며, 같은 명령에 `linkCodeList`를 주면 4컬럼으로 ✅가 나왔습니다. 응답 필드가 같은데 결과가 달라서 "API 필드와 가장 많이 겹치는 그리드" 선택이 불안정한 것 같습니다.
      • 클래스에 그리드가 하나뿐이면 그것을 쓰고, 여러 개일 때만 겹침으로 고르며, `missing:` 열 이름이 모델 속성명(`classTreeFullName`)이 아닌 변형(`classTreeFNm`)으로 나오는 이유도 확인해 주세요.
  5. `compare`가 값 하나를 돌려주는 SQL(건수 SQL 등)을 행 수로 비교함 (AssetERP S01, 이번 세션 앞서 기록)
      • `bbs02_notice.selectByNoticeDetailCodePaging…Total`처럼 값 하나(`count`)를 돌려주는 SQL은 행 수 1과 API의 `total`을 비교해 5 대 1 ❌로 나옵니다. 결과가 한 행·한 열이면 그 값을 API 응답의 `total`/동일 이름 필드와 비교해 주세요.
  6. `analysis method <클래스>.<메서드>`가 오버로드면 후보만 보여 주고 끝남 (AssetERP B15)
      • `Dcr30_Lookup_Link.open`은 후보 2개(`open(InterfaceCallback)`, `open(String, InterfaceCallback)`)만 나오고 Exit 2라서 `#번호`로 다시 돌려야 합니다. `--all-overloads`처럼 후보 본문(요약 또는 `-o code`)을 한꺼번에 보여 주는 옵션이 있으면 한 번에 끝납니다.
  7. `analysis grid`의 편집기 열이 `addTextArea(…, new MyTextArea())`를 빈칸으로 표시 (AssetERP S03)
      • `addTextArea(properties.addTitle(), 250, "겸직사항", new MyTextArea())`는 편집 가능한 열인데 `편집기` 열이 비어 있고 `addTextArea`는 읽기 전용으로 보여서, 원본을 `yunhee cat`으로 다시 확인해야 했습니다. 편집기 인자(`MyTextArea`)가 있으면 `largeText`처럼 표시해 주세요(S02의 읽기 전용 `addTextArea`와 구분).
  8. 훅 차단 안내에 `yunhee cat 파일:범위`를 먼저 알려 주세요 (AssetERP 전 세션)
      • `grep -n "x" 파일 -B/-A`나 `sed -n 1,19p 문서.md`가 훅에 막혔을 때 안내문이 `outline`·`analysis`만 제안해서, 문서나 AS-IS 줄 범위를 보려고 `yunhee cat 경로:시작-끝`(043-7)을 스스로 찾아야 했습니다. 안내에 `yunhee cat <파일>:<시작>-<끝>`을 추가해 주세요. 또 `docs/NN-*.md`는 "파일 전체는 Read(offset/limit)"이라고 되어 있으나 `sed -n`으로 문서 일부를 보는 것도 막힙니다 — 문서 범위 읽기는 허용하거나 안내해 주세요.
