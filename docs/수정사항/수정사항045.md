## 1. `compare`가 API 서버 오류(HTTP 500)를 `rows=0 ✅`로 보여 준다 (최우선)

**어떤 경우**
- AssetERP T13에서 새 API `GET v1/car/bookings`를 만들고 처음 배포했을 때, MyBatis record 생성자 자동 매핑 오류로 **HTTP 500**이 났다.
- 같은 시점에 아래 명령은 이렇게 출력했다.

```
yunhee compare GET v1/car/bookings -p date=2026-05-29 -p type=all \
  --sql car03_booking.selectByDate --param companyId=28000 --param startDate=2026-05-29 \
  --param type=all --param personId=-28656 --grid Car03_Tab_DayofMonth
→ API rows=0, SQL rows=0 ✅  필드 비교 못 함 (행 0건) (Car03_Tab_DayofMonth#buildGrid, 5컬럼)
```
- 같은 요청을 `yunhee api GET v1/car/bookings -p date=2026-05-29 -p type=all --log`로 보면 `HTTP 500 INTERNAL_ERROR`였고, 원인(`Constructor auto-mapping … ExecutorException`)은 `yunhee log errors --since 10m`으로 따로 찾았다.
- 이때 AS-IS 쪽도 우연히 0행이어서 "일치"로 보였다. **AS-IS가 0행이 아니었다면 `API rows=0, SQL rows=N ❌`로 나왔겠지만, 원인이 "API가 죽었다"가 아니라 "행이 다르다"로 읽힌다.** 어느 쪽이든 500이라는 사실이 출력에 없다.

**왜 문제인가**
- `compare`의 목적은 "TOBE API가 AS-IS SQL과 같은 결과를 내는가"이다. API가 500이면 대조 자체가 성립하지 않는데 성공/행 수 불일치로 보이면, 사용자(에이전트)가 깨진 API를 통과시키거나 엉뚱한 곳(SQL)을 의심한다. 로그를 따로 보지 않으면 발견하지 못한다.

**고칠 것**
1. API 응답이 HTTP 4xx/5xx이거나 `ApiResponse.success=false`이면 행 수 비교로 넘어가지 말고 **즉시 실패로 표시**한다.
   - 출력 예: `❌ API 실패: HTTP 500 INTERNAL_ERROR (추적ID: 9d51046c…) — yunhee log trace 9d51046c… --raw`
   - 종료 코드는 0이 아니어야 한다(스크립트·`yunhee run` 요약이 실패로 잡도록). 지금 `yunhee api`가 이미 같은 정보를 알고 있으므로 같은 오류 요약 코드를 재사용하면 된다.
2. 업무 예외(4xx, `INVALID_INPUT` 등)도 "행 0건"이 아니라 `API 업무 오류: <message>`로 구분해 표시한다(파라미터가 틀린 경우를 알려 준다).
3. 가능하면 위 실패 출력에 `--log` 요약(그 요청의 WARN/ERROR 1~2줄)을 붙인다.

**검증 방법**
- (a) 일부러 실패시키기: 존재하는 엔드포인트에 잘못된 값을 준다. 예) `yunhee compare GET v1/car/bookings -p date=not-a-date --sql car03_booking.selectByDate --param companyId=28000 --param startDate=2026-05-29 --param type=all --param personId=-28656` → **4xx 실패 출력 + 종료 코드 ≠ 0**이어야 한다(현재는 `rows=0 ✅` 또는 불일치로 나온다).
- (b) 500 재현: 임시로 매퍼 결과 열 하나를 빼서(record 생성자 열 수 불일치) 배포한 뒤 같은 명령 → `HTTP 500` 실패 출력.
- (c) 회귀: 정상 API(`yunhee compare GET v1/car/bookings -p date=2026-05-29 -p type=my --sql … --param personId=202204180108329`)는 종전처럼 `API rows=1, SQL rows=1 ✅`.
- (d) 기존 단위 테스트에 "API 5xx → 실패/종료 코드 1" 케이스 추가.

## 2. `compare`(와 `analysis sql -o sql`)의 AS-IS 쪽이 `/* if … */` 분기를 항상 적용한다

**어떤 경우**
- `car03_booking.selectByDate`는 `<if test="type.equals('my')">AND car03_person_id = :personId</if>` 분기를 가진다.
- `--param type=all`로 AS-IS SQL을 펼쳐도 분기가 **항상 적용**된다.

```
yunhee analysis sql car03_booking.selectByDate -o sql --param companyId=28000 \
  --param startDate=2026-05-29 --param type=all --param personId=-28656
→ …
   /* if type.equals('my')  */
      AND	car03_person_id = -28656
   /* end */
   ORDER BY …
```
- 그래서 `yunhee compare … --param type=all`은 `API rows=1, SQL rows=0 ❌`가 나왔다(API는 `type=all`에서 정상으로 1행을 돌려줌). `mapper-run … --compare car03_booking.selectByDate -p type=my -p personId=202204180108329`처럼 **분기가 실제로 켜지는 값**을 주면 `TOBE rows=1, AS-IS rows=1 ✅`였다.
- 이미 044번에는 `<if test="endCheck != true">`가 `(branch: endCheck ON/OFF)`로 평가되는 것이 기록돼 있다. 즉 **불리언 비교(`!= true`, `!= null`)는 평가되는데 문자열 메서드 호출(`x.equals('lit')`)은 평가되지 않아 "항상 적용"으로 떨어지는** 것으로 보인다. T15의 `infoId != null`은 정상 평가됐다.

**왜 문제인가**
- 정상 API가 불일치로 나오면 개발자가 TOBE SQL/서비스를 의심하게 된다. 우회(`mapper-run --compare`에 분기 값과 실제 데이터의 ID를 직접 주기)를 알고 있어야 한다.
- 더 나쁜 것은 "평가 못 했는데 말없이 켠다"는 점이다. 항상 적용이든 항상 미적용이든 결과가 틀릴 수 있다.

**고칠 것**
1. 분기 조건식 평가기를 확장한다. 최소 지원 목록:
   - `x.equals('lit')`, `'lit'.equals(x)`, `!x.equals('lit')`
   - `x == 'lit'`, `x != 'lit'` (문자열)
   - `x.isEmpty()`, `x != null && x.length() > 0` 등 자주 쓰는 것은 실제 소스에서 빈도를 세어 우선순위를 정한다(`yunhee analysis sql --list`로 색인의 `조건 분기`를 모아 보면 빈도가 나온다).
2. 평가할 수 없는 식은 **임의로 켜지 말고** 출력에 `⚠ 분기 평가 불가: type.equals('my') — 양쪽(켬/끔) 모두 보려면 --branch type.equals('my')=on|off`처럼 표시한다. 대조 결과 줄에도 `(분기 N개 평가 불가)`를 붙여 ✅/❌ 판정을 신뢰하지 말라는 표시를 한다.
3. 선택: 평가 불가 분기를 사용자가 `--branch '<식>'=on|off`로 강제할 수 있게 한다.

**검증 방법**
- `yunhee analysis sql car03_booking.selectByDate -o sql --param companyId=28000 --param startDate=2026-05-29 --param type=all --param personId=1`
  → 출력에 `car03_person_id` 조건이 **없어야** 한다(분기 OFF).
- 같은 명령에 `--param type=my` → `AND car03_person_id = 1`이 **있어야** 한다(분기 ON).
- `yunhee compare GET v1/car/bookings -p date=2026-05-29 -p type=all --sql car03_booking.selectByDate --param companyId=28000 --param startDate=2026-05-29 --param type=all --param personId=-28656`
  → API 행 수와 SQL 행 수가 같아야 한다(둘 다 같은 분기 OFF).
- 평가 불가 식(예: 일부러 `x.matches('…')`)을 가진 SQL → 경고가 출력에 있어야 하고 침묵하지 않아야 한다.
- 회귀: 044의 `endCheck != true`, `infoId != null` 케이스가 종전처럼 평가된다.
- 색인 전체에서 `조건 분기`가 있는 SQL 중 "평가 불가"로 분류되는 비율을 보고서로 한 번 출력해 두면(개수만) 확장 범위를 확인할 수 있다.

## 3. `page-style` 판별기가 TOBE를 잘못 읽거나 새 스타일을 모른다

**어떤 경우**
- (a) **SG를 CG로 읽는다.** AS-IS가 `SG`(조회 툴바 + 그리드 하나)인 화면의 TOBE를 `--compare`하면 `CG (편집 가능한 그리드 하나)`로 나와 `⚠ 불일치`가 된다. 해당 화면은 모두 견본 `docs/page-style/SG/Tdm01_Tab_Hr.tsx`를 열어 뼈대로 만든 것이다(`SearchBar` + `SingleGrid`/`MultiGrid`, 아이콘 열 포함).

```
yunhee page-style --compare …/Car04_Tab_PublicJournal.java frontend/src/pages/car/Car04_Tab_PublicJournal.tsx
→ Car04_Tab_PublicJournal.java  SG  (조회 툴바 + 그리드 하나)
  Car04_Tab_PublicJournal.tsx  CG  (편집 가능한 그리드 하나)  ⚠ 선언 SG ≠ 판별 CG
```
  같은 결과가 `Car04_Tab_PrivateJournal`(T11), `Car04_Tab_PrivateJournalAdmin`(T12), `Car04_Tab_PublicJournal`(T14), `Car04_Tab_Journal`(T16)에서 반복됐다.
- (b) **같은 계열이 맞게 나오는 경우도 있다.** T15 `Car04_Tab_PublicJournalAdmin`은 AS-IS·TOBE 모두 `SGP`로 `일치`였다(툴바 + 그리드 + 편집 팝업 `*_Edit_*` 포함). 즉 TOBE에 `*_Edit_*`/팝업이 있으면 SGP로 가고, 없으면 CG로 떨어지는 것으로 보인다. SG의 기준(조회 툴바 + 그리드 하나, 조회창 `*_Lookup_*`만 있음)이 TOBE 쪽 판별에 반영되지 않은 듯하다.
- (c) **등록되지 않은 스타일은 `미분류`만 낸다.** T13 `Car03_Tab_List`(위 현황 그리드 + 아래 달력/그리드, 조회 툴바 없음)는 `미분류 (그리드 하나, 조회 툴바 없음)`이었다. 03 원칙 22에 따라 새 SID **GCG**를 `docs/page-style.md` 표에 등록했지만, 판별기는 그 표를 읽지 않아 `--compare`가 `⚠ 선언 GCG ≠ 판별 미분류`를 낸다. STP(Pay10_Tab_Retire)도 같은 사정으로 기록돼 있다.

**왜 문제인가**
- 03 원칙 22는 `page-style --compare`가 `일치`인지 확인하라고 하는데, 정상 변환인데도 불일치가 나와 매번 결과확인 13번에 "판별기 불일치" 사유를 적는다. 검사가 신호가 아니라 소음이 되고, 진짜 어긋난 화면을 놓칠 수 있다.

**고칠 것**
1. TOBE 판별 규칙을 AS-IS와 같은 기준으로 맞춘다.
   - SG: `SearchBar`(또는 조회 툴바) + 그리드 하나, 편집 팝업(`*_Edit_*`)이 **없고** 셀 편집 훅(`useGridCrud`)도 **없음**. 조회창(`*_Lookup_*`)·아이콘 열(`iconCell`)·`Modal.confirm`은 SG를 해치지 않는다.
   - CG: 그리드가 **셀 편집**(`CellEditGrid`/`useGridCrud`)일 때만. `SingleGrid`/`MultiGrid`는 CG 근거가 아니다.
   - SGP: 위 SG + 같은 파일에서 import한 `*_Edit_*`(편집 팝업).
2. 새 SID를 코드가 아니라 **설정으로** 등록한다. `docs/page-style.md`의 `## 스타일 목록` 표(SID·이름·구성)를 읽거나 `.yunhee.toml [page-style]`에 `{sid, 구성 설명}`을 받고, 표에 있는데 판별 규칙이 없는 SID는 `미분류`가 아니라 `선언(GCG)만 있고 판별 규칙 없음 — 비교 생략`으로 구분해 `불일치`로 세지 않는다.
3. `--explain` 옵션(또는 `-v`)으로 판별 근거(찾은 위젯: SearchBar, SingleGrid, iconCell, import된 *_Edit_* …)를 출력하게 한다. 규칙이 틀렸을 때 사용자가 즉시 원인을 볼 수 있다.

**검증 방법**
- 자기 검사: `yunhee page-style --compare <Tdm01_Tab_Hr.java> docs/page-style/SG/Tdm01_Tab_Hr.tsx` → `일치`(견본 자신이 불일치면 규칙이 틀린 것). SGP 견본(`docs/page-style/SGP/Chk02_Tab_DailyList.tsx`)도 같은 방식.
- 회귀 표(기대값):

| AS-IS 클래스 | TOBE 파일 | 기대 |
|:---|:---|:---|
| `Car04_Tab_PublicJournal` | `pages/car/Car04_Tab_PublicJournal.tsx` | SG 일치 |
| `Car04_Tab_Journal` | `pages/car/Car04_Tab_Journal.tsx` | SG 일치 |
| `Car04_Tab_PrivateJournal` | `pages/car/Car04_Tab_PrivateJournal.tsx` | SG 일치 |
| `Car04_Tab_PrivateJournalAdmin` | `pages/car/Car04_Tab_PrivateJournalAdmin.tsx` | SG 일치 |
| `Car04_Tab_PublicJournalAdmin` | `pages/car/Car04_Tab_PublicJournalAdmin.tsx` | SGP 일치 (현재도 통과 — 회귀 방지) |
| `Car03_Tab_List` | `pages/car/Car03_Tab_List.tsx` | GCG(선언) — 규칙이 없으면 "비교 생략", `불일치` 아님 |

- 셀 편집 그리드 화면(예: `Sys06_Tab_Menu` 계열 CG)은 여전히 CG로 나와야 한다(과교정 방지).
- 전체 `*_Tab_*` 일괄(`yunhee page-style --all`이 있다면)에서 판별 분포가 수정 전후로 어떻게 달라졌는지(SG↔CG 이동 건수)를 출력해 두면 영향 범위를 확인할 수 있다.
