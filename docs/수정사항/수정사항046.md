## 1. `api`/`compare`의 `-p`에 `%25`를 주면 서버에 `%25`가 글자 그대로 간다

**어떤 경우**
- LIKE 조건의 `%`를 파라미터로 줄 때 습관적으로 URL 인코딩된 `%25`를 썼다.

```
yunhee api GET v1/emp/benefits -p startDate=2020-01-01 -p closeDate=2026-12-31 -p benefitCode=%25 -p searchText= --log
→ HTTP 200, Rows: 0
  SQL 2: k.c.k.a.b.e.m.E.selectByText (28000, 2020-01-01, 2026-12-31, %25, %%) → Total 0
```
- 서버 로그의 바인딩 값이 `%25`이다. 즉 `yunhee`가 `-p` 값을 **한 번 더 인코딩**해서(`%` → `%25`, `%25` → `%2525`) 서버가 한 번 디코딩하면 `%25`가 남는다.
- `-p benefitCode=%`(인코딩 없이)로 주면 서버에 `%`가 가서 5행이 나온다.
- `compare`에서도 같은 증상: `--sql … --param searchText=%`(SQL 쪽은 그대로 `%`)와 API 쪽 `-p searchText=%25`를 맞춰 쓰면 `API rows=0, SQL rows=5 ❌` 또는 `API rows=7, SQL rows=10 ❌`처럼 **일부 행만 걸러진 불일치**가 나온다(`%25`가 "25로 끝나는 문자열" 검색이 되어, 제목에 `2025`가 든 행만 남는다).

**왜 문제인가**
- 결과가 0행이 아니라 *일부 행*이거나 *0행*이라 "서버 코드의 LIKE/조건이 틀렸다"로 읽힌다. 실제로 이번에 위 그리드의 필터 조건과 데이터를 한참 의심했다.
- `yunhee api`는 응답 외에 *서버가 받은 값*을 보여 주지 않으면(`--log`를 켜야 보인다) 원인 파악이 어렵다.
- 문서(05 §7 "`yunhee api`·`compare`")에 `%` 처리 규칙이 없다.

**고칠 것** (둘 중 하나, 가능하면 ①+③)
1. **이미 인코딩된 값은 다시 인코딩하지 않는다.** `-p k=v`의 `v`에 `%XX`(16진 두 자리) 패턴이 있으면 *이미 인코딩된 것으로 보고* 그대로 넘긴다. (`%`만 단독이거나 뒤가 16진 두 자리가 아니면 지금처럼 인코딩한다.)
   - 주의: 사용자가 일부러 리터럴 `%25`를 서버에 보내고 싶은 경우는 없다고 봐도 되지만, 필요하면 `--raw-param` 같은 탈출구를 둔다.
2. 아니면 현행(항상 한 번 인코딩)을 유지하되 **`%` 뒤에 16진 두 자리가 오는 값**을 만나면 경고한다: `⚠ -p searchText=%25 는 서버에 '%25'(글자 그대로)로 전달됩니다. '%'를 보내려면 -p searchText=% 로 주세요.`
3. 어느 쪽이든 `yunhee api --help`와 `docs/help/ops-and-log.md`(또는 05 §7)에 "LIKE용 `%`는 `-p k=%`로 준다"를 한 줄 적는다.

**검증 방법**
- (a) 서버가 받은 값 확인: `yunhee api GET v1/emp/benefits -p startDate=2020-01-01 -p closeDate=2026-12-31 -p benefitCode=% -p searchText= --log`의 `SQL` 줄 바인딩이 `(…, %, %%)`이어야 한다(`%25` 아님).
- (b) ①을 택했다면: 같은 명령에서 `-p benefitCode=%25`로 줘도 위와 같은 `(…, %, %%)`이 나오고 행 수(company 28000에서 5행)가 같아야 한다. ②를 택했다면 `%25` 입력 때 경고가 출력되어야 한다.
- (c) `compare` 회귀: `yunhee compare GET v1/emp/benefits -p startDate=2020-01-01 -p closeDate=2026-12-31 -p benefitCode=% -p searchText= --sql emp17_benefit.selectByText --param companyId=28000 --param startDate=2020-01-01 --param closeDate=2026-12-31 --param benefitCode=% --param searchText=%` → `API rows=5, SQL rows=5 ✅`.
- (d) 한글 등 비ASCII·공백·`&`·`+`가 든 값(`-p searchText="김 철수&x"`)은 종전처럼 한 번만 인코딩되어 서버에 원문으로 가는지 확인(①이 일반 인코딩을 깨뜨리지 않았다는 회귀).
- (e) 단위 테스트: 인코딩 함수에 `%`, `%25`, `%2`, `%ZZ`, `a%25b`, 한글, 공백 입력을 넣은 표 테스트.

## 2. `sql-check --tobe`가 "record DTO에 결과 열이 모자란다"를 일반 경고와 똑같이 취급해 서버 500을 못 막는다 (최우선)

**어떤 경우**
- DTO가 Java **record**이고 MyBatis가 생성자 자동 매핑(`Constructor auto-mapping`)을 쓰면, **결과 집합에 record의 모든 컴포넌트 열이 있어야** 한다. 하나라도 없으면 *행이 한 건이라도 있을 때* 예외가 난다. (일반 setter 클래스는 없는 열을 무시한다.)
- 이번에 `BenefitRes`(컴포넌트 18개)에 대해 일부 열만 SELECT하는 조회 세 개를 만들었다.

```
yunhee sql-check --tobe backend/src/main/resources/mapper
… EmpBenefitMapper: selectByText ✅ ⚠ (필드 누락: accountName) /
                    selectCodesByIds ✅ ⚠ (필드 누락: accountName, apprId, apprStatusCode, apprStatusName, apprTitleName, benefitDetail, benefitYn, companyId, issueAmt, issueDate, note, occDate, payRequestYyyymm, personId, personName) /
                    selectById ✅ ⚠ (필드 누락: accountName, apprStatusName, …)
```
- `✅`(SQL이 DB에서 돈다)와 `⚠ (필드 누락 …)`이 *같은 줄*에 나오고, `select *`에서 일부러 열을 줄인 정상 경우도 같은 모양의 경고를 낸다. 그래서 "경고지만 괜찮겠지"로 넘겼고, 배포 후 행이 있는 조회에서 **HTTP 500**이 났다.
- 서버 로그(`yunhee log errors`)의 원인:

```
org.apache.ibatis.executor.ExecutorException: Constructor auto-mapping of 'public …BenefitRes(java.lang.Long, …)' failed because '[accountName]' were not found in the result set; Available columns are '[benefit_id, company_id, …]' and mapUnderscoreToCamelCase is 'true'.
```
- 더 나쁜 점: 이 500은 **0행일 때는 나지 않아서** `GET`이 `Rows: 0`으로 정상 응답했고, 첫 배포·API 시험(`API rows=0, SQL rows=0 ✅`)이 모두 통과했다. 데이터가 있는 달·회사로 시험했을 때 비로소 드러났다(수정사항045 §1과 같은 가림 효과).

**왜 문제인가**
- 이 경고는 *record DTO + 일부 열*일 때만 **런타임 오류가 확정**인데, 도구가 그 구분을 하지 않아 사람이 매번 DTO 종류를 확인해야 한다. 확인하지 않으면 배포 후 데이터 있는 요청에서만 터지는 버그가 된다.
- AssetERP는 신규 DTO를 record로 쓰는 것이 규칙(`TOBE-Framework.md`)이라 이 상황이 앞으로 계속 생긴다.

**고칠 것**
1. `sql-check --tobe`가 `resultType`(또는 resultMap)의 DTO 클래스를 읽어 **record인지** 판정한다(소스 `public record X(…)` 또는 컴파일된 클래스의 `isRecord`; 소스 파싱이면 `record 이름(` 패턴으로 충분). record이면 컴포넌트 이름(camelCase → 스네이크 변환은 `mapUnderscoreToCamelCase` 규칙과 동일하게)이 **결과 열에 전부 있는지** 검사한다.
2. 모자라면 일반 경고(`⚠`)가 아니라 **오류 등급**으로 표시하고 종료 코드를 0이 아니게 한다.
   - 출력 예: `selectByText ❌ record BenefitRes 열 누락: accountName — 결과에 열이 없으면 행이 있을 때 MyBatis가 'Constructor auto-mapping … not found in the result set'으로 500을 낸다. SELECT에 'NULL AS account_name'을 더하거나 열 목록 <sql>을 공유하세요.`
3. 일반(setter) 클래스의 "필드 누락"은 지금처럼 `⚠`로 둔다(오류 아님). 결과에 *DTO에 없는* 열(남는 열)은 두 경우 모두 무시되므로 경고하지 않는다.
4. 컬럼 별칭이 같은 SQL이 `<sql>`+`<include>`로 펼쳐지는 경우(수정사항 U02 교훈: `sql-check`가 `include`를 못 펼친다)에는 *검사 불가*임을 명시한다(`? include 미해결 — mapper-run으로 확인`). 거짓 ❌를 내지 않는 것이 우선이다. 이번 최종 매퍼는 `<include refid="benefitColumns"/>`를 쓰므로 이 분기가 실제로 걸린다(§검증 (d)).

**검증 방법**
- (a) 재현: `EmpBenefitMapper.xml`의 `selectByText`에서 `, NULL AS account_name` 한 줄을 지운 상태(또는 아래 최소 예)로 `yunhee sql-check --tobe backend/src/main/resources/mapper` → 해당 statement가 `❌ record BenefitRes 열 누락: accountName`이고 종료 코드 ≠ 0이어야 한다. 최소 예: record `R(Long id, String name)`에 `SELECT id AS id FROM t`.
- (b) 오탐 없음: 위 열을 되돌린 최종 매퍼에서는 `selectByText`, `selectCodesByIds`, `selectById`가 경고 없이 통과해야 한다. 열이 전부 있는 `selectByBenefitCode`도 통과.
- (c) setter 클래스 DTO(예: record가 아닌 기존 DTO)에서 열이 모자란 statement는 `⚠`만 나오고 종료 코드는 0.
- (d) `<sql>`/`<include>`로 열 목록을 공유하는 statement(현재 `selectByText`·`selectCodesByIds`·`selectById`가 `benefitColumns`를 include)는 거짓 ❌ 없이 "검사 불가/펼침 결과로 통과" 중 하나로 나와야 한다. 펼칠 수 있게 구현했다면 열이 전부 있음을 정확히 판정해야 한다(a의 삭제 상태에서는 ❌).
- (e) 회귀: 전체 매퍼 실행 시간이 크게 늘지 않아야 하고(DTO 파싱은 파일당 한 번 캐시), 기존 출력 형식(`✅`/`⚠`/`❌ ERROR`)은 유지.
- (f) 단위 테스트: ① record+열 부족 → 오류 ② record+열 충분 → 통과 ③ 일반 클래스+열 부족 → 경고 ④ record+별칭 대소문자·스네이크/카멜 변환(`appr_title_name` ↔ `apprTitleName`) → 통과.

## 3. 새 SID `GGH`(Grid+Grid 좌우) 판별 추가 방법 (AssetERP U08, 2026-10-30)

**배경**: `Pay50_Tab_ExpensePay`(1400)는 위에 조회 툴바, 아래가 **좌우 분할**(왼쪽 마스터 그리드 680 / 오른쪽 상세 그리드)이다. 상하 분할인 `GG`와 달라 AssetERP에서 새 SID `GGH`로 `docs/page-style.md`에 등록했다(견본 `docs/page-style/GGH/Pay50_Tab_ExpensePay.tsx`, 점검 규칙은 `tools/page-style-check.py GGH`). 지금 `yunhee page-style`은 AS-IS·TOBE 모두 `GG (그리드 2개(마스터·상세))`로 읽는다.

**지금 상태 (0.6.9, `src/yunhee/tools/page_style.py`)**
- 유효한 SID 목록은 `load_valid_sids()`가 `page-style.md`의 "## 스타일 목록" 표 첫 열에서 읽으므로, **표에 `GGH` 행을 넣으면 선언 `스타일: GGH`는 이미 유효하다**(경고 "유효한 SID 목록에 없습니다"는 표를 고치기 전에만 나온다). `DEFAULT_SIDS`(19개)는 표를 못 찾을 때의 대체값이다.
- 남는 문제는 판별이다: `yunhee page-style --compare … Pay50_Tab_ExpensePay.java …tsx` → `⚠ 선언 GGH ≠ 판별 GG`.
- 원인은 §7 "그리드 2개 이상 → GG"(`if g >= 2: return "GG"`)가 `layout`을 보지 않기 때문이다. 위의 §6(`has_tabs and layout == "vertical"`)만 상하 분할을 본다.

**고칠 것 (순서대로)**
1. `DEFAULT_SIDS`와 모듈 머리 docstring(5행)의 SID 나열에 `GGH`를 더한다(`"GG"` 다음).
2. 판별 규칙을 `# 7. 그리드 2개 이상 (GG)` **바로 앞**에 넣는다. GDP(§4 규칙)와 같은 자리에서 `layout == "horizontal"`을 쓴다:
   ```python
   # 6-1. GGH (Grid+Grid 좌우): 위 SearchBar + 가로 Splitter + 그리드 2개(오른쪽이 *_Page_*/*_TabPage_* 컴포넌트가 아니다)
   if (
       g >= 2
       and layout == "horizontal"
       and (top_search or search)          # 조회 줄이 SearchBar. 버튼 줄이면 GDP 쪽
       and not has_detail_page
       and t == 0
   ):
       return "GGH", f"위 조회 줄 + 좌우 분할 그리드 {g}개(마스터·상세)"
   ```
   - `top_search`/`search` 변수는 §3(SGT) 규칙이 이미 쓰는 것과 같은 의미로 맞춘다(전체 폭 위쪽 `SearchBar`). 실제 변수 이름·의미는 `page_style.py`의 특징 추출부(§3 위쪽)를 보고 맞춘다.
   - 선언 우선: `declared == "GGH"`이고 `g >= 2`, `layout == "horizontal"`이면 조건을 완화해 `GGH`를 낸다(다른 SID와 같은 방식, §2-1).
   - 순서: SGT(트리+그리드 좌우)·GDP(버튼 줄+오른쪽 페이지)·SGHF(폼 좌우)보다 **뒤**, 일반 GG(§6·§7)보다 **앞**. GDP와는 "조회 줄이 SearchBar인가 / 오른쪽이 페이지 컴포넌트인가"로, GG와는 `layout`으로 가른다.
3. **AS-IS(GXT)쪽 레이아웃**: `Pay50_Tab_ExpensePay.java`는 `setNorthWidget`/`setWestWidget`/`setCenterWidget`(BorderLayout)이다. 위 `layout == "horizontal"`이 Java 쪽에서도 서도록, West+Center 두 그리드를 가로 분할로 읽는 기존 처리(SGT·GDP가 쓰는 것)를 그대로 쓰는지 확인한다. 안 되면 `JAVA_GRID` 계열 특징에 `west/center` 존재를 `layout="horizontal"`로 올리는 보강이 필요하다.
4. `docs/yunhee-page-style-판별.md`(AssetERP)의 §2 SID별 판별 규칙 표에 `GGH` 행을 더하고, §4-4 다음에 "4-5. 새 SID GGH" 절을 둔다(기대 화면: `Pay50_Tab_ExpensePay`). 이 파일은 AssetERP 쪽 요청서라 yunhee 저장소가 아니라 `framework-sprt/AssetERP/docs/`에 있다.
5. `src/yunhee/CHANGELOG.md`에 "page-style: 새 SID GGH(좌우 분할 마스터-상세) 판별" 한 줄. 다른 SID와 같이 `docs/help/migration.md`의 SID 목록 설명이 있으면 한 줄 더한다.

**검증 방법**

- (b) 회귀: GG 견본(`Est02_Tab_PfResultReport`)은 그대로 `GG`(상하 분할), GDP 4개(`Sms02_Tab_TotalCount`·`Sys10_Tab_TotalSize`·`Sms03_Tab_SendAdmin`·`Ics02_Tab_Manager`)는 그대로 `GDP`, SGT 견본 `Fnd08_Tab_OrgAuth`는 `SGT`.
- (c) `yunhee page-style --all`의 분포에서 `GG`가 줄고 `GGH`가 생기는 화면 목록을 보고, GGH가 된 화면이 실제로 좌우 분할 + 위 SearchBar인지 샘플 3개를 연다(오판이면 규칙의 `top_search` 조건을 조인다).
- (d) 단위 테스트: ① 가로 Splitter + SearchBar + 그리드 2개 → `GGH` ② 세로 Splitter + 그리드 2개 → `GG` ③ 가로 + 버튼 줄(SearchBar 아님) + 오른쪽 `*_TabPage_*` → `GDP` ④ 가로 + 트리 + 그리드 → `SGT` ⑤ 선언 `스타일: GGH` + 가로 + 그리드 2개 → `GGH`.

**같이 보이는 것 (별도 요청 가능)**: AssetERP U07 `Pay50_Tab_ExpensePayWrite`는 원본이 SG(툴바 + 그리드 하나)인데 TOBE를 `CellEditGrid`로 만들면 `--compare`가 `TOBE CG`로 읽는다(`⚠ 선언 SG ≠ 판별 CG`). 판별기가 §8 "단일 그리드"에서 `editable_grid`를 SG보다 먼저 보기 때문이다. 선언이 `SG`이고 CG 판별 근거가 `editable_grid`뿐이면 선언을 우선하는 규칙(§2-1과 같은 방식)이 필요하다.

## 참고: 같은 세션에서 확인한 것 (수정 불필요)
- `yunhee compare`로 `API rows=N, SQL rows=N ✅ fields ⊇ grid cols`, `analysis ui --tobe`의 이벤트 누락 지적, `run`의 실패 요약은 정확했다.
- 같은 정보 요청이지만 이번에 수정 대상으로 올리지 않은 것(우선순위 낮음): ① `sql-check --tobe` 출력이 매퍼 전체라 `grep`으로 걸러야 한다(매퍼 이름 인자 지원 제안), ② `api --log`가 500일 때 `Caused by` 첫 줄을 보여 주면 좋겠다(§2의 원인을 `log errors`로 따로 찾았다), ③ `compare`가 `0=0`일 때 ✅ 대신 ⚠(필드 비교 못 함)로 구분하면 좋겠다.
