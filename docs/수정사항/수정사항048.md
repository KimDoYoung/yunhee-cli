## 1. AS-IS SQL이 DB에 없는 함수를 써도 `port-sql`·`analysis sql`이 알려 주지 않는다

**어떤 경우**
- 증빙자료 창의 [불러오기](tdm52)를 옮기려고 AS-IS SQL `dcr00_doc_list.selectNoAuthByText`를 봤다. 이 SQL은 DB 함수 `f_get_apprDcrAuth(…)`를 쓴다.

```
yunhee port-sql dcr00_doc_list.selectNoAuthByText
→ <!-- 1. 매퍼 조각 -->
  <sql id="apprColumns">
      ROW_NUMBER() OVER() AS id,
      f_get_apprDcrAuth(apr01_company_id, #{empId}, #{orgId}, apr01_appr_id) AS auth_yn,
  …                                   ← 경고 없이 매퍼를 만들어 준다
```

- 그런데 이 함수는 asseterpdb에 없다.

```
yunhee sql "SELECT f_get_apprDcrAuth(1::numeric,1::numeric,1::numeric,1::numeric)"
→ HINT:  No function matches the given name and argument types.
yunhee sql "SELECT proname FROM pg_proc WHERE proname ILIKE '%dcrauth%'"   → 0건
```

- `docs/as-is/sql-check.md`에도 이 SQL이 없다. 원인: SQL과 함수가 AS-IS에 들어온 것은 **2026-10-28**(IDMS-IC `7ec7ea2b0` "[10/28]문서불러오기 책무예외사항 적용")이고, sql-check.md는 **10-22**에 만든 것이다. `./check-git.sh`는 `index-src`만 다시 돌리고 `sql-check`는 돌리지 않는다(`check-git.sh:76`). 즉 **원본은 새 함수를 쓰기 시작했는데 로컬 DB에는 그 함수가 없고, 이를 알려 주는 곳이 없다.**
- 나는 `pg_proc`를 따로 조회하고서야 알았다. 몰랐다면 이 매퍼를 그대로 넣고 배포 뒤 500을 봤을 것이다.

**왜 문제인가**
- 변환 가이드 1절: "필요한 것이 DB에 없으면 그 ID는 `보류`". 이 판단은 SQL을 옮기기 **전에** 나와야 한다. 지금은 `port-sql` → 손질 → `sql-check --tobe`(TOBE 매퍼 EXPLAIN)까지 가야 걸리고, `port-sql` 결과를 크게 고친 뒤라 낭비가 크다.
- AS-IS는 매일 바뀌므로(변경반영 작업), 원본에 새로 생기는 함수·테이블·열은 계속 나온다.

**고칠 것**
1. `port-sql`과 `analysis sql -o sql`이 결과 SQL을 만든 뒤, 그 SQL이 쓰는 **DB 객체(함수·테이블·열)가 대상 DB에 있는지** 확인해 맨 위에 경고를 낸다. 가장 간단한 방법은 `sql-check`가 이미 하는 EXPLAIN(파라미터는 NULL·타입 캐스트)을 그 SQL 하나에 돌리는 것이다.
   - 예: `⚠ DB에 없는 객체: function f_get_apprDcrAuth(numeric, numeric, numeric, numeric) — 변환 가이드 1절에 따라 보류 검토`
   - EXPLAIN이 동적 SQL 때문에 실패하면 "확인 못 함"이라고만 적고 결과는 그대로 낸다.
2. `analysis sql`(md 출력)에 그 SQL의 **sql-check 상태 한 줄**을 붙인다: `sql-check: 통과 / 없는 객체(…) / 결과 없음(sql-check.md가 이 SQL보다 오래됨 — 2026-10-22 생성)`. sql-check.md 생성일과 색인(또는 원본 파일 git 날짜)을 비교해 "오래됨"을 판단한다.
3. (선택) `index-src`나 `drift`가 "색인 기준 이후 새로 생긴 SQL"을 알 수 있다면, 그 SQL만 EXPLAIN하는 `sql-check --new-since-index`(또는 `--changed-asis`)를 만든다. 그러면 `check-git.sh`에 한 줄 추가로 매일 새 SQL만 검사할 수 있다.

**검증 방법**
- (a) `yunhee port-sql dcr00_doc_list.selectNoAuthByText` → 맨 위에 `f_get_apprDcrAuth`가 DB에 없다는 경고가 나와야 한다(매퍼는 그대로 만들어도 된다).
- (b) `yunhee analysis sql dcr00_doc_list.selectNoAuthByText` → 같은 경고 + `sql-check: 결과 없음(sql-check.md가 더 오래됨)` 한 줄.
- (c) 회귀: DB에 객체가 다 있는 SQL(`dcr00_doc_list.selectByText`, `crm09_contact.selectBiz02Emp`)에는 경고가 없어야 한다. `analysis sql crm09_contact.selectBiz02Emp`의 상태 줄은 sql-check.md에 있으면 `통과`.
- (d) 없는 열 예: sql-check.md "없는 DB 객체" 첫 줄의 `chk03_daily_list_write.selectDailyListStatusPaging`(`sch22_confirmer_id` 없음) → `port-sql`에 열 경고가 나와야 한다.
- (e) 3을 만들었다면: `yunhee sql-check --new-since-index` 결과에 `dcr00_doc_list.selectNoAuthByText`가 "없는 DB 객체"로 나와야 한다.

## 2. `analysis sql`이 서비스 이름(`dom.Class.method`)을 받지 못하고 힌트도 없다

**어떤 경우**
- AS-IS 클라이언트 코드에는 서비스 이름이 적혀 있다: `new ServiceRequest("ics.Ics40_DcrPreconfirm.selectByApprId")`, `service.retrieve("crm.Crm09_Contact.selectBiz02Emp", …)`. 이 이름을 그대로 넣으면:

```
yunhee analysis sql ics.Ics40_DcrPreconfirm.selectByApprId -o sql
→ [ERROR] statement를 찾을 수 없습니다: ics.Ics40_DcrPreconfirm.selectByApprId
yunhee analysis sql dcr.Dcr00_DocList.selectByText -o sql
→ [ERROR] statement를 찾을 수 없습니다: dcr.Dcr00_DocList.selectByText
```

- 매퍼 이름으로 주면 된다: `yunhee analysis sql ics40_dcr_preconfirm.selectByApprId -o sql` → SQL이 나온다.
- 이번 세션에서 세 번 이 오류를 만났고, 세 번 다 매퍼 XML을 `grep -n`으로 찾아 `yunhee cat`으로 읽었다(규칙상 피해야 하는 경로).

**왜 문제인가**
- 서비스 이름 → 서버 메서드 → `sqlSession.selectList(mapperName + ".selectByApprId")` → 매퍼 문장은 색인이 이미 아는 연결이다(`analysis method <클래스>.<메서드> --server`가 따라간다). 사용자(에이전트)가 바꿔 넣어야 할 이유가 없다.
- 오류에 후보가 없어서 "SQL이 없다"로 오해하기 쉽다.

**고칠 것**
1. 인자가 `dom.ClassName.method` 꼴이고 매퍼 문장으로 못 찾으면, 서버 클래스 `server/{dom}/{ClassName}.java`의 그 메서드에서 부르는 매퍼 문장(`mapperName + ".id"` 또는 `"ns.id"` 리터럴)을 찾아 그 SQL을 보여 준다. 첫 줄에 `서비스 ics.Ics40_DcrPreconfirm.selectByApprId → 매퍼 ics40_dcr_preconfirm.selectByApprId`.
2. 메서드가 여러 문장을 부르면 목록을 보여 주고 고르게 한다(또는 모두 출력).
3. 그래도 못 찾으면 오류에 후보를 적는다: `비슷한 문장: ics40_dcr_preconfirm.selectByApprId (매퍼 이름은 '테이블.id' 꼴입니다)`.
4. `port-sql`·`compare --sql`도 같은 해석을 쓴다.

**검증 방법**
- (a) `yunhee analysis sql ics.Ics40_DcrPreconfirm.selectByApprId -o sql` → `ics40_dcr_preconfirm.selectByApprId`의 SQL(`WHERE ics40_appr_id = #{apprId}`).
- (b) `yunhee analysis sql crm.Crm09_Contact.selectBiz02Emp -o sql` → `crm09_contact.selectBiz02Emp`의 SQL(`UNION`이 든 것).
- (c) `yunhee analysis sql dcr.Dcr00_DocList.selectNoAuthByText` → `dcr00_doc_list.selectNoAuthByText`(서버 `Dcr00_DocList.java:174-175`가 `mapperName + ".selectNoAuthByText"`를 부른다).
- (d) 없는 이름 `yunhee analysis sql ics.Ics40_DcrPreconfirm.noSuch` → 오류 + 후보 목록(같은 매퍼의 문장들).
- (e) 회귀: 매퍼 이름 입력(`ics40_dcr_preconfirm.selectByApprId`)은 지금과 같은 결과.

## 3. TOBE의 "미연결 자리"(다음 단계 안내)를 모아 주는 명령이 없다

**어떤 경우**
- AssetERP `docs/변환/13-누락대장.md`는 TOBE에서 창을 열어야 할 자리에 `message.info('…다음 단계에서 연결됩니다')` 같은 안내만 있는 곳을 메뉴별로 모은 할 일 목록이다. 2026-11-05에 손으로 조사해 만들었다(Tab 377개와 하위 파일을 모두 읽음).
- 이번 세션에서 1번 작업을 한 뒤 3번 작업의 **줄 번호가 밀려** 목록의 줄로 바로 갈 수 없었다(예: 목록 `Apr16_Lookup_StampDocReg.tsx:154` → 실제 168). 결국 파일마다 `yunhee grep "다음 단계|연결됩니다|아직 변환"`을 다시 돌렸다.
- `trace-gap`(ASIS에만 있는 화면·서비스)은 이 종류를 다루지 않는다(`yunhee trace-gap -d emp --side tobe`로 확인).

**왜 문제인가**
- 13-누락대장은 계속 갱신해야 하는 목록인데, 지금은 다시 만들려면 사람(에이전트)이 전체를 다시 읽어야 한다.
- 안내 문구가 화면마다 조금씩 달라서(`다음 단계에서 연결됩니다`, `다음 단계에서 제공됩니다`, `아직 변환 전입니다(다음 단계)`, `[E6 생략] …다음 단계`) grep 한 줄로는 빠지거나 넘친다.

**고칠 것**
1. 새 명령(예: `yunhee trace-gap --stubs` 또는 `yunhee stubs`)이 TOBE `frontend/src`에서 미연결 자리를 찾아 표로 낸다: `파일:줄 | 문구 | 가장 가까운 [E…] 주석 | 여는 화면(그 파일을 import하는 _Tab_ 화면) | 메뉴 번호`.
2. 찾는 기준(설정 가능하게):
   - `message.info/warning(…)`의 글자에 `다음 단계`·`아직 변환`·`연결됩니다`·`연결합니다`·`제공됩니다`가 있는 것
   - `// [E\d+ 생략]` 주석
   - 머리 주석의 `1단계:` / `다음 단계:` 줄(자리 목록과 따로, "화면 머리에만 남은 것"으로)
3. 메뉴 번호는 `pages/screens.ts` 등록과 `docs/as-is/menus.tsv`로 붙인다(13-누락대장의 "`#1385 (Pay50_Tab_ExpenseManager)`" 꼴).
4. `-o md`는 13-누락대장 각 줄과 같은 꼴(`- [ ] \`파일:줄\` — 메뉴명 #번호 (\`Tab 클래스\`)`)로 내면 목록을 그대로 갈아 끼울 수 있다.

## 4. "이 창을 누가 어떤 인자로 여는가"를 AS-IS에서 한 번에 볼 수 없다

**어떤 경우**
- 판촉물 구매(#1135) 상대방 성명이 여는 `Crm09_Lookup_SelectSingle`은 TOBE에 이미 있었지만 `open("keyInCompany")` 모드만 만들어져 있었다. 원본 이 자리는 `open("emp")`(다른 SQL `selectBiz02Emp`, 열 2개)를 쓴다. 이를 알기까지 `analysis method … -o code`로 `setting`·`retrieve`·`buildGrid`를 차례로 읽었다.
- 호출부와 인자는 `yunhee grep "new Crm09_Lookup_SelectSingle" ~/work/IDMS-IC/…/client -C 2`로 찾았다 → 2곳(`Biz01_TabPage_List.java:209` `open("emp")`, `Biz01_Tab_PriorApprovalSimple.java:270` `open("keyInCompany")`).
- `analysis screen Crm09_Lookup_SelectSingle --list`는 클래스 자체(버튼 3·이벤트 5·그리드 1)만 보여 주고, 누가 여는지는 없다. `trace-code`는 공통코드용이다.

**왜 문제인가**
- 조회창·편집창은 "모드(open/view/edit, code 글자)"마다 SQL과 열이 다르다. 미연결 창을 이을 때마다 "TOBE 창이 이 모드를 지원하는가"를 확인해야 하는데(이번 세션에서 `Ics40_Edit_Msg.editRegEmpMsg`, `Crm09 "emp"`, `Apr05_Lookup_LoadDoc2` tdm52 세 번), 그 출발점이 호출부 목록이다.

**고칠 것**
1. `yunhee analysis callers <클래스>`(이름은 자유): AS-IS에서 그 클래스를 `new`하는 곳마다 `파일:줄 | 부른 메서드(open/view/edit/gridInsert…) | 리터럴 인자 | 감싼 메서드 | 메뉴`를 표로 낸다.
2. `--tobe frontend/src`를 주면 TOBE에서 그 컴포넌트를 렌더하는 곳(`<Crm09_Lookup_SelectSingle … code="emp"`)도 같은 표에 나란히 놓아, 원본 호출부 중 TOBE에 짝이 없는 줄을 표시한다.

**검증 방법**
- (a) `yunhee analysis callers Crm09_Lookup_SelectSingle` → 2줄: `Biz01_TabPage_List.java:209 open("emp") openLookupTargetInfo`, `Biz01_Tab_PriorApprovalSimple.java:270 open("keyInCompany")`.
- (b) `yunhee analysis callers Tdm00_Lookup_RelateAppr` → 5곳(자기 생성자 `Tdm00_Lookup_RelateAppr.java:50`은 빼고): `Tdm52_Edit_ChckManl.java:403` lookupFile(view/open "tdm52" — `if` 두 갈래라 둘 다 나와야 한다), `Tdm52_Edit_ChckManlBatch.java:190` lookupFile(open "tdm52"), `Tdm52_Edit_ChckManlCmnt.java:178`(view "tdm52"), `Tdm54_Lookup_ChckInsuff.java:605`, `Tdm54_Lookup_ChckInsuffCmnt.java:398`(view "tdm63"). `new` 줄과 `open/view` 줄이 떨어져 있어 `grep -C 1`로는 3곳만 인자가 보였다 — 메서드 안에서 그 변수의 호출을 따라가야 한다.
- (c) `--tobe frontend/src`: 위 (a)의 두 줄이 TOBE `Biz01_TabPage_List.tsx`(`code="emp"`)·`Biz01_Tab_PriorApprovalSimple.tsx`와 짝지어져야 한다.

## 5. 쓰기 API 시험에서 만든 행을 찾고 지우는 일이 길다

**어떤 경우**
- 변환 가이드 3절 3: "저장 API: 시험 행 등록 → 수정 → 삭제로 되돌린다". 이번에 새 POST 2개를 이렇게 시험했다.

```
yunhee api POST /api/v1/biz/people/external -c kfstest -b '{"promoId":…,"targets":[{"targetCompanyName":"시험회사",…}]}'
→ Data: 1                               ← 건수만 온다(새 ID는 없다)
yunhee sql "SELECT biz02_person_id FROM biz02_person WHERE … '시험회사' …"   ← 새 행 ID를 따로 찾는다
yunhee api DELETE /api/v1/biz/people -c kfstest -b "[<ID>]"
yunhee sql "SELECT count(*) FROM biz02_person WHERE biz02_person_id=<ID>"    ← 남았는지 다시 본다
```

- 호출 4번, 그중 2번은 손으로 쓴 SQL이다.

**고칠 것**
1. `yunhee api … --track <테이블>[,<테이블>]`: 호출 전후로 그 테이블의 행 수와 **새로 생긴 PK**(PK 열은 `information_schema`로)를 보여 준다. 예: `biz02_person: 72 → 73 (+1: biz02_person_id=202611059035758)`.
2. `--cleanup`(선택, `--track`과 함께): 끝에 새로 생긴 행을 그 테이블에서 지운다. 실제 운영 DB가 아니라 `YUNHEE_DB`가 로컬일 때만 허용하고, 지운 건수를 출력한다. (API의 삭제 경로를 시험하려면 쓰지 않는다.)
3. `--track`만으로도 "시험 행이 남지 않았는가" 확인이 한 줄로 끝난다.

**검증 방법**
- (a) `yunhee api POST /api/v1/biz/relate-apprs/promo -c kfstest -b '{"promoId":202204280115828,"apprId":202509189046469}' --track biz05_relate_appr` → `biz05_relate_appr: n → n+1 (+1: biz05_relate_appr_id=…)`.
- (b) 그 ID로 `yunhee api DELETE /api/v1/biz/relate-apprs -c kfstest -b '[…]' --track biz05_relate_appr` → `n+1 → n (-1)`.
- (c) 실패 호출(`promoId`=1, 다른 회사) `--track biz05_relate_appr` → 400 + `변화 없음`.
- (d) `--cleanup`: (a)에 붙이면 끝에 `정리: biz05_relate_appr 1건 삭제`, 이후 `yunhee sql "select count(*) from biz05_relate_appr"`가 호출 전과 같다.
