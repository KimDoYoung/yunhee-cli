# 수정사항 051 — `trace-crud`·`trace-pair` 오탐, `api`의 테넌트·세션·응답 필터, `log trace` 원인 표시

## 1. `trace-crud` — TOBE 쓰기(C/U/D)를 못 센다 (우선순위 높음)

TOBE에 쓰기 API·매퍼가 있고 실제로 동작하는데(`api --track`으로 행 수 변화 확인) "⚠ TOBE에 … 없음"으로 나온다.

| 재현 | 출력 | 실제 |
|:---|:---|:---|
| `trace-crud --screen '#1077'` | `sys06_menu: ASIS CRUD / TOBE RUD ⚠ TOBE에 C 없음` | `SysMenuMapper.xml:427` `<insert id="insertMenu">` ← `SysMenuService.createMenu` ← `POST /api/v1/sys/menus` (화면 `Sys06_Edit_Menu`가 `sysApi.saveMenu`로 부름 — trace-pair는 이 짝을 찾음) |
| `trace-crud --screen '#1360'` | `sys06_menu: ASIS CRU / TOBE R ⚠ TOBE에 CU 없음` | `SysMenuGuideMapper.xml:64` `<update id="updateNote">` ← `PUT /api/v1/sys/menu-guides` |
| `trace-crud --screen '#1078'` | `sys08_code_kind: TOBE R ⚠ CUD 없음`, `sys09_code: TOBE RD ⚠ CU 없음`, `sys13_code_group: TOBE CR ⚠ UD 없음` | 세 테이블 모두 등록·수정·삭제가 API로 동작(§2의 `save:`/`remove:` 경로) |
| `trace-crud --screen '#1197'`·`--table sys80_admin_user_list` | `ASIS CRUD / TOBE -  (다른 화면에 있음: SysAdminUserListMapper)` / `⚠ TOBE에 CRUD 없음` | `Sys80_Tab_AdminUserList.tsx` → `SysAdminUserListController` `GET·PUT·DELETE` → `SysAdminUserListMapper` (같은 화면) |

- 원인 후보 (a): 화면 → API 사슬을 §2와 같은 이유로 놓친다(#1078·#1197).
- 원인 후보 (b): #1077·#1360은 사슬은 찾았는데(trace-pair가 짝을 냄), 그 API가 부르는 **매퍼 문장의 테이블**을 C/U로 세지 않는다. `<insert>`·`<update>`·`<delete>` 태그와 본문의 `INSERT INTO`·`UPDATE`·`DELETE FROM` 대상 테이블을 쓰기로 센다.
- "다른 화면에 있음"이 같은 화면의 매퍼라면 그 매퍼를 이 화면의 것으로 본다.
- 확실하지 않으면 `⚠ 없음` 대신 `? (못 셈 — 사유)`로 적는다. `없음`은 "TOBE에 기능이 빠졌다"는 결론으로 바로 이어진다.

## 2. `trace-pair` — 함수를 객체 속성으로 넘기면 "TOBE 호출"을 못 찾는다 (우선순위 높음)

CRUD 그리드 부품(`useCrudGrid` 등)에 API 함수를 **부르지 않고 넘기는** 꼴을 따라가지 못한다.

```tsx
// frontend/src/pages/sys/Sys08_Tab_CodeKindAdmin.tsx:54-55
save: sysApi.updateCodeKinds,
remove: sysApi.deleteCodeKinds,
```

| 재현 `trace-pair '#1078'` | "TOBE 호출" | 실제 호출부 |
|:---|:---|:---|
| `sys.Sys08_CodeKind.update ↔ PUT /api/v1/sys/code-kinds` | 빈칸 | `Sys08_Tab_CodeKindAdmin.tsx:54` |
| `sys.Sys08_CodeKind.delete ↔ DELETE /api/v1/sys/code-kinds` | 빈칸 | `Sys08_Tab_CodeKindAdmin.tsx:55` |
| `sys.Sys09_Code.update ↔ PUT /api/v1/sys/codes` | 빈칸 | `Sys09_Grid_Code.tsx:60` |
| `sys.Sys13_CodeGroup.update ↔ PUT /api/v1/sys/code-groups` | 빈칸 | `Sys13_Lookup_CodeGroup.tsx:44` |
| `sys.Sys13_CodeGroup.deleteAll ↔ DELETE /api/v1/sys/code-groups` | 빈칸 | `Sys13_Lookup_CodeGroup.tsx:45` |
| `sys.Sys13_CodeGroup.delete ↔ DELETE /api/v1/sys/code-groups/members` | 빈칸 | `Sys13_TabPage_Code.tsx:58` |

- `sysApi.xxx(` 호출뿐 아니라 `sysApi.xxx` **참조**(객체 속성 값, 함수 인자, `const f = sysApi.xxx`)도 호출부로 센다.
- 이 수정이 §1 (a)도 함께 푼다(같은 사슬을 쓴다면).

## 3. `api -c <회사>`가 그 회사 주소(테넌트)로 접속하지 않는다 (우선순위 높음)

- `yunhee api … -c kalpa`는 **admin 주소**로 접속하고 회사코드 `kalpa`를 로그인 본문에 넣는다. 머리 줄도 `tenant=admin · company=kalpa`.
- TOBE 서버는 로그인 보안(공인IP)을 **접속 주소의 테넌트**로 검사한다(`AuthService.login` L82-89). 그래서 kalpa의 IP 제한을 켜 두어도 `-c kalpa`로는 막히지 않아 "기능이 안 된다"로 잘못 읽었다. `-c kalpa -t kalpa`로 해야 막혔다(SYS-BZ-0017).
- `--base http://kalpa.localhost:8082/AssetERP`를 줘도 `tenant=admin` 그대로였다 — `X-Tenant-Id`(기본 admin)가 호스트보다 앞서는 것으로 보인다. **버그로 본다**: `--base`의 서브도메인이 있으면 테넌트도 그것으로.
- 제안: `-c X`(X가 admin이 아닌 회사)면 기본 테넌트도 X. admin 주소에서 회사를 골라 들어가는 경우만 `-t admin`으로 명시. 머리 줄에 실제 접속 URL(호스트)을 함께 찍는다.

## 4. `api`가 로그인 세션을 다시 써서 로그인 시점 검사를 다시 보지 못한다 (우선순위 중간)

- 공인IP를 허용한 뒤 로그인 성공 → 그 IP의 종료일을 어제로 바꿈 → `yunhee api GET … -c kalpa -t kalpa`가 **200**. 새로 로그인하지 않고 세션을 다시 썼다(`yunhee log req POST /api/auth/login`에 로그인이 1건뿐). `POST /api/auth/login`을 직접 부르자 401 `IP_NOT_ALLOWED`.
- 제안: `--fresh`(또는 `--no-session`) — 이번 호출 전에 세션을 버리고 다시 로그인. `--help`에 "로그인 성공 세션을 테넌트·계정별로 다시 쓴다"를 적는다.
- 머리 줄에 `login=new|reused`를 찍으면 착각이 없다.

## 5. `api` 응답 필터 (우선순위 중간)

- 큰 목록에서 몇 칸만 보려고 매번 `--raw | python3 -c "json…"`을 썼다(0008~0017에서 약 15번). 요약 모드는 첫 행만, `--raw`는 전체라 중간이 없다.
- 제안: `--fields a,b,c`(행마다 그 칸만 TSV), `--where k=v`(행 거르기), `--count-by k`(칸 값별 건수). 예:
  - `yunhee api GET /api/v1/sys/corps -c kalpa -p corpType=% … --count-by corpTypeName` → `국내은행 24 · 증권회사 24 · 선물회사 9`
  - `yunhee api GET /api/v1/sys/calendars -c kalpa -p year=2026 --where workingYn=false --fields day,weekday,offReason`

## 6. `log trace` — 500 오류의 원인 줄이 안 보인다 (우선순위 중간)

- `PUT /api/v1/sys/admin-user-lists`에 휴대폰 18자(DB `varchar(13)`) → HTTP 500 "서버 내부 오류"(trace `09ffcc715439503b`). `yunhee log trace 09ffcc715439503b` 요약에 `ERROR … 처리되지 않은 예외`만 있고 **원인(`value too long for type character varying(13)` 등)이 없었다**.
- 제안: 처리되지 않은 예외는 스택의 가장 안쪽 `Caused by:` 한 줄(SQLState·메시지)을 요약에 붙인다. `api --log`도 같은 줄을 보이면 한 번에 끝난다.

## 7. 원본이 바뀐 것을 `drift`가 못 잡는 경우 (우선순위 낮음 — `trace-pair`는 잡음)

- #1077 일괄복사 창: 원본이 2026-07-07(`c5de7dbf5`)에 `sys.Sys06_Menu.updateByMenuYn` → `insertByMenuYn`으로 바뀌었는데, TOBE는 그 전 소스로 변환했다. `drift --base baseline`은 기준 이후 변경만 보므로 "변경 0"이다.
- `trace-pair '#1077'`은 "ASIS에만 있음: `insertByMenuYn`"과 "TOBE에만 있음: `PUT /menus/company-use` [AS-IS 주석: `updateByMenuYn`]"을 따로 냈다. 이 둘을 묶어 **"원본 변경 의심: TOBE 주석의 서비스 `updateByMenuYn`을 현재 AS-IS는 부르지 않고 `insertByMenuYn`을 부른다"** 한 줄로 내 주면 바로 알아본다.
- 같은 꼴: `SysCompanyService.initCompany` 주석은 `UpdateDataModel L90-224 1~15번`인데 현재 원본은 33번까지(2026-03~04 추가). TOBE 주석의 원본 줄 범위·번호와 현재 원본을 비교하는 검사가 있으면 좋다.

## 8. 덧붙임 (낮음)

- `yunhee grep -h` → "No such option: -h". 모든 명령에서 `-h`를 `--help`로.
- `yunhee analysis method <클래스>`(메서드 없이) → 형식 오류만. 그 클래스의 메서드 목록을 보여 주면 다음 호출이 줄어든다.
- `yunhee sql`의 열 이름 오류에 "비슷한 열" 후보(`sys01_loc_code` → `sys01_loc_nm`)를 붙인다 — `analysis sql`의 "비슷한 문장"처럼.
