## 1. `api` 로그인: 회사 안에서 사번 찾기, `--password`, 실패 때 무엇으로 시도했는지 알리기 (상)

### 재현

| 명령 | 결과 |
|:---|:---|
| `YUNHEE_TEST_ADMIN_USER=401 YUNHEE_TEST_ADMIN_PASS='Kalpa1234!' yunhee api GET /api/v1/att/commutes/me/last-info -u 401 -c kalpa` | `로그인 실패 (HTTP 401) … (실패 1/5회, 4회 더 실패하면 계정이 잠깁니다.)` |
| `YUNHEE_TEST_ACCOUNTS='401:Kalpa1234!' yunhee api … -u 401 -c kalpa --fresh` | 같은 실패 2/5 |
| `YUNHEE_TEST_ACCOUNTS='401:1111' yunhee api … -u 401 -c kalpa --fresh` | 200 |

- 원인을 찾으려고 `src/yunhee/tools/api_client.py` `resolve_user_credentials` L82-165를 읽어야 했다. 알게 된 것:
  - `-u admin`이 아니면 `YUNHEE_TEST_ADMIN_PASS`는 **DB에서 비밀번호를 못 찾았을 때만** 쓰인다(직원은 `YUNHEE_TEST_ACCOUNTS`가 우선). 도움말에 없다.
  - 사번으로 사원을 찾을 때 `ORDER BY (emp01_company_id = 28000) DESC, emp01_person_id` — **`-c kalpa`를 줘도 회사로 거르지 않는다.** 사번 `401`이 여러 회사에 있으면 회사 28000의 401이나 ID가 가장 작은 회사의 401을 고른다.
    이번엔 우연히 kalpa 401이 골라졌지만, kova·igo를 만들면(같은 사번 체계) 틀린 사원으로 로그인 시도 → 그 사원의 실패 횟수가 오른다.
  - 실패 메시지가 서버 문구만 보여 줘서 "어느 사원 ID·어느 출처의 비밀번호로" 시도했는지 모른다.
- 직원 계정은 5회 실패로 잠긴다. 업무분석은 직원 7명 × 회사 3개로 로그인을 자주 바꾸므로 **위험이 크다**.

### 사용법(바뀐 뒤)

```bash
yunhee api GET /api/v1/att/commutes/me -u 401 -c kalpa --password 1111
yunhee api GET /api/v1/att/commutes/me -u 401 -c kalpa          # YUNHEE_TEST_DEFAULT_PASS(=1111)를 씀
```

### 구현

1. `config.py`에 `TEST_DEFAULT_PASS = os.getenv("YUNHEE_TEST_DEFAULT_PASS", "")` 추가. `.env.yunhee` 예시(`docs/help` 설정 절)에 `YUNHEE_TEST_DEFAULT_PASS=1111` 한 줄.
2. `api_client.resolve_user_credentials(user_or_role, db_name=None, company_code=None, password=None)` — 인자 둘 추가.
   - 사원 찾기 SQL을 회사 코드로 거른다. 회사 코드 → 회사 ID는 로그인 때 서버가 쓰는 표에서 찾는다. framework-sprt에서는 서브도메인 = 회사 코드이고
     `sys01_company`에 코드 열이 없으므로(열 목록: `sys01_company_id, sys01_company_nm, …` — 코드 열 없음) **먼저 `api_client`가 이미 쓰는 테넌트 판정 방식을 확인**한다:
     `grep -rn "companyCode" ~/work/framework-sprt/AssetERP/backend/src/main/java/kr/co/kfs/asseterp/biz/auth` 로 로그인 서비스가 회사 코드를 회사 ID로 바꾸는 SQL을 찾아 같은 SQL을 쓴다.
     (못 찾으면 대안: 로그인 응답의 `companyId`를 세션 파일에 저장해 두고, 두 번째부터는 그 값으로 거른다. 첫 로그인은 사번이 회사 안에서 하나일 때만 진행, 여럿이면 "사원 ID로 `-u`를 주세요"로 멈춘다.)
   - 비밀번호 우선순위: `password` 인자 > `YUNHEE_TEST_ACCOUNTS`의 `사번:비번`/`사원ID:비번` > `TO_DECRYPTS(emp01_password)` > `TEST_DEFAULT_PASS` > `TEST_ADMIN_PASS`(옛 동작, 경고 한 줄).
   - 반환에 `pw_source`(문자열: `"--password"`, `"YUNHEE_TEST_ACCOUNTS"`, `"emp01_password"`, `"YUNHEE_TEST_DEFAULT_PASS"`, `"YUNHEE_TEST_ADMIN_PASS"`)를 `user_info`에 넣는다.
3. `cli.py` `api` 명령(L946~)에 `--password` 옵션 추가 → `request_api(..., password=...)` → `login(...)`까지 전달.
4. `login()` 실패 처리(L200 근처): 메시지 끝에 한 줄 덧붙인다:
   `시도: 사원 202611109048654(사번 401, 회사 kalpa) · 비밀번호 출처 YUNHEE_TEST_ACCOUNTS · 서버 실패 횟수 2/5 — 같은 계정으로 다시 부르기 전에 비밀번호를 확인하세요`
5. **안전장치**: 서버 응답에 `실패 N/5회`가 있고 N ≥ 3이면 그 세션 키로 `--fresh` 재로그인을 막고 "잠금 직전" 오류로 끝낸다(`--force-login`으로만 통과).

### 테스트 (`tests/test_fix060.py::TestApiLogin`)

- `resolve_user_credentials`의 DB 호출은 `psycopg.connect`를 monkeypatch한 가짜 커서로 바꾼다(기존 `tests/test_api_client.py`의 방식을 따른다 — 먼저 그 파일을 읽고 같은 fixture를 쓴다).
  - 같은 사번 `401`이 회사 A·B에 있을 때 `company_code="B"`면 B의 사원 ID를 고른다.
  - 회사를 못 정하고 같은 사번이 둘 이상이면 예외(메시지에 "사원 ID로").
  - 우선순위: `password="x"`가 `YUNHEE_TEST_ACCOUNTS="401:y"`보다 앞선다, `ACCOUNTS`가 DB 값보다 앞선다, DB 값이 없으면 `YUNHEE_TEST_DEFAULT_PASS`.
  - `pw_source`가 맞게 채워진다.
- `login()` 실패 메시지: `httpx.post`를 monkeypatch해 `{"code":"LOGIN_FAILED","message":"… (실패 3/5회 …)"}` 401을 돌려주게 하고, 출력에 "시도:"·"출처"가 있고 다음 `--fresh`가 막히는지.

## 2. `biz-endpoints <도메인>` — TOBE API 표: 경로·파라미터·본문 필드·서비스 메서드·권한 검사 (상)

### 재현(지금 하는 일)

- ATT 한 도메인을 보려고: 컨트롤러 6개의 `Mapping` 줄 grep → DTO 9개 `cat` → 서비스 7개 `outline` → 필요한 메서드 `Read`. 그래도 틀렸다:
  - `DELETE /api/v1/att/work-policies`를 `-p ids=…`로 불러 500(`@RequestBody List<Long>`이었다).
  - `PUT /api/v1/pay/annuals/{id}/appr-id`를 `-p apprId=`로 불러 500(본문 `{apprId}`였다). 같은 일을 하는 `PUT /api/v1/att/overtime-reqs/me/{id}/appr`는 `@RequestParam apprId`였다.
- 권한 검사가 있는지(`user.requireSysAdmin()`)·본인 행 검사(`countMine`)가 있는지 보려고 서비스를 또 읽었다. 이 차이가 곧 보안 의심(#62·#67·#75)이었다.


### 구현 (`src/yunhee/tools/biz/endpoints.py`)

1. TOBE 루트: `config`의 `YUNHEE_TOBE_SRC_DIR`(지금 `~/work/framework-sprt/AssetERP`). 컨트롤러 = `backend/src/main/java/**/biz/<도메인>/controller/*.java`.
2. **재사용**: `src/yunhee/tools/trace/tobe.py`에 `parse_controller(text, file) -> list[Endpoint]`(L183)·`parse_service`(L233)·`HTTP_ANNOTATION`(L20)이 이미 있다. 먼저 `Endpoint` 데이터클래스 필드를 읽고(파일 위쪽) 모자란 것만 더한다:
   - 파라미터: 메서드 시그니처에서 `@RequestParam(required = false) Long personId` → `personId?`(required=false나 defaultValue가 있으면 `?`), `@PathVariable` → 경로에 이미 있음, `@RequestBody X req` → 본문 타입 `X`.
     `@AuthenticationPrincipal`은 뺀다. 정규식 예: `@RequestParam(?:\(([^)]*)\))?\s+(?:@\w+(?:\([^)]*\))?\s+)*([\w<>]+)\s+(\w+)`.
   - 본문 타입이 `List<X>`면 `List<X>`로 적고 X의 필드를 편다.
3. DTO 필드: `dto/<X>.java`가 `record X(Long a, LocalDate b, …)`면 괄호 안을 `,`로 나눠 `이름(타입)`. 타입이 `String`/`Long`/`Boolean`/`boolean`이면 타입은 생략하고 `LocalDate`·`LocalDateTime`·`List<…>`·`BigDecimal`만 붙인다(짧게). 중첩 `record Row(…)`는 `rows[]{…}`로.
   클래스 DTO(Lombok `@Getter`)면 `private <타입> <이름>;` 줄을 모은다.
4. 서비스 메서드: 컨트롤러 메서드 본문에서 `service.xxx(` 또는 `<필드명>.xxx(`를 찾아 필드 타입(`private final AttCommuteService service;`)으로 `AttCommuteService.xxx`. (`trace/tobe.py`의 `_calls`·`field_types`를 재사용할 수 있으면 쓴다.)
5. **검사 열**(가장 중요): 서비스 메서드 본문(중괄호 짝 맞추기 — `tobe.py`의 `_body` 재사용)을 보고 다음을 순서대로 판정, 해당하는 것을 `·`로 잇는다:
   - `requireSysAdmin(` 또는 `isSysAdmin()`으로 막음 → `KFS관리자`
   - `requireRole(`·`hasMenu(`·`checkMenu`·`@PreAuthorize`(컨트롤러 메서드 위) → `메뉴/역할`(지금은 없지만 생기면 잡히게)
   - `getUserId()`를 매퍼 호출 인자로 넘김, 또는 `countMine`/`checkMine`/`Mine(` 호출 → `본인`
   - `getCompanyId()` 사용 → `회사`
   - 아무것도 없음 → `없음`(빨간 표시 `⚠없음`)
   - 서비스가 다른 private 메서드를 부르면 한 단계만 따라간다(`checkMine` 같은 것이 private이라서).
6. `-o json`: `[{method, path, query:[{name, required, type}], body:{type, list, fields:[…]}, service, guards:[…], file, line}]`. #3·#4·#5가 이 JSON을 쓴다.
7. 도메인 대신 컨트롤러 파일 경로를 줘도 되게(`yunhee biz-endpoints backend/src/.../AttCommuteController.java`).

## 3. `biz-authz <도메인> -u <낮은 권한 사번> -c <회사>` — 권한 훑기 (상)

### 재현(지금 하는 일)

- 의심 #9·#10·#12·#14·#15·#24·#27·#31·#40·#44·#47·#48·#50·#59·#62·#67·#75 …: 모두 "메뉴가 없는 사원이 관리자 화면 API를 부르면 된다". 이벤트마다 한두 개를 골라 손으로 확인했고, 빠뜨린 것도 있을 것이다.

### 사용법

```bash
yunhee biz-authz att -u 401 -c kalpa                 # GET만 실제 호출(기본, 안전)
yunhee biz-authz att -u 401 -c kalpa --probe-write   # 쓰기는 '빈 본문'으로만 찔러 본다(아래 규칙)
yunhee biz-authz pay -u 401 -c kalpa --path annuals -p personId=  # 경로 거름, 공통 쿼리값
```

출력:

| 메서드 | 경로 | 검사(정적) | 사원 401 결과 | 판정 |
|:---|:---|:---|:---|:---|
| GET | /api/v1/att/commutes/admin | 회사 | 200 rows=13 | ⚠ 관리자 화면 자료를 사원이 받음 |
| GET | /api/v1/att/commutes/status | 회사 | 200 rows=7 | ⚠ |
| GET | /api/v1/att/commutes/person-status | 회사·본인 | 200 rows=12 | 본인 자료(정상) |
| PUT | /api/v1/att/commutes/{commuteId}/time | 회사 | 빈 본문 → 200 Data:0 | ⚠ 검사 없이 서비스까지 들어감 |
| PUT | /api/v1/pay/work-times | KFS관리자 | 빈 본문 → ACCESS_DENIED | 막힘(정상) |

### 구현 (`src/yunhee/tools/biz/authz.py`)

1. `biz-endpoints`의 JSON(#2)을 함수로 직접 받는다(`endpoints.collect(domain)`).
2. **"관리자 화면 API" 고르기**: 엔드포인트 경로 → 그 API를 부르는 프론트 화면 → 메뉴 번호로 가야 정확하다. 단계:
   - 프론트 `frontend/src/api/<도메인>.ts`에서 함수 ↔ URL(`trace/tobe.py` `parse_api_ts` L117 재사용), 그 함수를 import하는 `pages/**.tsx`(파일 이름 = AS-IS 클래스 이름).
   - 클래스 → 메뉴: `docs/as-is/src/menus.md`(행 `| 메뉴 경로 | 번호 | 사용 | [`클래스`](…) |`).
   - 로그인 사원의 메뉴 목록: 서버 API가 있으면 그것(framework-sprt에서는 메인 화면이 메뉴 트리를 받는 API — `yunhee biz-endpoints sys --path menu`로 찾아 설정값 `YUNHEE_BIZ_MY_MENU_PATH`로 둔다), 없으면 DB:
     `sys05_user_role`(사원→권한그룹) → `sys07_role_menu`(권한그룹→메뉴) → `sys06_menu.sys06_menu_no`. (테이블 열 이름은 구현 전에 `yunhee sql "select column_name from information_schema.columns where table_name='sys07_role_menu'"`로 확인한다 — 추측하지 말 것.)
   - 판정에 쓰는 것: "그 API를 쓰는 화면의 메뉴 번호가 사원 메뉴 목록에 **없다**" → 관리자(남의) 화면 API. 화면이 로그인 창처럼 메뉴가 없으면(`Att02_Lookup_Commute`) "메뉴 없음 — 판정 보류".
3. **GET 호출**: 경로 변수(`{commuteId}`)가 있는 GET은 기본 건너뜀(`--sample-ids`로 `commuteId=…` 줄 때만). 필수 쿼리는 `-p`로 준 값, 없으면 타입별 기본값(`LocalDate` → 오늘, `int` → 1, `String` → 빈칸)을 넣는다. `request_api(...)`로 부르고 상태·`rows` 수만 기록.
4. **쓰기 `--probe-write`**(실제 데이터를 바꾸지 않기 위한 규칙):
   - 본문 타입이 `List<…>`면 `[]`, record면 `{}`(모든 필드 null), 경로 변수는 `0`(없는 ID).
   - 응답 해석: `ACCESS_DENIED`/403 → "막힘", `DATA_NOT_FOUND`/`INVALID_INPUT`/200 → "검사 없이 서비스까지 들어감(⚠)". 500 → "오류(본문 형식 확인)".
   - 그래도 위험할 수 있으니 실행 전 `--track`으로 쓰는 테이블(서비스가 부르는 매퍼의 테이블 — `trace-pair` 정보 재사용 가능, 어려우면 생략) 행 수를 찍고 끝에 다시 찍어 **변화가 있으면 빨간 경고**.
   - `DELETE`는 `--probe-write`여도 기본 제외, `--probe-delete`로만.
5. 결과 끝에 "⚠ N건 — `보안_및_버그_의심.md`에 적을 후보" 요약과, 각 ⚠ 줄을 그대로 붙여 넣을 수 있는 한 줄(`| … | 401 GET /att/commutes/admin → 200 rows=13 |`)을 `--emit-rows`로 출력.

### 테스트 (`TestBizAuthz`)

- HTTP는 monkeypatch: `request_api`를 가짜로 바꿔 경로별 응답 사전(`{"/api/v1/foo/bars": (200, rows 3), "/api/v1/foo/admin": (403, ACCESS_DENIED)}`)을 돌려준다.
- 메뉴 판정은 가짜 메뉴 목록(사원 메뉴 `{1001}`)과 가짜 화면↔API 연결로 — "메뉴 밖 화면 + 200 → ⚠", "메뉴 안 → 정상", "403 → 막힘".
- `--probe-write`: 본문 생성 규칙(`List` → `[]`, record → `{}`, 경로 변수 0), DELETE 제외, `--track` 변화 경고.

## 4. `biz-appr` — 결재 상신·승인 한 번에 (상)

### 재현(지금 하는 일)

결재가 필요한 이벤트(휴가·출장·연장근무·오후근무·연봉계약 …)마다 6단계를 손으로 했고, 이번엔 임시 스크립트(`appr.sh`, 30줄)를 만들었다:

1. `GET /api/v1/apr/apprs/new?classTreeId=<분류>` → 새 문서 ID·상신 단계 ID
2. `GET /api/v1/apr/apprs/link-seed?classTreeId=…&linkCode=A74&refId=<업무행 ID>` → 제목·시행일·본문
3. 본문 조립: `{mode:"request", classTreeId, linkCode, title, content, effectDate:"…T00:00:00", regDate, signCompany, confirmed:true, steps:[{apprStepId, stepTypeCode:"00", seq:"001", stepStatusCode:"10", stepEmpId, lockYn:"false"}, {stepTypeCode:"10", seq:"002", stepStatusCode:"10", stepEmpId:<결재자>, lockYn:"false"}]}`
4. `PUT /api/v1/apr/apprs/{apprId}`
5. 업무 행에 결재 ID 기록 — **업무마다 다르다**: `PUT /att/overtime-reqs/me/{id}/appr?apprId=`(쿼리), `PUT /att/pm-works/{id}/appr?apprId=`(쿼리), `PUT /pay/annuals/{id}/appr-id` 본문 `{apprId}`(쿼리로 보냈다가 500).
6. 결재자로 로그인해 `POST /api/v1/apr/apprs/{apprId}/confirm {action:"confirm"}`
- 분류 ID(`classTreeId`)도 매번 `dcr30_link`에서 SQL로 찾았다(`dcr30_link_cd`, `dcr30_class_tree_id`, 회사별).

### 사용법

```bash
# 연장근무 신청 202611129140065 을 401이 상신, 301이 승인
yunhee biz-appr A74 --ref 202611129140065 -u 401 -c kalpa --approver 301 --confirm
# 분류를 직접 주기, 결재자 여럿(순서대로), 승인 안 하고 상신만
yunhee biz-appr D01 --ref 202611129140114 -u 301 -c kalpa --class 202611109047134 --approver 201,100
# 반려
yunhee biz-appr A73 --ref 202611129140094 -u 402 -c kalpa --approver 302 --reject "사유 부족"
```

출력(짧게):
```
분류 202611109047109 인사/인사관리/근태관리 (dcr30_link A74)
상신 apprId=202611129140071 「연장근무 신청서 / 김사원 사원 (2026-11-12)」 상태 10
연결 PUT /api/v1/att/overtime-reqs/me/202611129140065/appr?apprId=… → 200
승인 301 → 30 완료
```

### 구현 (`src/yunhee/tools/biz/appr.py`)

1. **분류 찾기**(`--class` 없을 때): `yunhee sql`과 같은 연결로 읽기 전용 조회
   `SELECT dcr30_class_tree_id FROM dcr30_link WHERE dcr30_company_id = <로그인 회사 ID> AND dcr30_link_cd = <링크코드>`. NULL이면 멈추고 안내:
   "회사 관리자가 #1280 문서분류지정에서 A74 분류를 지정해야 합니다 — `yunhee api PUT /api/v1/dcr/links -b '[{\"linkId\":<id>,\"classTreeId\":<분류>}]' -u admin -c kalpa`". (로그인 회사 ID는 #1의 세션 정보에서.)
2. 1~4단계는 위 "재현"의 본문 그대로. `link-seed`의 `effectDate`가 없으면 오늘. `content`가 null이면 `<p>(본문 없음)</p>`.
   결재자 여럿이면 seq `002`, `003` …, 모두 `stepTypeCode "10"`. `--agree 202`(합의, stepTypeCode는 서버 코드 확인 후 상수로) 같은 옵션은 다음 단계.
3. **업무 행 연결**(5단계): 링크코드 → 연결 API 표를 코드에 둔다(설정 파일로 빼도 됨, `src/yunhee/tools/biz/appr_links.toml`):
   ```toml
   [A74] path = "/api/v1/att/overtime-reqs/me/{ref}/appr"  ; style = "query"   # apprId=
   [A73] path = "/api/v1/att/pm-works/{ref}/appr"           ; style = "query"
   [D01] path = "/api/v1/pay/annuals/{ref}/appr-id"         ; style = "body"    # {"apprId": …}
   ```
   표에 없는 링크코드는 **#2 `biz-endpoints`로 찾는다**: 경로에 `appr`가 들어가고 경로 변수가 하나인 PUT 중, 프론트에서 그 링크코드 상수(`const LINK_CODE = 'A74'`)를 가진 화면이 부르는 것. 못 찾으면 연결을 건너뛰고 "연결 API를 `--link-path`로 주세요".
   `--link-path '/api/v1/x/{ref}/appr' --link-style query|body`로 직접 줄 수 있게.
4. 승인: 결재자마다 순서대로 그 계정으로 `POST …/confirm`(#1 로그인). `--reject "사유"`면 마지막 결재자가 `{action:"reject", message}`.
5. 각 단계 응답의 `ok:false`·`message`를 그대로 보여 주고 멈춘다(예: "결재선에 상신자 외 결재권자가 없습니다" → `confirmed:true` 재전송은 이미 본문에 있음).
6. `--dry-run`: 만든 본문 JSON만 출력.

## 5. `biz-patch` — 조회한 값의 몇 칸만 바꿔 저장 (중)

### 재현

- #1075 회사 설정의 `근태 팝업사용` 하나만 켜려고: `GET …/account --raw > acct.json` → python으로 `commutePopupYn="true"`, 이름 열(`…Nm`) 빼기 → `PUT`. 연봉 복원·산출식 복원도 같은 모양(3번).
- 이 PUT들은 **보내지 않은 칸을 비운다**(연봉 저장이 그랬다) — 손으로 본문을 만들면 값이 지워지는 사고가 난다.

### 사용법

```bash
yunhee biz-patch /api/v1/sys/companies/202611109046432/account --set commutePopupYn=true -u admin -c admin
yunhee biz-patch /api/v1/pay/annuals --where annualId=202611129140115 --set annualPay=39000000 --list -u 301 -c kalpa
#   --list : GET이 목록이면 --where로 한 줄 고르고, PUT 본문을 [그 줄]로 보낸다
#   --put <경로> : 저장 경로가 GET과 다를 때 (기본은 같은 경로)
#   --drop-suffix Nm,Name : 이름 열 빼기 (기본 Nm)
```

### 구현 (`src/yunhee/tools/biz/patch.py`)

1. `request_api("GET", path, params=…)` → `data`. `--list`면 `data`가 배열이어야 하고 `--where k=v`(여러 개 AND)로 정확히 한 줄 고름(0개·2개 이상이면 멈춤).
2. `--set k=v`: 값 변환 — `true/false` → bool이 아니라 **원래 값의 타입을 따른다**(원래 `"false"` 문자열이면 `"true"` 문자열, 원래 숫자면 int/float, 원래 null이면 문자열 그대로). 없는 키면 경고 후 추가.
3. `--drop-suffix`로 읽기 전용 이름 열 제거(기본 `Nm`). `--keep k1,k2`로 보낼 키만 고를 수도.
4. `PUT`(`--method POST` 가능). 저장 전후 차이를 `키: 이전 → 이후` 줄로 출력하고, 응답 뒤 한 번 더 GET 해서 **바꾸지 않은 칸이 비었는지** 비교해 비었으면 경고("서버가 보내지 않은 칸을 지웠을 수 있음" — 지금은 다 보내므로 없어야 정상).
5. `--dry-run`: 보낼 본문만.

### 테스트 (`TestBizPatch`)

- 가짜 GET `{"a":"false","b":1,"cNm":"x"}` + `--set a=true b=2` → PUT 본문 `{"a":"true","b":2}`(cNm 빠짐).
- `--list --where id=2` 두 줄 중 하나 고름, 0줄·2줄이면 오류.
- 저장 뒤 GET에서 `b`가 null이 되면 경고 출력.

### 확인 방법

```bash
yunhee biz-patch /api/v1/sys/companies/202611109046432/account --set commutePopupYn=false -u admin -c admin
yunhee biz-patch /api/v1/sys/companies/202611109046432/account --set commutePopupYn=true -u admin -c admin
yunhee api GET /api/v1/att/commutes/me/last-info -u 401 -c kalpa      # popupYn true
```

### 기대효과

- 설정 바꾸기·시험 뒤 되돌리기가 한 줄. 손으로 만든 본문 때문에 다른 칸이 지워지는 사고 예방.

### 구현 결과 (2026-11-12)
- `src/yunhee/tools/biz/patch.py` 구현: GET 데이터 조회, 원래 데이터 타입(bool, int, float, 'true'/'false' 문자열) 보존형 `--set` 치환, `--list` 및 `--where` 단일 행 선택, 접미사(`--drop-suffix`) 제거, 저장 후 GET 재조회 기반 미변경 필드 소실 경고 검증 구현.

## 7. `biz-db-write -f <x.sql>` — 로컬 DB에만, 자동 백업 뒤 쓰기 (중)

### 재현

- 사용자 결정(2026-11-12): "localhost asseterpdb는 시험·분석을 위해 얼마든지 CRUD 가능". 하지만 에이전트의 `psql` 직접 실행은 framework-sprt 훅이 막고(`yunhee sql`을 쓰라 함),
  `yunhee sql`은 읽기 전용·`--rollback`만 있다. 그래서 시험 행 4줄 정리를 사용자에게 `! docker exec -i … psql … < file`로 부탁했다(왕복 1회 + 대기).
- 직원 비밀번호 `1111`도 규칙(`f_password_rule`)상 API로는 못 넣어 `sys25_password` 직접 입력이 필요하다.

### 사용법

```bash
yunhee biz-db-write -f cleanup.sql                 # 백업 → 실행 → 커밋, 영향 행 수 출력
yunhee biz-db-write -f cleanup.sql --dry-run       # = sql --rollback (지금과 같음)
yunhee biz-db-write -e "DELETE FROM att02_commute WHERE att02_commute_id = 202611129140091"
yunhee biz-db-write -f x.sql --no-backup           # 백업 생략(작은 정리, 사용자가 허락할 때만)
```

### 구현 (`src/yunhee/tools/biz/dbwrite.py`)

1. **안전 조건(모두 만족해야 실행)**:
   - 연결 문자열의 호스트가 `localhost`/`127.0.0.1`/`::1`(또는 docker 호스트 이름 설정값 `YUNHEE_DB_WRITE_HOSTS`)이고 DB 이름이 `YUNHEE_DB_WRITE_ALLOW`(기본 `asseterpdb`)에 있을 것. 아니면 거절.
   - 설정 `YUNHEE_DB_WRITE=1`이 켜져 있을 것(기본 꺼짐 — 프로젝트가 명시적으로 켠다).
   - 문장 검사: `DROP`·`TRUNCATE`·`ALTER`·`CREATE`·`GRANT`·`DELETE`/`UPDATE`인데 `WHERE` 없음 → 거절(`--allow-ddl`이 있어야). `sql_runner.guard_statement`(L145) 옆에 `guard_write_statement`를 둔다.
2. **백업**: 기본으로 실행 전에 백업. 프로젝트에 백업 스크립트가 있으면 그것(`YUNHEE_DB_BACKUP_CMD`, framework-sprt는 `tools/db_dump_backup.sh`), 없으면 `pg_dump -Fc`를 `~/.cache/yunhee/backup/<db>-<시각>.dump`로.
   백업 실패면 실행하지 않는다.
3. 실행: 한 트랜잭션에서 문장마다 실행·영향 행 수 기록 → 하나라도 오류면 전체 롤백 → 모두 되면 커밋. 출력: `문장 n: DELETE 1` 줄들 + `커밋됨 · 백업 <경로> · 되돌리기: pg_restore …`.
4. 기록: `~/.cache/yunhee/db-write.log`에 시각·파일·영향 행 수·백업 경로 한 줄(나중에 "무엇을 바꿨나" 확인용).
5. framework-sprt 훅과의 관계: 훅은 `psql`을 막을 뿐이라 `yunhee biz-db-write`는 통과한다. 훅 문구에 이 명령을 안내하도록 framework-sprt 쪽에서 고친다(이 수정사항 범위 밖, framework-sprt 작업).

### 테스트 (`TestBizDbWrite`)

- 연결 문자열 판정: `postgresql://u@localhost:5432/asseterpdb` 허용, `…@10.0.0.5:5432/asseterpdb` 거절, DB 이름 불일치 거절, `YUNHEE_DB_WRITE` 꺼짐 거절.
- 문장 검사: `DELETE FROM t` 거절, `DELETE FROM t WHERE id=1` 허용, `DROP TABLE t` 거절.
- 백업 명령 실패(가짜 `subprocess.run` returncode 1) → 실행 안 함.
- 두 번째 문장 오류 → 첫 문장도 롤백(가짜 커서로 commit/rollback 호출 확인).

### 확인 방법

```bash

echo "UPDATE att01_work_policy SET att01_note = 'biz-db-write 시험' WHERE att01_work_policy_id = 202611129140059;" > /tmp/t.sql
YUNHEE_DB_WRITE=1 yunhee biz-db-write -f /tmp/t.sql        # 백업 경로·UPDATE 1·커밋됨
yunhee sql "select att01_note from att01_work_policy where att01_work_policy_id=202611129140059"
echo "UPDATE att01_work_policy SET att01_note = NULL WHERE att01_work_policy_id = 202611129140059;" > /tmp/t.sql
YUNHEE_DB_WRITE=1 yunhee biz-db-write -f /tmp/t.sql --no-backup
echo "DELETE FROM att01_work_policy;" > /tmp/t.sql; YUNHEE_DB_WRITE=1 yunhee biz-db-write -f /tmp/t.sql   # 거절(WHERE 없음)
```

### 기대효과

- 시험 데이터 정리·시험용 지름길(비밀번호 등)을 사람 손 없이. 백업이 자동이라 사고가 나도 되돌린다.

### 구현 결과 (2026-11-12)

   {화면마다 원본 이벤트 [E1]… 를 한 줄씩: | n | TODO | #번호 | 단추 이름 [조회] 등 | TODO |}

   | 테이블 | 무엇 | 실행 |

   <details><summary>시나리오 데이터 (자동 시험용)</summary>

   </details>

## 10. 기대효과 요약

| 단계(업무분석 한 이벤트) | 지금 | 바뀐 뒤 |
|:---|:---|:---|
| TOBE API 파악 | 컨트롤러·DTO·서비스 읽기 3~5회, 형식 착각 500 | `biz-endpoints` 1회 |
| 직원 로그인 | 헤매면 10여 회 + 잠금 위험 | `--password`/기본 비번, 회사 안 사번 |
| 결재 | 6회 + 본문 조립 | `biz-appr` 1회 |
| 권한 의심 찾기 | 손으로 몇 개, 빠뜨림 | `biz-authz` 1회, 전부 |
| 설정 바꾸기·되돌리기 | GET→python→PUT | `biz-patch` 1회 |
| 공통코드 | 열 짐작 실패 | `biz-code` 1회 |
| 시험 데이터 정리 | 사용자에게 부탁 | `biz-db-write` |
| 문서 | 100줄 손으로 | 틀 자동, 약 2/3만 씀 |

- 추정(측정 아님): 도메인 하나(이벤트 5~10개)에 드는 에이전트 토큰이 30~40% 줄고, 사람 왕복(DB 정리·잠금 해제)이 없어진다. #1·#2·#3·#4가 그중 대부분이다.
