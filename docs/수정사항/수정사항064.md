## 1. `biz-appr` — 연결 시드가 없는 링크 코드에서 `AttributeError`로 멈춘다 (중간)

- 일어난 일: `yunhee biz-appr A27 --dry-run --ref 1 -u 201 -c kalpa --link-path /api/v1/ics/checklist-confirms/relate-apprs/appr-id --link-style body`가 트레이스백으로 죽었다.
  `tools/biz/appr.py:219 title = seed_data.get("title") …` → `'NoneType' object has no attribute 'get'`. A27(체크리스트 상신)·A32(준수보고)는 업무 화면이 시드(제목·본문)를 주는 구조가 아니라서 시드 API 응답의 `data`가 `null`이다.
  (B15는 시드가 있어 `--dry-run`이 제목·단계까지 조립해 줬다.) 그래서 `GET /apr/apprs/new` → `PUT /apr/apprs/{id}` (mode request) → `POST /apr/apprs/{id}/confirm`을 손으로 불러 우회했다(ICS-BZ-0017·0018).
- 고칠 것:
  1. `seed_data = seed_data or {}`로 받는다. 시드가 없으면 제목 `"{link_code} 신청서"`·본문 `"<p>(본문 없음)</p>"` 기본값이 이미 있으니 그대로 쓴다.
  2. 시드가 없을 때 `--title`·`--content` 옵션으로 덮어쓸 수 있게 한다(시드가 있어도 덮어쓰기 가능).
  3. 링크 연결 본문이 `{apprId}` 하나로 끝나지 않는 API(`relate-apprs/appr-id`는 `stdDate·cycleType·checklistLClassId·apprId·lastApprId`)를 위해 `--link-body '{"stdDate":"…","apprId":"{apprId}"}'`처럼 템플릿을 받는 옵션을 더한다(`{apprId}`·`{ref}` 치환).
  4. `--approver`에 사번을 주면서 YUNHEE_TEST_ACCOUNTS에 없으면 `경고: 직원에 YUNHEE_TEST_ADMIN_PASS를 사용합니다`만 나오고 어느 비밀번호로 시도하는지 안 보인다 — 로그인 실패 시 어떤 사번·회사로 몇 번째 시도인지 한 줄로 보여 준다.
- 확인: `yunhee biz-appr A27 --dry-run --ref 1 -u 201 -c kalpa --approver 100` → 오류 없이 조립된 상신 본문 출력. `--title "…"` 이 본문에 반영된다.

## 2. `api --fields` — 응답에 없는 필드 이름이면 조용히 빈 칸이다 (작음)

- 일어난 일: `yunhee api GET /api/v1/ics/extr-activities/company … --fields regDate,personName,activityCorp,apprStatusName,activityPay`가 `personName`·`apprStatusName` 칸을 **빈 값**으로 출력했다. 실제 응답 키는 `personNm`·`apprStatusNm`이었다.
  한참 뒤 `--raw`로 보고서야 "신청자 이름이 안 나온다"가 데이터 문제가 아님을 알았다(`compare`의 "missing: activityTgtName2"도 같은 이름 차이 때문이다).
- 고칠 것:
  1. `--fields`에 응답에 없는 이름이 있으면 표 위에 한 줄 경고: `⚠ --fields: personName 없음 (비슷한 키: personNm, personNo)`. 비슷한 이름은 편집 거리 또는 접두 일치로 고른다.
  2. 경고 때문에 값이 비는 칸은 빈 문자열 대신 `-`로 출력해 "값이 빈 것"과 "키가 없는 것"을 가른다.
- 확인: 위 호출을 다시 → 경고 줄에 `personNm`이 보인다.

## 3. `compare` — SQL이 `${isPostgreSql}` 분기로 감싸이면 SQL 행이 늘 0이다 (중간)

- 일어난 일: `compare GET /api/v1/ics/class-trees --sql ics01_class_tree.selectByCompanyId …`가 `API rows=57, SQL rows=0 ❌`를 냈다. `analysis sql … -o code`를 보니 본문이 `<choose><when test="${isPostgreSql}"><include refid="selectByCompanyId_postgresql"/>`뿐이다.
  `${isPostgreSql}`가 컴파일 시 값으로 치환돼야 하는 자리표시인데 `compare`가 이를 `false`로 보고 `otherwise`(오류 주석)로 간다. 파라미터·분기를 아무리 바꿔도 0이라 시간을 썼다.
  또 `selectByTypeCodePaging`은 `-- 필요: advisYn, lawSearch, statuteSearch, typeCode`처럼 필수 파라미터를 **실행 오류 뒤에야** 알려 줬다.
- 고칠 것:
  1. `compare`·`mapper-run`·`analysis sql`이 `${isPostgreSql}`·`${isOracle}` 같은 DB 분기 자리표시를 현재 DB 종류(PostgreSQL)로 치환한다. 치환하지 못한 `${…}`가 남으면 `⚠ 치환 못 한 자리표시: ${…} → SQL 행 수를 믿지 말 것`을 결과 줄에 붙인다.
  2. SQL 필수 파라미터는 실행 전에 `analysis sql` 출력의 "파라미터" 줄과 같은 목록을 `compare`가 먼저 보여 주고, `--param` 누락 항목에 `필요: a, b, c`를 한 번에 알린다(오류 뒤가 아니라 앞에서).
- 확인: `yunhee compare GET /api/v1/ics/class-trees --sql ics01_class_tree.selectByCompanyId -c kalpa -u 301 --param companyId=… --no-grid` → `API rows=57, SQL rows=57 ✅`.

## 4. 이벤트 뒤 정리 — 삭제로 생긴 고아 행을 찾을 길이 없다 (중간)

- 일어난 일: 시험 자료를 지운 뒤 `--track`은 지운 테이블의 행 수만 보여 준다. 그런데 다음처럼 **딸린 행이 남는 경우**를 알려 줄 방법이 없어 매번 `yunhee sql`로 직접 찾았다.
  - 공통 대분류 삭제 뒤 `ics22_checklist_l_class_company`(회사별 설정) 1행이 고아.
  - 개정내역 삭제 뒤 `ics19_revision_relate_ics`가 남음(원본도 같은 구조).
  - 체크리스트 재연결로 결재문서(`apr01_appr`)가 지워진 뒤 `apr04_appr_step` 2행이 고아.
  지울 때 쓴 ID도 로그에 없어서 SQL로 다시 찾아야 했다.
- 고칠 것: `yunhee biz-orphans [--table <테이블>] [--company <회사>]`(읽기 전용)를 더한다. DB 색인(`docs/as-is/db`)의 FK성 열(`…_id`가 다른 테이블 PK 이름과 같은 열)로 "부모가 없는 자식 행"을 세고, 상위 10건의 ID와 지울 `DELETE` 문을 **출력만** 한다(실행 안 함).
  `api --track`에 `--children`을 더해, 추적 테이블을 부모로 가진 테이블의 전후 행 수도 같이 보여 주는 쪽이 더 작은 구현이다.
- 확인: ICS-BZ-0012를 다시 해(공통 대분류를 만들고 kalpa 301이 저장한 뒤 지움) `yunhee biz-orphans --table ics22_checklist_l_class_company` → 고아 1건과 `DELETE FROM … WHERE ics22_checklist_l_class_company_id=…`가 나온다.

## 5. `trace-crud` — 원본에서 도달 불가한 삭제를 "TOBE에 D 없음"으로 경고한다 (작음)

- 일어난 일: `trace-crud --screen Ics20_Tab_RevisionHistory`가 `ics20_revision_history: ASIS RUD / TOBE RU  ⚠ TOBE에 D 없음`을 냈다. 그런데 `analysis screen`은 같은 화면의 삭제를 `[E6] … ⚠ 도달 불가 (deleteRow() 호출처 없음)`으로 이미 알고 있다. 경고가 사실이 아니어서 확인에 시간이 들었다(업무분석 문서에 사유를 따로 적어야 했다).

- 확인: `yunhee trace-crud --screen Ics20_Tab_RevisionHistory` → `ASIS RU(D 도달 불가) / TOBE RU` 경고 없음.

## 6. `biz-authz` — 요청 본문의 ID로 남의 행을 지우는 서비스는 못 잡는다 (중간, 새 기능)

- 일어난 일: ICS-BZ-0017의 의심 #148(`PUT /checklist-confirms/relate-apprs/appr-id`)은 검사 칸이 `본인·회사`라 `biz-authz`가 "막힘"으로 보지 않았는데, 서비스가 요청 본문의 `lastApprId`로 **결재문서를 삭제**한다. 호출자가 그 문서의 주인인지는 어디서도 보지 않는다.

## 9. `biz-authz --probe-write` — 입력 검사가 없는 저장 API에 빈 행이 실제로 생긴다 (중간)

- 일어난 일: `yunhee biz-authz adv --probe-write`는 "빈 본문으로 안전하게 인가 검사 프로빙"이라고 하지만 `PUT /api/v1/adv/accounts`는 입력 검사가 없어 **모든 칸이 빈 일임계좌 행(`adv02_account`)이 실제로 만들어졌다**(`빈 본문 → 200 Data:{accountId:…935,…}`). 이 화면의 TOBE에는 삭제 API도 없어(`trace-crud`: `adv02_account` CRUD→CRU) 지울 수 없었고, 이름을 바꿔 시험 자료로 재사용했다.
- 고칠 것:
  1. `--probe-write`가 `200`을 받은 쓰기 API에는 `⚠ 행이 만들어졌을 수 있음: accountId=…935 — 지울 API: 없음` 한 줄을 붙이고, 응답에서 보이는 `…Id`와 지울 방법(`DELETE …`가 있으면 그 경로, 없으면 `DELETE FROM … WHERE …_id=…`)을 출력한다(실행은 안 함 — `biz-orphans`(4번)와 같은 방식).
  2. 옵션 설명의 "안전하게"를 "서버 검증이 있으면 거절되지만, 없으면 빈 행이 생긴다"로 바꾼다. `--probe-write --dry-run`으로 부를 API 목록만 먼저 보게 한다.
- 확인: `yunhee biz-authz adv --probe-write --dry-run` → 부를 PUT/POST 목록만. 실제 실행 뒤 `⚠ 행이 만들어졌을 수 있음` 줄.

## 10. `biz-appr` — 연결 API를 `--link-path`로 알려 줘야 한다는 안내가 없다 (작음)

- 일어난 일: FND 결재(A60·A61)는 업무 화면의 연결 API가 `est/pf-contracts/{id}/plan-appr-id`처럼 이름이 제각각이라 `--link-path`를 줘야 연결됐다. 옵션을 안 읽고 "연동 코드가 없어 쓸 수 없다"고 착각해 TDM·FND 첫 결재(상신·승인 API를 손으로 호출)에서 시간을 썼다. `--help`에는 예시(`/api/v1/.../{ref}/appr`)만 있고 "어떤 API가 연결 API인지"는 알려 주지 않는다.
- 고칠 것: 링크 코드의 화면(`dcr30_link` 코드명 → 업무 화면)에서 `biz-endpoints`로 `…appr-id`·`…/appr` 꼴 PUT API를 찾아 `--link-path`를 **제안**한다. `--link-path` 없이 실행했을 때 `상신은 했으나 업무 행 연결 없음 — 후보: PUT /api/v1/est/pf-contracts/{ref}/plan-appr-id (--link-path로 지정)`을 마지막 줄에 낸다.
- 확인: `yunhee biz-appr A60 --ref <계약ID> --as 301 --approver 201,100 --dry-run` → 끝에 후보 경로 한 줄.

## 11. `log trace` — 로컬 서버(`bm.sh`, 8080) 로그의 추적ID를 못 찾는다 (중간)

- 일어난 일: 사용자가 알려 준 추적ID `b05c856b6063f6fd`를 `yunhee log trace b05c856b6063f6fd`로 찾으니 `로그에 없음 (오늘 파일만 봄)`이라고 했다. 이 로그는 `docker:t3600-tomcat`(8082 배포 서버)만 보고 있었고, 8080 로컬 서버의 로그는 `~/tmp/asseterp-data/logs/AssetERP-backend-*.log`에 있었다.
  `yunhee grep`은 이 경로가 "허용 범위 밖"이라 거절해서, 결국 일반 도구로 줄 번호를 찾아 읽어야 했다(원인은 `collation "ko_KR.utf8" … does not exist`).
- 고칠 것:
  1. `log trace`·`log errors`가 기본 소스에서 못 찾으면 **다른 소스(`--source local`, 설정의 로컬 로그 디렉터리)도 자동으로 한 번 더 찾는다.** 못 찾으면 `docker 소스에서 없음. --source local --dir ~/tmp/asseterp-data/logs 로 다시 찾아 보세요`를 안내한다.
  2. 같은 로그 디렉터리를 `yunhee grep`·`yunhee cat`이 읽게 허용하거나(`YUNHEE_LOG_DIR`을 허용 경로에 포함), `yunhee log grep <패턴> -C n`을 더한다.
- 확인: `yunhee log trace b05c856b6063f6fd` → 로컬 서버 로그에서 찾아 `FrmRelateMapper.selectByRelate … collation "ko_KR.utf8"` 요약.

## 12. `sql --rollback` — DDL을 막아 `CREATE COLLATION` 같은 수정을 미리 시험할 수 없다 (작음)

- 일어난 일: DB 교체 뒤 `ko_KR.utf8` 정렬 규칙이 빠져 수십 화면이 500이었다. `CREATE COLLATION "ko_KR.utf8" (provider = icu, …)`가 맞는지 `yunhee sql -f x.sql --rollback`으로 시험하려 했으나 `안전 가드: --rollback 모드에서는 'CREATE' 문장(COMMIT/END/DDL)을 실행할 수 없습니다.`로 막혔다. PostgreSQL의 DDL은 트랜잭션 안에서 롤백되는데도 못 했다.
- 고칠 것: `--rollback --allow-ddl`(또는 `--ddl-in-tx`)을 더한다. PostgreSQL이면 트랜잭션 안에서 DDL을 실행하고 끝에 `ROLLBACK`한다(`COMMIT`·`END`는 계속 막는다). Oracle 등 DDL이 자동 커밋되는 DB에서는 거절한다.
- 확인: `yunhee sql "CREATE COLLATION …; SELECT '가' < '하' COLLATE \"ko_KR.utf8\"" --rollback --allow-ddl` → 결과가 나오고 실제 DB에는 규칙이 안 생긴다.

## 13. `biz-endpoints`·`biz-authz` — 서비스 안에서 검사하는 API가 `⚠없음`으로 나온다 (작음)

- 일어난 일: `biz-endpoints fnd`가 `DELETE /api/v1/fnd/opr-funds`의 검사 칸을 `⚠없음`으로 냈지만, 서비스 `FndOprFundService.delete` 첫 줄이 `checkEditable(user, oprId)`(회사·결재 상태 검사)를 부른다. 사원 401로 시험하니 200으로 안전하게 끝났다(오탐). 반대로 `body 한 칸의 ID를 그대로 delete 매퍼에 넘기는` 경우(6번)는 못 잡는다.
- 고칠 것: 서비스 메서드 첫 몇 줄에 `check*`·`load*`·`require*`·`verify*` 호출이 있으면 검사 칸에 `서비스내부(checkEditable)`처럼 적고 `⚠없음`으로 세지 않는다. `biz-authz`도 이를 "정적으로는 검사 있음"으로 분류해 시험 대상 우선순위를 낮춘다.
- 확인: `yunhee biz-endpoints fnd --path opr-funds` → `DELETE`의 검사 칸이 `서비스내부(checkEditable)`.

## 14. `api` — 결과가 0행일 때 선택 파라미터 힌트가 없다 (작음)

- 일어난 일: `GET /api/v1/fnd/fund-codes/org-auth`가 정상 펀드가 있는데도 **빈 목록**이었다. 원인은 선택 파라미터 `closeYn`을 안 주면 서버가 해지 펀드 기준으로 조회하기 때문이었고(`-p closeYn=false -p classFundExceptYn=false`를 주니 나옴), `api`는 `rows=0`만 알려 줘 원인을 찾느라 시간이 들었다.
- 고칠 것: `api`가 `rows=0`이고 같은 경로의 `biz-endpoints` 쿼리 칸에 `?` 선택 파라미터가 있으면 `rows=0 — 선택 파라미터: closeYn?, classFundExceptYn?, fundName? (안 준 값에 서버 기본값이 걸릴 수 있음)` 한 줄을 붙인다.
- 확인: `yunhee api GET /api/v1/fnd/fund-codes/org-auth -u 402 -c kalpa` → 빈 목록 아래에 파라미터 힌트 한 줄.
