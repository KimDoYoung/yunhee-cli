## 1. `api --get` — 객체·배열을 JSON이 아닌 Python 표기로 출력한다 (중간)

- 일어난 일: `yunhee api -u 301 -c kalpa GET /api/v1/ast/fund-fee-closes -p holdDate=2026-11-12 --get data.0`이
  `{'keyId': 1, 'trName': '펀드운용보수 미수처리', … 'corpCode': None, …}`를 냈다. 작은따옴표·`None`·`True`라 다음 호출의 `-b`에 그대로 넣으면 `JSON 본문 파싱 실패: Expecting property name enclosed in double quotes`로 실패한다.
  조회한 줄을 그대로 [결산처리]·[결산취소]에 보내는 일이 이벤트마다 있어(#1218 결산, #1174 환평가) 결국 `--raw | python3 -c 'json.dumps(…["data"][0])'`로 우회했다.
- 고칠 것:
  1. `--get` 결과가 dict·list면 `json.dumps(v, ensure_ascii=False)`로 출력한다(문자열·숫자는 지금처럼 맨 값).
  2. 머리말이 붙지 않는지 확인한다(`$(yunhee api … --get data.0)`으로 바로 쓰는 용도).
- 확인: `ROW=$(yunhee api … --get data.0); yunhee api -u 301 -c kalpa POST /api/v1/ast/fund-fee-closes/cancel -b "{\"items\":[$ROW]}"` → 파싱 오류 없이 서버까지 간다(시험 뒤 [결산처리]로 되돌림).

## 2. `compare` — SQL 쪽 파라미터만 빠졌는데 첫 줄이 `[ERROR] TOBE API 결과`다, 필수 파라미터를 나눠서 알려 준다 (중간)

- 일어난 일:
  - `yunhee compare GET /api/v1/ast/fx-evals -u 301 -c kalpa -p closeDate=2026-11-14 --sql ast06_tr.selectFxEvalList --param companyId=… --param closeDate=2026-11-14` →
    `[ERROR] TOBE API 결과: rows=1` / `[ERROR] AS-IS SQL 실행 실패: syntax error at or near ":"` / `SQL 필수 파라미터 누락 (-- 필요: assetType, holdDate)`. TOBE는 정상인데 첫 줄만 보면 TOBE가 실패한 것으로 읽힌다.
  - `compare GET /api/v1/ast/books/finance … --sql ast09_book.selectByHoldDate`는 처음엔 `-- 필요: astType, searchText`를, `ast06_tr.selectDepositTr`는 `assetType`을 실행 뒤에 알려 줬다. 화면마다 2~3번 다시 돌렸다(수정사항 064 #3.2 "실행 전에 한 번에"가 아직 일부만 된 것으로 보인다).
- 고칠 것:
  1. SQL 쪽만 실패하면 TOBE 줄은 `TOBE API rows=1 ✅`(정보)로, 실패 줄만 `[ERROR] AS-IS SQL …`로 낸다.
  2. 실행 전에 `analysis sql`의 "파라미터" 줄 전체와 `--param`으로 받은 것을 비교해, 빠진 것을 **SQL을 돌리기 전에** 한 줄로 알리고 돌리지 않는다: `SQL 파라미터 부족: assetType, holdDate (받음: companyId, closeDate) — --param으로 주거나 --fill-missing`.
- 확인: 위 첫 호출 → `[ERROR] TOBE …` 줄이 없고, 실행 전 안내 한 줄만 나온다.
- **추가 재현(2026-11-14 DCR-BZ-0005) — 로그인 사원 자동 보충이 `personId`를 못 채운다**:
  `yunhee compare GET /api/v1/apr/apprs/dcr-write -u 401 -c kalpa -p startDate=2026-01-01 -p closeDate=2026-11-14 --sql apr01_appr.selectByDcrWritePaging --param companyId=202611109046432 --param startDate=2026-01-01 --param closeDate=2026-11-14 --param searchText=%`
  → `SQL params: … empId=202611109048654, orgId=202611109048610 …` / `SQL 필수 파라미터 누락 (-- 필요: limit, offset, personId)` / 첫 줄 `[ERROR] TOBE API 결과: rows=22`.
  0.9.5 changelog(062 #2)는 "로그인 사원 정보(`userId`, `personId`, `orgId`, `companyId`)를 미입력 SQL 파라미터에 자동으로 채운다"고 했는데, 실제로는 `empId`·`orgId`만 채운다. 이 SQL은 `#{personId}`를 쓴다(`apr01_reg_emp_id = #{personId}`).
  - 고칠 것:
    1. 로그인 사원 ID 하나를 **SQL이 실제로 쓰는 이름으로** 넣는다. AS-IS 매퍼마다 이름이 다르다: `personId`·`empId`·`userId`·`regEmpId`·`stepEmpId`. 순서: SQL 파라미터 목록(`analysis sql`의 "파라미터" 줄)에 있는 이름 중 위 목록에 있는 것을 모두 같은 사원 ID로 채운다. 이미 `--param`으로 준 이름은 건드리지 않는다.
    2. 조직은 `orgId`·`orgCodeId`, 회사는 `companyId`. 같은 규칙.
    3. 페이징 SQL(`…Paging`)의 `offset`·`limit`은 API에 준 `-p offset=`·`-p limit=`를 그대로 쓰고, 없으면 API 쪽 기본값(이 API는 0·100)과 같은 값을 쓴다. 쓴 값을 `SQL params` 줄에 `offset=0(기본)`처럼 보인다. API가 `total`을 주면(`API rows=22 (total 22)`) `--total-sql`이 없어도 "총건수 SQL 없음 — --total-sql apr01_appr.selectByDcrWriteTotal"처럼 같은 매퍼의 `…Total` ID를 제안한다.
  - 확인: 위 명령(`--param personId` 없이) → `SQL params: … personId=202611109048654(로그인) …`, `API rows=22 (total 22), SQL rows=22 ✅`.

## 3. `compare` — `=` 비교 파라미터에 `%`를 주면 SQL 0행인데 이유를 안 알려 준다 (작음)

- 일어난 일: `compare GET /api/v1/ast/book-fund-fees/fund-fee-books … --sql ast30_book_fund_fee.selectFundFeeBook --param fundCode=% --param searchText=%` → `API rows=5, SQL rows=0 ❌`.
  원인은 `<when test="fundCode != null"> AND t1.ast30_fund_cd = #{fundCode}`(같음 비교)에 `%`를 준 것, 반대로 `ast33_fund_trans.selectByDate`는 `LIKE UPPER(#{searchText})`라 빈 값이면 0행이었다(`API rows=1, SQL rows=0`). `analysis sql -o code`를 열어 보고서야 알았다.
- 고칠 것: SQL 행이 0이고 API 행이 0이 아니면, 받은 파라미터마다 SQL에서 쓰는 모양(`=`·`LIKE`·`IN`·`<if test>`)을 한 줄씩 보여 준다. 특히 `%`를 `=`에 넣었거나, 빈 값을 `LIKE`에 넣었으면 `⚠ fundCode='%'가 '=' 비교에 쓰임 — 빼거나 실제 값`처럼 짚는다.
- 확인: 위 호출 → `⚠ fundCode='%'…` 줄. `--param fundCode` 없이 → `5 = 5 ✅`.

## 7. `biz-authz`·`biz-endpoints` — `--screen`으로 못 찾는 화면이 있고, GET 시험이 필수 파라미터 없이 "0행"으로 끝난다 (중간)

- 일어난 일:
  - `yunhee biz-authz ast --screen 1218,1252,1216,1401 -u 401 -c kalpa --probe-write --dry-run` → `조회된 엔드포인트가 없습니다`. 같은 화면들로 `biz-event-new`는 API를 찾았고, `--path fund-fee-closes --path fund-trans`로 바꾸면 나온다.
    `yunhee biz-endpoints --screen 1214`(ICAM 운용보수 발생내역, `Icam10_Tab_FundMngFee`)도 빈 결과였다 — 화면이 API를 `Icam10_Lookup_getICAM`(팝업) 안에서 부른다.
  - `--path`로 돌린 결과의 GET 줄이 `GET /api/v1/ast/fund-fee-closes | 회사 | 200 rows=0 | ⚠?(0행 — 자료 없음)`이었다. 필수 `holdDate`를 무엇으로 넣었는지 안 보이고, 실제로 `holdDate=2026-11-12`면 사원 401도 1행을 받는다(이 흐름에서 의심 #119가 나왔다). "자료 없음"으로 끝나 놓칠 뻔했다.
- 고칠 것:
  1. `--screen`이 화면 번호 → 클래스 → 그 화면과 **팝업·탭(함께 쓰는 클래스)**의 프론트 API 호출까지 따라가 엔드포인트를 모은다(`biz-event-new`와 같은 수집 함수를 쓴다).

- 확인: `yunhee biz-authz ast --screen 1218 -u 401 -c kalpa -p holdDate=2026-11-12` → `GET /fund-fee-closes … 200 rows=1 | ⚠허용(메뉴 없음)`.

  1. `--no-link`: 연결 단계를 건너뛰고 상신·승인만 한다. `--ref`는 필수가 아니게.
  2. `--effect-date YYYY-MM-DD`: 시행일을 정한다(A72는 시행일 연월로 찾는다). 지금은 `effectDate`가 오늘로 들어간다.
  3. 링크코드가 연결 API를 모를 때의 "후보"는 **같은 도메인**(A72면 `flt`)의 `appr-id`·`appr` 경로만 보이고, 없으면 `연결 API 없음 — 링크코드·시행월로만 찾는 결재일 수 있음: --no-link`라고 안내한다.
  4. `--seed-arg` 값으로 제목을 만들 때 seed가 연도를 붙이는지 알려 준다: A09 seed는 `(yyyy년 {periodString})`이라 `periodString=2026년 4분기`를 주면 제목이 "2026년 2026년 4분기"가 된다(이번에 실제로 그렇게 나왔다). `--dry-run`의 제목 줄을 보고 고칠 수 있게, `--dry-run` 결과 맨 위에 `제목: …`을 한 줄로.
- 확인: `yunhee biz-appr A72 -u 301 -c kalpa --approver 100 --no-link --effect-date 2026-12-01 --title "임직원매매 책임자보고(2026년 12월)" --confirm` → 상신·승인 30, `GET /api/v1/flt/ceo-reports/apprs?startDate=2026-12-01` → 그 문서 "완료".
