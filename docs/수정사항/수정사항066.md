- 확인: 위 dry-run이 `연결 POST /api/v1/biz/promos/cards/appr-link`를 낸다.

## 4. `compare` — 원본 화면이 `%`를 보내는 파라미터를 안내하지 않는다 (낮음)

- 일어난 일: #1132·#1136·#1209·#1130 창에서 원본 화면은 "전체"를 `provideRcvType="%"`·`crmName="%"`·`statusCode="%"`·`providePurCode = 코드 + "%"`로 보낸다. `compare`는 `-- 필요: provideRcvType`만 알려 줘서 값을 몰라 `analysis method`·`grep`으로 화면 코드를 찾아야 했다(`10`을 주면 0행, `10%`가 맞음).
- 고칠 것: 필수 파라미터 안내에 화면 클래스(`--grid` 또는 SQL을 부르는 화면)에서 그 키에 넣는 값의 모양을 같이 보인다: `provideRcvType (화면 기본 "%")`, `providePurCode (화면: 코드 + "%")`.
- 확인: `compare GET /api/v1/biz/promos/others … --sql biz01_promo.selectByOther --grid Biz01_Tab_Other`(provideRcvType 빼고) → `-- 필요: provideRcvType (화면 기본 "%")`.

## 5. `api` — 요청 헤더를 줄 수 없다 (중간)

- 일어난 일: ICAM 배치 본체(`biz/batch/action/Icam*Action`, ICAM 시뮬레이터)는 cron 진입점 `GET|POST /api/v1/batch/{actionCode}`로만 돈다. 이 진입점은 JWT가 아니라 `X-Batch-Api-Key` 헤더(개발 프로필 `dev-batch-key`)와 IP로 막는다(`BatchApiKeyFilter`). `yunhee api`에는 헤더 옵션이 없어 `icamFund`·`icamOfficeMngFee`·`icamFundMngFee`를 한 번도 돌리지 못했다. 화면 버튼은 `DisabledIcamBatchRunner`라 늘 400이다(의심 #179). 셸 curl은 규칙상 쓰지 않는다. SB01 작업기록(2026-11-04)에도 같은 이유로 "성공 경로 미확인"이 남아 있다.
- 고칠 것:
  1. `-H/--header "이름: 값"`(반복)을 더한다.
  2. `--no-login`을 더한다(JWT 없이 헤더만으로 부르기). 배치 진입점처럼 로그인이 필요 없는 경로용이다.
  3. 값은 환경변수로도 받는다: `-H "X-Batch-Api-Key: $env:ASSETERP_BATCH_API_KEY"` 또는 `YUNHEE_API_HEADERS`. 출력·로그에서 값은 `***`로 가린다.
- 확인: `yunhee api POST /api/v1/batch/icamFund -p companyId=28000 -p worker=yunhee --no-login -H "X-Batch-Api-Key: dev-batch-key" --track icam03_fund` → 200 `FUND 작업완료..commit`, `icam03_fund` 행 변화가 보인다. 헤더 없이는 401·403이 나온다.

## 6. `biz-appr` — KFS(회사 28000) 기본 계정 104로 쓸 수 없고, 비밀번호 출처가 `api`와 다르다 (중간)

- 일어난 일:
  - `biz-appr A33 --ref … -u 104 -c kfstest` → `로그인 실패 (HTTP 401) … 실패 1/5회`. `비밀번호 출처 emp01_password`라고 나왔다. `yunhee api`(인자 없음)는 같은 104를 **admin 서브도메인**에 `.env.yunhee`의 `YUNHEE_TEST_ADMIN_PASS`로 넣어 성공한다(`tenant=admin … company=28000`). 같은 사번인데 두 명령이 다른 서브도메인과 다른 비밀번호를 써서 잠금 위험이 생겼다.
  - `-u 104 -c admin --password …` → `사원을 찾을 수 없습니다: 104 (회사: admin)`. `-u 29049 -c admin`(사원 ID)도 같았다. 사원을 `-c`의 회사(admin = 0)에서만 찾기 때문이다.
  - 결국 A33(ICAM 사용자ID 신청서)·A34(미사용ID 권한정지 신청서)는 `GET /apr/apprs/new` → `PUT /apr/apprs/{id}`(mode request, `effectDate` 필수) → 연결을 `yunhee api`로 손으로 했다.
- 고칠 것:
  1. `-u`·`-c`를 생략하면 `yunhee api` 기본 계정과 같은 계정을 쓴다(같은 서브도메인, 같은 비밀번호 출처).
  2. 사원 찾기는 "로그인한 사원의 회사"로 한다. 로그인 응답의 `company=`를 쓴다. 회사 코드가 같은지만 보지 않는다.
  3. 로그인 전에 비밀번호 출처(`YUNHEE_TEST_ACCOUNTS` > `.env.yunhee` 기본 계정 > `emp01_password`)를 한 줄로 보인다. `api`가 이미 같은 계정으로 로그인해 둔 토큰(`login=reused`)이 있으면 그것을 쓴다.
  4. 연결 후보 표에 A33·A34를 더한다: `PUT /icam/users/{ref}/appr-id {apprId}`, A34는 `PUT /icam/users/stops/appr-id {ids:[…], apprId}`(여러 행을 한 문서에).
- 확인: `yunhee biz-appr A33 --ref <icam55 id> --approver 29025 --dry-run`(-u·-c 없이) → `상신자 104(천영임, 회사 28000)`, `연결 PUT /api/v1/icam/users/<id>/appr-id`.

## 7. `biz-authz` — 날짜 범위가 필요한 조회를 좁은 기본값으로 불러 "0행 — 자료 없음"이라 한다 (낮음)

- 일어난 일: `biz-authz icam -u 401 -c kalpa`에서 `GET /icam/users`(`startDate`·`closeDate` 필수)가 `200 rows=0 ⚠?(0행 — 자료 없음)`이었다. 손으로 `startDate=2000-01-01&closeDate=2099-12-31`을 주니 **KFS 신청서 13행**이 나왔다(의심 #244, 상). `users/results`·`users/stop-auths`도 같다. 회사 열이 없는 표라 회사 조건으로 0행이 된 것이 아니었는데, 판정만 보면 넘어갈 뻔했다.
- 고칠 것:
  1. 안전 GET 프로브에서 이름이 `startDate`·`closeDate`·`fromDate`·`toDate`인 파라미터는 넓은 범위(`2000-01-01`~`2099-12-31`)로 준다. `stdDate`·`yearText`는 DB에서 그 표의 최근 값을 찾을 수 있으면 그 값을 쓴다.
  2. 0행이면 쓴 파라미터를 같이 보인다: `0행 (startDate=… closeDate=…)`. 이렇게 하면 "자료 없음"인지 "조건이 좁음"인지 가릴 수 있다.
  3. SQL에 회사 조건이 없는 표(매퍼에 `company_id` 조건이 없음)는 `⚠ 회사 조건 없음 — 넓게 다시 부름`으로 따로 표시한다.
- 확인: 위 명령 → `GET /icam/users … 200 rows=13 ⚠ 회사 조건 없는 KFS 자료를 사원이 받음`.

## 8. `mapper-run`·`compare` — 빈 값 파라미터(`-p key=`)를 받으면 알려 주지 않는다 (낮음)

- 일어난 일: `mapper-run "IcamFundOperateStatusMapper.xml#selectFundBookAvg" --compare icam06_fund_book.selectFundBookAvg -p companyId=100 … -p fundType= -p searchText= --count` → `TOBE rows=0, AS-IS rows=0 ✅`. 실제로는 SQL이 `WHERE (:fundType='1' AND …) OR (:fundType='2' AND …)`라서 빈 값이면 늘 0행이다. `fundType=1`을 주니 6=6이었다. 빈 값을 빼면 `파라미터 부족: fundType`이라고 알려 주는데, 빈 값을 주면 아무 말 없이 "0=0 ✅"가 나와 헛시험이 됐다. (실수 목록의 "불리언 `-p flag=false`는 글자"와 같은 부류다.)
- 고칠 것:
  1. `-p key=`(빈 글자)를 받으면 한 줄 경고를 낸다: `⚠ fundType='' — 빈 글자로 넘깁니다(빼면 null)`.
  2. 두 쪽이 모두 0행이면 `✅` 대신 `0=0 (확인 못 함 — 조건을 넓혀 보세요)`를 낸다. 빈 값을 받은 파라미터가 SQL의 `=` 비교에 쓰이면 그 이름을 같이 보인다.
- 확인: 위 명령 → 경고 줄과 `0=0 (확인 못 함 …, fundType='' 이 = 비교에 쓰임)`.
