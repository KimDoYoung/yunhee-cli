## 공통 기반 — Java 매퍼 시그니처 읽기 (1·2·3이 함께 씀)

- 입력은 `<Name>Mapper.xml`의 `namespace`(예: `kr.co.kfs.asseterp.biz.emp.mapper.EmpDeductMapper`)다. 이것으로 같은 이름의 Java 인터페이스를 찾는다.
- statement id와 같은 이름의 메서드에서 파라미터마다 (이름, Java 타입)을 뽑는다.
  - `@Param("deductId") Long deductId` → (`deductId`, `Long`)
  - 파라미터가 record·DTO 하나면(`@Param` 없음, 또는 `@Param("req") XxxReq req`) 그 record 구성요소·DTO 필드를 펼친다. `#{companyId}`·`#{req.companyId}` 둘 다 찾을 수 있어야 한다.
  - `List<Long>`·`Collection<String>`은 `<foreach collection>`용 목록으로 표시한다.
- 타입은 PostgreSQL 쪽으로 바꾼다.

  | Java | PostgreSQL |
  |:---|:---|
  | `Long`·`long`·`Integer`·`int`·`BigDecimal`·`Double` | `numeric` |
  | `String` | `text` |
  | `LocalDate` | `date` |
  | `LocalDateTime` | `timestamp` |
  | `Boolean`·`boolean` | `text` — 이 DB는 불리언을 `'true'`/`'false'` 글자 열로 쓴다(예: `emp20_cancel = 'true'`). 실수 목록의 "`-p flag=false`는 글자"와 같은 이유 |

- 결과를 캐시하고 Java 파일의 mtime이 바뀌면 다시 읽는다. 메서드를 못 찾으면 그 사실을 한 줄로 알리고, 지금처럼 타입을 모르는 채로 진행한다.
- 확인: 아래 세 메서드의 시그니처가 이대로 나와야 한다(내부 함수 단위 시험이면 된다).
  - `EmpDeductMapper.insertAddDeductTypes`: `deductId: Long, personId: Long, startDate: LocalDate, companyId: Long, itemTypeCodeName: String`(Java: `EmpDeductMapper.java:37`)
  - `FrmListMapper.selectIcsNotice`: `companyId: Long, empId: Long, orgCd: Long, selectDate: LocalDate`(`FrmListMapper.java:25`)
  - `BatchSchMapper.insertSch04List`: `companyId: Long, stdDate: LocalDate`(`BatchSchMapper.java:13`)

## 1. `test-params` (새 명령) + `mapper-run --auto-params` — 시험 값을 DB에서 스스로 찾기 (높음)

- 일어난 일: `sql-check` 거짓경보 4건을 확인할 때 이렇게 했다.
  1. `mapper-run … --rollback`을 값 없이 불러 `-- 필요: companyId, stdDate`를 봤다.
  2. Java 시그니처를 `yunhee grep`으로 찾았다.
  3. `information_schema`로 열 이름을 봤다(이 단계 전에 한 번 짐작했다가 틀렸다).
  4. `yunhee sql`로 조건에 맞는 실제 행을 찾았다.
  5. 그 값을 `-p`로 넣었다.

  문장 하나에 이 과정을 3~5번 반복했다. `insertAddDeductTypes`는 "이전 공제 이력이 있는 사원"이어야 의미 있는 실행이 되므로, 아무 사원이나 넣으면 0행 INSERT로 헛시험이 된다.
- 만들 것:
  1. **`yunhee test-params "<매퍼.xml>#<id>" [-c <회사코드|회사ID>] [--n 3] [-o text|json|args]`**
     - 필요한 파라미터마다 넣을 값을 고르고 근거를 함께 보인다.
     - 출력 예(text):
       ```
       EmpDeductMapper.insertAddDeductTypes  (Java EmpDeductMapper.java:37)
         companyId       Long       28000            ← sys01_company (회사 지정 -c 또는 기본 회사)
         personId        Long       29029            ← emp35_deduct.emp35_person_id (같은 문장 WHERE emp35_person_id = #{personId})
         deductId        Long       202306211546068  ← emp35_deduct.emp35_deduct_id (personId=29029 의 행)
         startDate       LocalDate  2023-07-01       ← emp35_deduct.emp35_start_date (같은 행)
         itemTypeCodeName String    AddDeductType    ← Java 호출부 상수 EmpDeductService.java:27 ADD_DEDUCT_TYPE
       다시 돌리기: yunhee mapper-run "backend/src/main/resources/mapper/EmpDeductMapper.xml#insertAddDeductTypes" -p companyId=28000 -p personId=29029 -p deductId=202306211546068 -p startDate=2023-07-01 -p itemTypeCodeName=AddDeductType --rollback
       ```
     - `-o args`는 `-p k=v …`만 한 줄로 낸다(스크립트에서 이어 붙이는 용도). `-o json`은 `{name, javaType, value, source}` 배열이다.
  2. **`yunhee mapper-run … --auto-params`**: 위에서 고른 값으로 바로 실행한다. 사람이 준 `-p`가 이긴다(일부만 직접 주고 나머지는 자동으로 채울 수 있다). 실행 전에 고른 값을 한 줄로 보인다.
- 값 고르는 순서(앞에서 정해지면 뒤는 보지 않는다):
  1. **SQL 안에서 그 파라미터와 비교되는 열.** `WHERE emp35_person_id = #{personId}`·`AND x.col IN (#{…})`·`JOIN … ON col = #{…}`처럼 `#{p}`와 맞붙은 열을 찾고, 그 열이 있는 표에서 실제 값을 고른다. `sql-check`가 이미 펼친 SQL을 쓰면 된다.
  2. **같은 행 묶기.** 한 표에서 둘 이상의 파라미터 값을 뽑을 때(위 `personId`·`deductId`·`startDate`)는 **같은 행**에서 고른다. 서로 엇갈린 행의 값을 섞으면 0행이 된다.
  3. **이름 규칙.** `companyId` → `-c`로 정한 회사, 없으면 `.env.yunhee` 기본 계정의 회사. `personId`·`empId`·`userId` → 그 회사의 재직 사원(`emp01_person`). `orgId`·`orgCd` → 그 사원의 현재 조직. `stdDate`·`selectDate`·`*Date` → 오늘. `startDate`/`closeDate` 짝 → `2000-01-01`/`2099-12-31`(수정사항066 7절과 같은 원칙). `yearText` → 올해.
  4. **Java 호출부의 상수.** 서비스에서 그 매퍼 메서드를 부르는 곳의 인자가 `static final` 상수면 그 값을 쓴다(위 `ADD_DEDUCT_TYPE = "AddDeductType"`).
  5. 못 정하면 `?`로 두고 이유를 적는다(`-- 필요: … (값을 못 정함: 비교 열 없음)`). **빈 글자로 채우지 않는다**(수정사항066 8절 — 빈 값은 헛시험이 된다).
- 고른 값이 "의미 있는지"도 본다. SELECT는 `--count`로 행이 1 이상이 나오는 조합을 `--n`번까지 시도해 고르고, 끝까지 0행이면 `0행 — 조건에 맞는 자료 없음(고른 값: …)`로 알린다. 쓰기 문장은 `--rollback`으로 실행한 영향 행 수를 함께 보인다.
- 열 이름은 반드시 `information_schema.columns`로 확인한 것만 쓴다. 이 기능을 만든 계기 중 하나가 열 이름 짐작이다.
- 확인(모두 `--rollback`, DB는 바뀌지 않는다):
  - `yunhee mapper-run "backend/src/main/resources/mapper/EmpDeductMapper.xml#insertAddDeductTypes" --auto-params --rollback` → 고른 값 줄 + `INSERT n (롤백됨)`, n ≥ 1(집 DB: 29029/202306211546068에서 4).
  - `yunhee mapper-run "backend/src/main/resources/mapper/BatchSchMapper.xml#insertSch04List" --auto-params --rollback` → `INSERT n (롤백됨)`(집 DB: companyId=28000·오늘에서 14).
  - `yunhee test-params "backend/src/main/resources/mapper/FrmListMapper.xml#selectNoticeCnt"` → `companyId`·`personId`·`orgId` 세 값과 근거, `rows=1`.
  - `yunhee test-params "…/FrmListMapper.xml#selectIcsNotice" -o args` → `-p companyId=… -p empId=… -p orgCd=… -p selectDate=YYYY-MM-DD` 한 줄.
  - 사람이 준 값 우선: `… --auto-params -p personId=29043` → personId는 29043, deductId는 29043의 행에서 다시 고른다.

## 2. `sql-check` — 파라미터 타입을 Java 시그니처에서 가져와 바인딩, 기계용 출력 (높음)

- 일어난 일: `yunhee sql-check --tobe backend/src/main/resources/mapper --summary`에서 4건이 이렇게 실패했다.
  ```
  BatchSchMapper.insertSch04List       ERROR: UNION types numeric and text cannot be matched
  EmpDeductMapper.insertAddDeductTypes ERROR: column "emp36_deduct_id" is of type numeric but expression is of type text
  FrmListMapper.selectNoticeCnt        ERROR: UNION types numeric and text cannot be matched
  FrmListMapper.selectIcsNotice        ERROR: UNION types text and numeric cannot be matched
  ```
  모두 `#{companyId}`·`#{deductId}`(Java `Long`)를 EXPLAIN이 글자(text/unknown)로 넣어서 생긴 것이다. 실제 실행(Java가 `Long`으로 바인딩)과 `mapper-run`(실제 값)에서는 모두 정상이었다. 프로젝트는 이 4건을 `tools/tests/sql-check-known.tsv`(문장 + 오류 문구로 건너뜀)로 빼 두었다. 이 수정이 들어가면 그 파일이 필요 없어져야 한다.
- 고칠 것:
  1. `--tobe` 모드에서 공통 기반으로 Java 타입을 알면 EXPLAIN 바인딩을 타입대로 한다. `PREPARE`의 파라미터 타입을 주거나 `$1::numeric`처럼 캐스트를 붙인다. 값은 지금처럼 NULL이나 더미를 써도 된다. 실행하지 않으니 타입만 맞으면 된다.
  2. 타입을 못 정한 파라미터는 지금처럼 한다. 결과 줄 끝에 `(타입 모름: deductId)`를 붙여, 남은 타입 오류가 거짓경보일 수 있음을 알린다.
  3. 기본으로 켠다. 옛 동작을 보려면 `--no-java-types`를 준다.
  4. **기계용 출력** `-o tsv`: `매퍼\t문장ID\t결과(ok|fail|skip)\t분류\t오류 첫 줄`.
     - 분류는 `missing`(does not exist — 테이블·열·함수 없음), `type`(타입 불일치), `syntax`, `other`.
     - 프로젝트의 `tools/tests/sql-check.sh`가 지금은 `--summary` 사람용 글을 정규식으로 읽는다. tsv로 바꿀 수 있게 한다.
- 확인:
  - `yunhee sql-check --tobe backend/src/main/resources/mapper --summary` → 위 4건이 ✅로 바뀌고, 남는 실패는 **DB에 없는 것 2건**이다.
    - `AttOvertimeReqMapper.getConfirmList`(열 `att03_confirm_yn` 없음)
    - `PlnResrchMapper.selectDetailInit`(함수 `f_apr_get_approval` 없음)
  - `--no-java-types`로 다시 돌리면 옛 결과(실패 6)가 그대로 나온다.
  - `-o tsv | awk -F'\t' '$3=="fail"'` → 두 줄, 분류 `missing`.

## 3. `test-gen-mapper` (새 명령) — 매퍼 스모크 시험(JUnit) 뼈대 만들기 (높음)

- 일어난 일: 시험이 없는 도메인이 15개다(`att chk company dbm est frm help ifi kfs mrb opr pln push scm user`). `ast`·`sys`도 얇다. 지금 있는 DbTest(예: `backend/src/test/java/kr/co/kfs/asseterp/biz/sys/SysUserPropsDbTest.java`, `biz/emp/Emp*DbTest.java`)는 모두 손으로 썼다. 매퍼 하나당 "모든 문장이 오류 없이 도는가"부터 손으로 쓰면 하루가 간다.
- 만들 것: **`yunhee test-gen-mapper <MapperName|도메인> [-c <회사>] [--out backend/src/test/java] [--dry-run] [--force]`**
  - 입력 예: `AttCommuteMapper` 또는 도메인 `att`(그 도메인의 매퍼 전부).
  - 출력: `backend/src/test/java/kr/co/kfs/asseterp/biz/<도메인>/<Mapper이름>SmokeDbTest.java` — 매퍼 하나당 파일 하나.
  - 프로젝트 관례를 그대로 따른다(`SysUserPropsDbTest` 참고):
    (메서드는 실제 `AttCommuteMapper.java`의 것 — `selectByTextAdmin` L19, `insertBatch` L27. 인자 `…`는 생성 때 채워진다)
    ```java
    @MybatisTest
    @AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
    class AttCommuteMapperSmokeDbTest {
        @Autowired AttCommuteMapper mapper;

        /** 자동 생성(yunhee test-gen-mapper 2026-11-16) — 값: test-params(회사 28000). 손으로 고치면 맨 위 표시를 지운다. */
        @Test void selectByTextAdmin() {
            var rows = mapper.selectByTextAdmin(28000L, 29029L, …);
            assertThat(rows).isNotNull();          // 스모크: 오류 없이 돈다
        }

        @Test void insertBatch() {                 // @MybatisTest 가 롤백한다
            int n = mapper.insertBatch(28000L, 29029L, …);
            assertThat(n).isGreaterThanOrEqualTo(0);
        }
    }
    ```
  - 값은 1(`test-params`)로 채운다. Java 리터럴로 바꾼다: `Long` → `28000L`, `LocalDate` → `LocalDate.parse("…")`, record·DTO 인자 → 생성자 호출(구성요소 순서는 record 선언을 읽는다), `List<Long>` → `List.of(…)`.
  - 값을 못 정한 문장은 `@Disabled("값을 못 정함: <파라미터> — test-params 참고")`로 만든다. 지어낸 값은 넣지 않는다.
  - DELETE·UPDATE도 롤백되므로 실행한다. 단 `@MybatisTest` 밖에서 커밋하는 것(`REQUIRES_NEW`·DB 함수 안의 COMMIT 등)이 의심되면 `@Disabled("롤백 밖 커밋 의심")`으로 한다.
  - 파일이 이미 있으면 덮지 않는다(`--force`일 때만 덮음). `--dry-run`은 만들 파일 목록과 문장별 상태(값 채움 / @Disabled 이유)만 보인다.
  - 끝에 요약을 낸다: `매퍼 12 · 문장 148 · 채움 131 · Disabled 17(값 없음 15, 커밋 의심 2)`.
- 확인:
  - `yunhee test-gen-mapper att --dry-run` → `att` 매퍼 목록과 문장별 상태가 나오고, 파일은 만들지 않는다.
  - `yunhee test-gen-mapper AttCommuteMapper` → 파일 1개가 생긴다. 이어서 `yunhee run "gradle test --tests '*AttCommuteMapperSmokeDbTest'"`(backend 폴더)가 컴파일되고 통과한다(Disabled는 건너뜀).
  - 같은 명령을 한 번 더 부르면 `이미 있음 — --force`로 멈춘다.
  - 만든 파일이 `@Setter`·`@Data`·Map 파라미터를 쓰지 않는다(프로젝트 규칙 `docs/TOBE-Framework.md`).

## 4. `test-scenario-skel` (새 명령) — 업무분석 이벤트 → 시나리오 파이썬 뼈대 (중간)

- 일어난 일: 업무 시나리오 시험은 `AssetERP/tools/tests/scenario/`에 있다.
  - `runner.py`: `Client(회사, 사번, 비밀번호)`, `Scenario.step(no, desc, client, method, path, body, expect)`, `raw(…)`, `check(…)`, `db_rows(sql)`
  - 모듈: `apr.py`·`emp.py`·`pay.py`, 등록: `all.py`의 `SCENARIOS`
  - 원천은 업무분석 이벤트 문서(`docs/2-업무분석/biz-event/<도메인>/<ID>-*.md`) 끝의 `<details>` "시나리오 데이터" yaml이다(예: `EMP-BZ-0014-휴가신청결재.md` L82~). 그런데 yaml의 `body`가 일부만 있고, 나머지는 주석(`# mode=request, …`)이나 `<휴가/휴가신청>` 같은 자리표시라 그대로 실행할 수 없다. 이벤트 9개를 옮길 때 DTO(record)를 하나씩 열어 요청 본문을 손으로 썼다.
- 만들 것: **`yunhee test-scenario-skel <이벤트ID> [--company kova] [--module emp] [--print]`**
  - yaml `steps`마다 `sc.step(...)` 한 줄(또는 `api:`가 목록이면 여러 줄)을 만든다.
  - **요청 본문**: TOBE 컨트롤러에서 `METHOD path`에 맞는 메서드를 찾고, `@RequestBody`의 record 구성요소를 전부 키로 넣는다. yaml `body`에 있는 값은 그 값을 쓰고, 없는 키는 `None  # TODO <Java 타입>`으로 둔다. 자리표시(`<…>`)는 `sc.ctx["…"]`로 바꾸고 주석을 단다.
  - **기대값**: `expect.field/value` → `expect={"field": value}`, `expect.rows: n` → `expect={"length": n}` 주석, `expect.table/delta` → `count_rows` 전후 비교 `sc.check(...)` 뼈대.
  - 계정: yaml `actor`의 회사·사번을 `--company`로 바꾼다. 시나리오는 가상회사 kova(직원 100·201·202·301·302·401·402, 비밀번호 1111)에서 돈다.
  - 출력: `--print`면 화면에만 보이고, 아니면 `tools/tests/scenario/<module>.py` 끝에 함수 `xxx_bz_nnnn(emp)`를 덧붙이고 `all.py`의 `SCENARIOS`에 한 줄을 더한다. 같은 이름의 함수가 있으면 멈춘다.
- 확인:
  - `yunhee test-scenario-skel EMP-BZ-0014 --print` → 이미 손으로 쓴 `tools/tests/scenario/emp.py`의 `emp_bz_0014`와 단계 번호·메서드·경로가 같다. `PUT /api/v1/emp/my-leaves` 본문 키가 그 컨트롤러 `@RequestBody` record의 구성요소와 같다.
  - `yunhee test-scenario-skel PAY-BZ-0005 --print` → 파이썬 문법 오류가 없다(`python3 -c 'import ast; ast.parse(…)'`).

## 5. `test-coverage` (새 명령) — 어떤 매퍼 문장·화면이 시험되고 있나 (중간)

- 일어난 일: "시험이 없는 도메인 15개"는 `backend/src/test/java/…/biz/` 폴더 이름을 보고 셌다. 실제로 어떤 매퍼 문장이 한 번이라도 실행되는지, 어느 화면(메뉴 번호)이 시험 밖인지는 모른다.
- 만들 것: **`yunhee test-coverage [--junit <JUnit XML 폴더>] [--scenario <scenario.json>] [--by domain|mapper|screen] [-o md|tsv]`**
  - **정적**: 시험 소스(`backend/src/test/java`)에서 `mapper.<메서드>(`·`service.<메서드>(` 호출을 찾고, 서비스는 `trace-crud`처럼 매퍼 문장까지 따라간다. 이것으로 문장마다 "시험이 부름 / 안 부름"을 정한다.
  - **동적(있으면)**: `tools/tests-all.sh`의 결과 폴더 `backend/junit/TEST-*.xml`(통과한 시험만)과 시나리오 결과를 받아, API → 컨트롤러 → 서비스 → 매퍼 문장으로 잇는다.
    - 주의: 지금 `scenario/scenario.json`은 단계마다 `{no, desc, ok, note}`만 있고 **부른 API가 없다**(2026-11-16 확인).
    - 그래서 시나리오 쪽은 `--since <시각> --until <시각>`으로 그 시간대의 서버 요청 기록(`yunhee log req`가 읽는 것)에서 `METHOD path`를 모은다.
    - 프로젝트가 나중에 `scenario.json` 단계에 `method`·`path`를 넣으면 그것을 먼저 쓴다(그 형식: `steps[].calls = [{method, path, status}]`).
  - **화면 단위**: `trace-pair`의 메뉴 ↔ 서비스 ↔ SQL 짝을 써서 `#1032 휴가신청 — 문장 14 중 9 시험됨`처럼 낸다. 표기는 프로젝트 규칙대로 화면번호 중심이다.
  - 출력 예(`--by domain`): `| 도메인 | 문장 | 시험됨 | 비율 |`. `-o tsv`는 문장 단위다.
- 확인:
  - `yunhee test-coverage --by domain` → `att`·`chk`·…(위 15개)의 시험됨이 0이다. `sys`의 `SysUserPropsMapper` 문장은 시험됨(`SysUserPropsDbTest`).
  - 3번으로 `AttCommuteMapperSmokeDbTest`를 만든 뒤 다시 돌리면 `att`의 숫자가 늘어난다.

## 6. `test-compare` (새 명령) — `compare`를 목록으로 한꺼번에, 결과를 기계용으로 (중간)

- 일어난 일: 프로젝트 일괄 시험기에 `--asis-compare`(조회 API vs AS-IS SQL 대조) 단계가 계획만 있고 비어 있다. `yunhee compare`는 한 건씩이고 출력이 사람용이라 단계로 묶기 어렵다.
- 만들 것: **`yunhee test-compare <목록.tsv> [-c <회사>] [-o tsv|junit] [--out <폴더>]`**
  - 목록 한 줄의 형식: `이름\tMETHOD path\tAS-IS SQL ID\t파라미터(k=v&…)\t옵션(--grid … --total-sql …)`. `#`으로 시작하는 줄은 주석이다.
  - 줄마다 `compare`와 같은 판정을 한다(행 수, 열 커버리지). 0=0은 `skip(확인 못 함)`으로 센다(수정사항066 8절과 같은 원칙).
  - `-o junit`은 `TEST-test-compare.xml` 하나에 줄마다 testcase를 넣는다. 그러면 프로젝트 `tools/tests/report.py junit`이 그대로 읽는다. `-o tsv`는 `이름\tok|fail|skip\tTOBE행\tASIS행\t메모`다.
  - 같은 계정 로그인은 한 번만 하고 토큰을 다시 쓴다(아래 7과 함께).
- 확인: 목록 3줄로 확인한다. 각각 이미 `compare`로 맞음을 확인한 조회 하나, 일부러 틀린 SQL ID 하나, 0행이 나오는 조건 하나다. 결과는 `ok 1 · fail 1 · skip 1`, `-o junit`의 XML에 `failures="1" skipped="1"`.

## 7. `api` — 같은 계정 로그인 실패 누적을 기억해 잠금 전에 멈춤 (낮음)

- 일어난 일: 서버는 로그인을 5회 실패하면 계정을 잠근다. 시험용 계정(kfstest 104·121·admin, kova 직원)이 잠기면 그 회사 관리자로 풀어야 한다. 프로젝트 실수 목록에 2026-11-10(두 번)·11-14에 잠금 직전까지 간 기록이 있다. 응답의 `실패 n/5회`는 보이지만, 다음 호출이 그 숫자를 기억하지 않는다.
- 고칠 것:
  1. 계정(서브도메인 + 사번)마다 마지막 로그인 실패 횟수를 `.yunhee/` 아래에 남긴다. 3/5 이상이면 다음 `api`·`biz-*`·`test-compare`가 로그인 전에 멈춘다: `⚠ kfstest/104 실패 3/5 — 더 부르면 잠길 수 있음. 비밀번호 출처: … (계속하려면 --force-login)`.
  2. 로그인에 성공하면 그 기록을 지운다.
- 확인: 일부러 틀린 비밀번호로 시험 계정(kova/402)을 3번 부르면, 4번째는 서버에 가지 않고 위 경고로 멈춘다. `--force-login`이면 간다. 올바른 비밀번호로 한 번 성공하면 기록이 0이 된다(끝나면 kova 관리자로 잠금 확인·해제).
