- `yunhee test-coverage --by domain` 합계가 **9,334문장**이다. `sql-check`의 4,667문장의 정확히 2배이고, 도메인마다 짝수다.
- `-o tsv --by mapper`를 보면 한 문장이 `deleteAcademics`와 `kr.co.kfs.asseterp.biz.emp.mapper.EmpAcademicMapper.deleteAcademics` **두 줄**로 나온다(정적 호출을 짧은 ID와 네임스페이스 ID로 따로 모으는 듯). 짧은 ID로 합치면 4,667문장 중 시험됨 844(18.1%), EMP 472 중 83(17.6%)이다. 표의 `emp 944 / 166`과 비율은 같지만 수는 2배다.

## 2. `--scenario`·`--junit`이 결과를 바꾸지 않는다

- 정적만 / `+--scenario` / `+--scenario --junit` 세 번의 결과가 줄 하나까지 같다. `sources` 칸에 `scenario` 출처는 0건이다.
- `scenario.json`은 `[{id, title, passed, failed, skipped, seconds, steps:[{no, desc, ok, note}]}]`이다. API 경로도 매퍼 문장도 들어 있지 않으니, 지금 형식으로는 연결할 수 없는 것이 당연하다. JUnit XML도 테스트 클래스 이름뿐이라, 정적 분석의 "테스트 → 서비스 → 매퍼" 연결과 다를 게 없어 보인다.
- 바라는 것: ① 입력을 써도 바뀐 것이 없으면 "시나리오 입력에서 연결된 문장 0 — 형식 …을 기대함"처럼 경고한다. ② 아래 3절의 서버 로그 방식을 쓴다.

## 3. 제안 — 서버 로그의 SQL로 "실제 실행된 문장" 세기

- 시나리오는 HTTP로 서버를 부른다. 서버 로그(DEBUG)에는 MyBatis가 문장마다 `… DEBUG k.c.k.a.b.e.m.E.selectNextId - ==>  Preparing: …`를 찍는다. `yunhee log tail --from 23:08 --to 23:10`도 "요청 612, SQL 4598"로 이미 센다.
- 걸림돌: 로그 패턴이 로거 이름을 줄여 **매퍼 클래스가 첫 글자(`E`·`C`·`A`)로만** 남는다. 매퍼를 특정할 수 없어서 문장 이름으로만 맞춰야 한다. 이 방식으로 EMP를 셌을 때 시나리오가 실행한 문장은 다음과 같았다. `selectNextId`처럼 여러 매퍼에 같은 이름이 있어 범위로만 나온다.
  - 이름 일치(상한): 214 / 472 = 45.3%
  - 이름이 한 매퍼에만 있는 것(확실): 77 = 16.3%
  - 확실 + 정적(JUnit) 83: 157 = 33.3%
- 바라는 것: `test-coverage --log <파일|docker> --from … --to …`(또는 `--since-run <run id>`)로 그 구간 `Preparing` 줄의 문장을 모아 커버리지에 더한다. 로거 이름이 줄어 있으면 도메인 패키지(`b.e.m` → `emp`·`est`)와 문장 이름으로 맞추고, 같은 이름이 여러 매퍼에 있으면 "모호"로 따로 센다. (프로젝트 쪽에서 매퍼 로거만 전체 이름으로 찍도록 logback을 바꾸면 정확해진다. 그건 프로젝트 결정.)
