# 수정사항 073 — 저장된 로그인(세션)이 다시 만든 회사의 옛 토큰을 그대로 씀: 0행·403

- 계기: framework-sprt 테스트 작업(2026-11-20). 가상회사 `igo`를 시험마다 지우고 다시 만드는 고정 시험 데이터(fixture)를 만들었다(`AssetERP/tools/tests/fixture-igo.sh`, 설계 `AssetERP/docs/5-테스트/fixture-설계.md`). 그 뒤 `yunhee test-compare … -c igo`로 조회 API ↔ AS-IS SQL을 대조했다.
- 작성: Claude(framework-sprt 세션), 사용자 요청. **yunhee 코드는 고치지 않았다** — framework-sprt 쪽에서 세션 파일을 지워 피해 갔다(아래 3절).

## 1. 무슨 일이 있었나

| 실행 | igo 회사 ID | 결과 |
|:---|:---|:---|
| 손으로 `test-compare` (fixture 직후) | 202611209696812 | ok 5 · fail 0 |
| `tests-all.sh --asis-compare` (fixture 가 igo 를 **다시 만든 뒤**) | 새 ID(다시 만듦) | **ok 0 · fail 5** — TOBE 4줄 0행, 1줄 `HTTP 403 ACCESS_DENIED` |
| 세션 파일을 지우고 다시 | 새 ID | ok 5 · fail 0 |

- 회사를 지우고 같은 서브도메인(`igo`)·같은 관리자(`admin/1111`)로 다시 만들면 **회사 ID 가 바뀐다**(전역 채번 `f_create_seq`).
- yunhee 는 `.yunhee/sessions/localhost_8082_igo_admin.json`(=`config.WORK_DIR/.yunhee/sessions/<host>_<회사>_<사용자>.json`)에 저장한 쿠키·헤더를 다시 쓴다.
- 그 토큰은 **아직 만료되지 않은 정상 JWT**라 서버가 401 을 주지 않는다 → `api_client.py`의 "401 이면 다시 로그인"(L1050 근처)이 안 걸린다. 토큰 속 회사 ID 는 **지워진 옛 회사**라
  - 회사 조건으로 거르는 조회는 0행(옛 회사에는 데이터가 없음)
  - 새 회사 ID 를 파라미터로 넘긴 조회(`/flt/item-types?companyId=<새 ID>`)는 "남의 회사" 403.
- 겉으로는 "TOBE 가 AS-IS 와 다르다"로 보여 **거짓 실패**가 된다. 원인이 세션이라는 단서가 출력에 없다.

## 2. 제안

1. **세션을 쓰기 전에 회사가 그대로인지 본다** (권장)
   - 로그인 때 응답의 회사 ID(또는 토큰 속 `companyId`)를 세션 파일 `user_info`에 남긴다.
   - 다시 쓸 때 로컬 DB(`YUNHEE_DB`)에서 `sys01_company`의 `sys01_loc_nm = <회사>` 행의 ID 와 비교해, 다르면(또는 행이 없으면) 세션을 버리고 새로 로그인한다. 한 줄 알림: `세션 버림: igo 회사 ID 바뀜(옛 … → 새 …)`.
2. **세션을 쓰지 않는 옵션**: `api`·`compare`·`test-compare`·`mapper-run`(로그인하는 명령 모두)에 `--fresh-login`(저장된 세션 무시, 새로 로그인하고 저장). 시험 스크립트가 "방금 회사를 만들었다"를 알 때 쓴다.
3. **세션 지우기 명령**: `yunhee session list` / `yunhee session clear [<회사>] [--user <id>]`. 지금은 파일 이름 규칙을 알아야 지울 수 있다(아래 3절).
4. 403·0행이 났을 때 결과 메모에 "저장된 세션 사용(로그인 시각 …)"을 붙이면 원인을 찾기 쉽다.

1이 있으면 2·3은 덜 급하다. 다만 DB 를 볼 수 없는 원격 서버 대상일 때를 위해 2는 있으면 좋다.

## 3. framework-sprt 에서 지금 피해 간 방법

`AssetERP/tools/tests/fixture-igo.sh` 3) 뼈대를 만든 직후:

```bash
rm -f "$ROOT"/.yunhee/sessions/*_"$LOC"_*.json "$ROOT"/../.yunhee/sessions/*_"$LOC"_*.json
```

- 세션 폴더가 `config.WORK_DIR` 기준이라 어느 쪽인지 몰라 두 곳을 지운다(실제로는 저장소 루트 `framework-sprt/.yunhee/sessions/`).
- 같은 문제는 kova(업무 시나리오, 시험마다 다시 만듦)에도 생길 수 있다 — 시나리오 실행기는 yunhee 를 쓰지 않고 직접 로그인해서 지금은 안 걸린다.

## 4. 검수 기준

- igo 를 지우고 다시 만든 뒤 세션 파일을 지우지 않고 `yunhee test-compare <목록> -c igo` → 새 회사로 로그인해 ok(제안 1), 또는 `--fresh-login` 으로 ok(제안 2).
- 같은 회사 ID 그대로면 세션을 계속 쓴다(로그인 횟수가 늘지 않음 — 로그인 실패 잠금 5회 규칙 때문에 중요).
