- 계기: `AssetERP/tools/yunhee-benchmark.sh`(설계 `docs/work/yunhee-benchmark-설계.md`)를 만들며 고정 소스 색인과 `analysis`·`drift` 출력을 독립 계산으로 대조하다가 찾았다. 032·033 항목은 영향 없음. 우선순위 **1 > 2 > 3**.

## 1. `index-src`: 소스 폴더에 `.git`이 없으면 **바깥 저장소**의 HEAD를 소스 기준으로 기록함 (가장 급함)

**재현**
```
cd /home/kdy987/work/framework-sprt                       # git 저장소 (브랜치 main, HEAD b27944b)
mkdir -p AssetERP/.yunhee/bench/src                       # IDMS-IC 의 `git archive` 를 푼 폴더 (.git 없음)
git -C ~/work/IDMS-IC archive 546a87d application/src/main/java | tar -x -C AssetERP/.yunhee/bench/src
yunhee index-src AssetERP/.yunhee/bench/src -t AssetERP/.yunhee/bench/index
→ 소스 b27944b (main, 2026-10-16 23:53) clean · 화면 503개 …
```
- 소스는 IDMS-IC(`546a87d`)인데, 요약·`_source.json`·화면 frontmatter는 **TOBE 저장소**의 `b27944b (main)`을 소스 기준으로 기록한다. `git -C <src_root> …`가 `src_root`의 조상 디렉터리에서 `.git`을 찾아 올라가기 때문이다.
- 영향: 이 색인으로 `drift`를 하면 엉뚱한 저장소 해시와 비교하고, 기준(baseline)도 틀린 커밋으로 기록된다. 조용히 틀리는 종류라 위험하다(경고 없음).
- 저장소 밖(`~/.cache/yunhee-bench/…`)에 풀면 올바르게 `vcs: none`으로 기록돼 우회했다.

**수정**
1. 소스 루트의 git 정보는 `git -C <src_root> rev-parse --show-toplevel`이 **`src_root` 자신과 같을 때만** 쓴다. 다르면 `vcs: none`으로 기록하고 요약에 한 줄: `⚠ 소스 폴더가 git 저장소의 루트가 아니다(바깥 저장소 <경로> 무시) — 파일 sha256 으로 기록`.
2. 소스 루트가 큰 저장소의 **하위 폴더**일 때(예: `<repo>/application`)는 쓰고 싶을 수 있으므로 옵션 `--vcs-root <경로>`를 둔다(기본: 위 1번 규칙).
3. `drift`는 색인의 `_source.json`이 `vcs: none`이면 "git 정보 없음 — sha256 비교" 한 줄을 머리에 낸다(지금도 동작하지만 안내가 없다).

**기대 (검증 ID `034-1`)**
```
yunhee index-src <git archive 로 푼 폴더 (저장소 안)> -t …
→ ⚠ 소스 폴더가 git 저장소의 루트가 아니다(바깥 저장소 /…/framework-sprt 무시)
→ 소스 (비-git) · 화면 503개 …
cat <index>/_source.json     # "vcs": "none"
```
- pytest: ① 임시 git 저장소 안에 `.git` 없는 하위 폴더를 소스로 주면 `vcs: none`과 경고 ② 소스 루트가 저장소 루트면 지금처럼 기록 ③ `--vcs-root`로 하위 폴더를 지정하면 그 저장소 정보를 기록 ④ 중첩 저장소(소스 루트에 자체 `.git`)는 그것을 쓴다.

## 2. `analysis screen --list`의 "줄 수" 열이 무엇인지 알 수 없음

**재현**
```
yunhee analysis screen Sys27_Tab_LoginManage --list --src-index docs/as-is/src
→ | Sys27_Tab_LoginManage | 51 | 2 | 6 | 1 |          # 줄 수 = 51
wc -l <소스>/…/Sys27_Tab_LoginManage.java               # 253
```
- AssetERP `01-변환목록.md`의 A21 "줄"은 254(원본 Java 줄 수)인데 `--list`는 51이다. 51이 어디서 나온 값인지(색인의 UI 절 줄? 메서드 본문 줄 합?) 출력만으로는 알 수 없고, 합계 행도 같은 열이라 "작업 규모"로 읽으면 크게 틀린다(큰 화면 `Emp00_Tab_TransInfo`는 33개 클래스인데 대표 클래스가 86줄로 나온다).

**수정**
1. 열 머리를 의미대로 바꾼다: 원본 파일 줄 수면 `줄(원본)`, 색인 UI 절 줄이면 `줄(UI절)`. 둘 다 필요하면 열을 둘로 나눈다.
2. `analysis screen --list --help`에 열 정의를 한 줄씩 적는다.
3. 합계 행에서 **연결·다른 도메인** 클래스를 제외하는 규칙(예: `합계 버튼 2`는 `Emp00_Lookup_SelectSingle`의 6을 뺀 값)이 있다면 합계 행 아래에 `※ 합계는 연결·다른 도메인 클래스 제외` 한 줄을 낸다.

**기대 (검증 ID `034-2`)**: 열 머리에서 의미가 읽히고, `줄(원본)`이면 `wc -l`과 ±1 이내로 같다.
- pytest: ① 열 머리 문구 ② 픽스처 클래스의 줄(원본) = 파일 줄 수 ③ 합계 행 주석.

## 3. `analysis screen --list`·`analysis ui` 등을 기계가 읽을 형식(`-o json`)으로

**현상**: `analysis` 유형 표(`yunhee analysis --list`)의 형식은 `screen`이 `md`뿐이다. 벤치마크는 마크다운 표를 `awk -F'|'`로 잘라 클래스·버튼 수를 읽는다(헤더·합계·"(연결·다른 도메인)" 꼬리표 처리가 필요하고, 열이 늘면 깨진다). `grid`·`model`은 이미 `json`이 있다.

**수정**
1. `analysis screen --list -o json`: `{"screen": "...", "classes": [{"name","lines","buttons","events","grids","linked": false}], "total": {...}}`
2. `analysis ui -o json`: 그룹별 합계와 클래스별 값, `--tobe`면 AS-IS/TOBE 칸 포함.
3. `analysis sql -o json`: `{"id","file","line","params":[…],"tables":[…],"functions":[…],"order_by":"…"}` — `-o md`의 `**테이블**:` 줄을 정규식으로 읽는 것을 없앤다.
4. 기본 출력(`md`)은 그대로.

**기대 (검증 ID `034-3`)**
```
yunhee analysis screen Sys27_Tab_LoginManage --list -o json | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['classes']), d['total']['buttons'])"
→ 2 2
```
- pytest: ① 스키마 키 ② md와 같은 값 ③ `linked` 구분 ④ 존재하지 않는 화면은 Exit 1 + 메시지(JSON이 아님).
