# 수정사항 036 — AssetERP E03·E03-1·E01-1·E04 변환에서 확인한 분석 도구의 빈틈 (대상 0.4.1)

- 작성: 2026-10-17, yunhee **0.4.1** 기준. 반영하면 **0.4.2**.
- 계기: AssetERP E03(법규개정내역)·E03-1(법규상세)·E01-1(법규 기한, 클래스 10개 2,840줄)·E04(체크리스트, 클래스 6개) 변환 중 `yunhee analysis`로 안 보여 **원본을 직접 읽어야 했던 것**을 모았다(작업기록 "yunhee 대신 다른 방법"). 새 명령은 없다. 전부 읽기 전용 분석의 출력 보강이다.
- 우리 쪽 확인: `tools/yunhee-benchmark.sh 취약` (범주 `취약` 시나리오 15~20, 이 수정이 반영되면 100%가 되어야 한다. 지금은 모두 0%에 가깝다).

## 1. `analysis sql … -o sql`이 `<if>`·`<choose>` 안의 조건을 지움 (036-1)

**재현**
```
yunhee analysis sql ics10_checklist.selectByAdmin -o sql -s <소스> --src-index <색인>
```
- 원본 XML은 `<choose><when test="checklistLClassId != null"> AND ics21_checklist_l_class_id = #{checklistLClassId} </when>…`인데, 출력은 빈 줄만 남고 **그 조건이 통째로 사라진다**(대분류·중분류 필터). `ics01_class_tree.selectByTypeCodePaging`의 `pagingCondition`(`classTreeId`·`detailSearchYn` 분기)도 같다. 이식할 때 가장 필요한 부분이라 XML을 직접 읽었다.

**수정**: 값이 없는 파라미터가 걸린 `<if>`/`<when>` 블록을 지우지 말고 주석 경계로 남긴다.
```
/* <if test="checklistLClassId != null"> */
AND ics21_checklist_l_class_id = :checklistLClassId
/* </if> */
```
- `-o sql`은 `--keep-conditions`(기본 켬 또는 옵션)로, 실행 가능한 SQL이 필요하면 `--param`으로 채워진 분기만 펼친다(지금처럼). `-o md`의 "조건 분기" 줄은 `when: \`dateType == 'reg'\``처럼 이미 나오지만 **그 안의 SQL 조각**이 없다 — 조각의 첫 줄 한 줄이라도 붙인다.

**기대 (검증 ID `036-1`)**: 위 명령의 출력에 `ics21_checklist_l_class_id`·`ics23_checklist_m_class_id` 비교 조건이 들어 있다.

## 2. `analysis screen --list`가 화면 안에서 만드는 클래스를 빠뜨림 (036-2)

**재현**
```
yunhee analysis screen Ics20_Tab_RevisionHistoryAdmin --list      # ics19_Grid_IcsList·ics20_Grid_FileList 없음
yunhee analysis screen Ics10_Tab_ChecklistAdmin --list             # Ics01_Lookup_SelectParent 없음
```
- 편집 폼이 `new ics19_Grid_IcsList()`·`new ics20_Grid_FileList()`로 쓰는 **서브 그리드 클래스**(이름이 소문자로 시작, 이벤트·그리드·아이콘 셀 보유)와, 조회창이 핸들러 안에서 `new Ics01_Lookup_SelectParent(callback)`로 여는 **조회창 속 조회창**이 목록에 안 나온다. 목록의 `연결` 표시는 필드로 가진 클래스만 잡는 듯하다.
- 그 때문에 `analysis ui` 대조표에서도 빠져 06 항목 10이 이 클래스들을 세지 못한다.

**수정**: 화면 소스의 `new <클래스>(` 표현식(필드 초기화·메서드 본문·익명 클래스 안 모두)과 `<클래스> x = new …`를 훑어 색인에 있는 클래스를 `(연결)`로 더한다. 이름 첫 글자 대소문자를 가리지 않는다. 한 단계만 따라가고(순환 방지) 연결의 연결은 `(연결·2단계)`로 표시한다.

**기대 (`036-2`)**: 위 두 명령의 목록에 각각 `ics19_Grid_IcsList`·`ics20_Grid_FileList`, `Ics01_Lookup_SelectParent`가 `(연결)`로 나온다.

## 3. `analysis method` 요약이 다른 조회창을 여는 호출과 그 인자를 안 보여 줌 (036-3)

**재현**
```
yunhee analysis method Ics10_Edit_Checklist.settings
→ 서비스 sch.Sch05_RelateIcs.modelUpdate (L254) 은 나오지만
  lookup.open("deadline", callback) (Ics01_Lookup_SelectMulti, actionCode "deadline") 가 없다
```
- 서비스 호출·분기는 인라인 핸들러 안까지 잘 나온다(좋다). 그러나 같은 핸들러 안의 **조회창 열기**(`new X().open("인자", cb)`)와 그 **문자열 인자**는 빠진다. 이 인자(`"classTree"` vs `"deadline"`)가 조회창의 동작을 바꾸는데 요약만 보고는 알 수 없어 원본을 읽었다.

**수정**: 요약에 `- 조회창 Ics01_Lookup_SelectMulti.open("deadline") (L238)` 한 줄을 더한다(대상 클래스가 색인에 있을 때, 상수 문자열·숫자 인자만).

**기대 (`036-3`)**: 위 출력에 `Ics01_Lookup_SelectMulti`와 `"deadline"`이 나온다.

## 4. `analysis model`이 별칭 getter를 계산 속성으로 알리지 않음 (036-4)

**재현**
```
yunhee analysis model Sch03_DeadlineModel
→ dayWeekName01 | dayWeekName01 | String |            ← resultMap 칸 비어 있음, 설명 없음
```
- 원본 모델은 `getDayWeekName01() { dayWeekName01 = this.dayWeekName; return dayWeekName01; }`·`setDayWeekName01(v) { this.dayWeekName = v; }`처럼 `*01`·`*02` 속성이 **기본 속성의 별칭**이다(편집기 바인딩용). 표에는 `keyId`만 `계산(getter L…)`로 표시되고 이 별칭들은 아무 설명이 없어, 화면 폼의 `*01`·`*02` 칸이 어느 DB 컬럼인지 알려면 모델 800줄을 읽어야 했다(E01-1).

**수정**: getter 본문이 `return this.<다른 필드>`·`x = this.<다른 필드>; return x` 꼴이면 resultMap 칸에 `별칭: <다른 필드>`(그 필드의 컬럼)을 적는다. setter가 다른 필드에 쓰는 경우도 같다.

**기대 (`036-4`)**: 위 출력의 `dayWeekName01` 행에 `별칭`과 `dayWeekName`이 나온다.

## 5. `compare`가 `PageRes`(`{total, rows}`) 응답을 풀지 못함 (036-5)

**재현**
```
yunhee compare GET /api/v1/ics/laws/lookup -p limit=50 -p offset=0 \
   --sql ics01_class_tree.selectByTypeCodePaging --param typeCode=IT --param companyId=0 … --grid Ics01_Lookup_SelectMulti
→ API rows=1, SQL rows=50 ❌  fields ⊇ grid cols ⚠️ (missing: classTreeCode, … 전부)
```
- 응답이 `data: {total, rows: […]}`이면 객체 하나를 행 1개로 센다. 페이징 API(C03 이후 모든 페이징 조회, E03 조회창)는 전부 이 모양이라 매번 `total`·행을 수동 대조해야 했다.

**수정**: `data`가 `rows` 배열을 가진 객체이면 `rows`를 행으로 보고(옵션 `--rows-key rows`, 기본은 자동 감지) `total`은 따로 `API total=186`로 보여 준다. 필드 대조도 `rows[0]` 기준.

**기대 (`036-5`)**: 위 명령이 `API rows=50, SQL rows=50 ✅ … (API total=…)`을 낸다(건수는 데이터에 따라 다름, 형식을 본다).

## 6. `analysis sql --param`에 매퍼가 모르는 이름을 줘도 조용함 (036-6)

**재현**
```
yunhee analysis sql sch03_deadline.selectByClassTreeId --param infoId=24762 --count
→ 0   (실제 매퍼 파라미터는 classTreeId — 틀린 이름이라 조건이 NULL이 되어 0건, 경고 없음)
```
- 같은 실수가 `compare --param`에서도 `SQL rows=0 ❌`로 나와 API가 틀린 줄 알고 시간을 썼다(E01-1).

**수정**: `--param`의 키가 그 SQL의 `파라미터` 목록에 없으면 즉시 `⚠ 알 수 없는 파라미터: infoId (매퍼 파라미터: classTreeId)`를 출력한다(`--count`·`-o sql`·`compare` 공통).

**기대 (`036-6`)**: 위 명령이 `알 수 없는 파라미터`와 `infoId`를 낸다.
